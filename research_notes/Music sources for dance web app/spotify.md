## 1. Web Playback SDK: controls, position reporting, browsers, Premium, DRM

### Takeaway
The SDK is an in-page, Premium-only player with seek and volume control, but it has no tempo control, no stated accuracy for playback position, and iOS-specific limits (volume cannot be set from JavaScript; audio must be unlocked by a tap). Spotify's documentation says it must not be used in commercial projects without written approval, and since March 2026 an app owned by an individual can serve at most five allowlisted users (section 4).

### Cited Findings
- `getCurrentState()`: "Collect metadata on local playback. It will return either a WebPlaybackState object or null depending on if the user is successfully connected." — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- `setVolume()`: "Set the local volume for the Web Playback SDK. Between 0 and 1." On iOS the docs add that the audio level is under the user's physical control: "The volume property is not settable in JavaScript. Reading the volume property always returns 1." — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- `seek(position_ms)`: "Seek to a position in the current track in local playback." The argument is an integer in milliseconds. — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- `activateElement()`: "Some browsers prevent autoplay of media by ensuring that all playback is triggered by synchronous event-paths originating from user interaction such as a click." It has to be called from a click handler before playback is transferred to the page, otherwise playback starts paused (paraphrase). — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- "Safari on iOS and other mobile browsers have restrictions for autoplay behaviour." When playback is transferred from another Spotify app, the browser sees the command as coming from Spotify's servers, not from the user (paraphrase). — [Getting Started with Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started)
- Browser support as stated by Spotify (search excerpt; the tool did not pin which of the two pages carries the sentence): supported by "most web browsers (Chrome, Firefox, Safari and Microsoft Edge) in both mobile (Android and iOS) and Desktop (macOS, Windows and Linux)". No per-version table was found. — [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk); [Web Playback SDK is out of beta! (2021-09-13)](https://developer.spotify.com/blog/2021-09-13-web-playback-sdk-out-of-beta)
- 13 Sept 2021: the SDK left beta; it "now supports mobile browsers for most scenarios. There are still some limitations around autoplay and background play", and `activateElement` was added for the first-interaction restriction. — [Web Playback SDK is out of beta! (2021-09-13)](https://developer.spotify.com/blog/2021-09-13-web-playback-sdk-out-of-beta)
- Premium: "The Web Playback SDK requires a Spotify Premium subscription". A second excerpt adds that mobile-only types of Premium subscription are excluded (page not pinned by the search tool; overview or the 2021 post). — [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk); [Web Playback SDK is out of beta! (2021-09-13)](https://developer.spotify.com/blog/2021-09-13-web-playback-sdk-out-of-beta)
- The `streaming` scope is available to the Web Playback SDK and "The user must have a Spotify Premium account." — [Scopes](https://developer.spotify.com/documentation/web-api/concepts/scopes)
- DRM: the reference says an initialization error is most likely due to the browser not supporting EME protection (paraphrase). — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- When the player sits in a cross-origin iframe, the iframe must allow `encrypted-media`; this affects Chrome since its Feature Policy disallows such features in iframes by default (paraphrase; attributed by the search tool to the Troubleshooting page). — [Troubleshooting](https://developer.spotify.com/documentation/embeds/tutorials/troubleshooting)
- Commercial use: "This SDK must not be used in commercial projects without Spotify's prior written approval." — [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk)
- The SDK reference also states that "the Spotify Platform can not be used to develop commercial streaming integrations". — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference)
- No tempo control: a reply in Spotify's developer forum (thread about six years old) says there is no way to change the speed of songs through the Web Playback SDK and suggests posting to the Ideas board. No later change was found. — [Spotify Community: Is a speed method on the roadmap for the Web Playback SDK](https://community.spotify.com/t5/Spotify-for-Developers/Is-a-speed-method-on-the-roadmap-for-the-Web-Playback-SDK/td-p/5072771)
- Speed-changing browser extensions for Spotify's own web player work by setting the standard playback-rate property on the web player's media element; one author reports the extension broke when Spotify updated the web player's code. This is a hack on open.spotify.com, not an SDK feature. — [ffoerg.de, 2021-04-24](https://ffoerg.de/posts/2021-04-24.shtml); [rnikko/spotify-playback-speed](https://github.com/rnikko/spotify-playback-speed)
- Position in practice: a developer polling `getCurrentState()` every second saw the reported position rise while the track was still buffering and then snap to the correct value when audio started; after a device switch the position kept rising beyond the track duration, while `paused` stayed false. — [spotify/web-playback-sdk issue #88](https://github.com/spotify/web-playback-sdk/issues/88); [issue #86](https://github.com/spotify/web-playback-sdk/issues/86)
- Another report: `player_state_changed` stopped firing and `getCurrentState` returned a position greater than the duration. — [Spotify Community: Web Player stops playing and player_state_changed…](https://community.spotify.com/t5/Spotify-for-Developers/Web-Player-stops-playing-and-player-state-changed-and/td-p/5183184)
- Tutorials show progress by polling `Player.getCurrentState`. — [How-To Geek: Build a Web Music Player With the Spotify API](https://www.howtogeek.com/introduction-to-web-programming-with-spotify-api/)
- A third-party binding of the SDK's state object lists `paused`, `position` and `track_window`. — [pub.dev spotify_sdk WebPlaybackState](https://pub.dev/documentation/spotify_sdk/3.0.2/spotify_sdk_web/WebPlaybackState-class.html)
- iOS/macOS Safari: several developers report that `activateElement()` alone does not unlock audio. One diagnosis: it resumes the AudioContext but does not call `play()` on the media element. Reported fixes: create `Spotify.Player()` inside the click handler, call `activateElement()` synchronously in the handler before any async work, and show a "press Play again" prompt on the `autoplay_failed` event. Several of these reports date from 2023. — [Spotify Community: Web Playback SDK doesn't work in Safari](https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-doesn-t-work-in-Safari/td-p/5556723); [fmeies/music-quiz PR #3](https://github.com/fmeies/music-quiz/pull/3); [ClooGin97/hitster PR #6](https://github.com/ClooGin97/hitster/pull/6); [theartcher/juke PR #1](https://github.com/theartcher/juke/pull/1)

### Inferences
- R1 (own buttons) is met on desktop and, with a first tap, on mobile. R4 (tempo) is not available and would also conflict with the "alter Spotify Content" rule (section 7).
- R2: Spotify publishes no accuracy figure. The app would have to extrapolate position from the last state with its own clock and re-anchor on every state change; the reported anomalies (position advancing during buffering) mean an error well above 30-50 ms can occur at start, after seeks and after stalls. Bluetooth or device output latency is not reported by the SDK at all.
- R5: playing the app's own Web Audio sounds next to the SDK is technically possible, and ducking would use `setVolume()`. On iOS that call has no effect, so ducking under the voice cannot work in iOS Safari.
- Because the audio is decrypted through EME inside Spotify's player, the app cannot reach the samples: no time-stretching, no in-browser beat detection.

### Gaps
- Not re-confirmed in this session (**unverified background**, high confidence): the SDK also has `pause()`, `resume()`, `togglePlay()`, `previousTrack()`, `nextTrack()`, `getVolume()`, `setName()`, `connect()`, `disconnect()`; events `ready`, `not_ready`, `player_state_changed`, `autoplay_failed`; errors `initialization_error`, `authentication_error`, `account_error`, `playback_error`. Starting a specific track is done through the Web API play endpoint with the SDK's `device_id`, not through an SDK method.
- Whether the state object carries `timestamp` and `duration` fields was not confirmed (the search found no evidence). **Unverified background:** the community TypeScript types (`@types/spotify-web-playback-sdk`, last updated November 2023) are believed to list `timestamp`, `duration` and `loading`.
- Which DRM systems are used (**unverified background:** Widevine in Chrome/Firefox/Edge, FairPlay in Safari) and what exactly happens on screen lock or in a background tab: no source found beyond Spotify's "limitations around autoplay and background play".
- No measured figures for position jitter in beat-synced visuals were found; the GitHub issues could not be opened (GitHub access for those repositories is not enabled in this session).
- Whether Spotify changed or deprecated the SDK itself in 2026: nothing found either way.

## 2. iFrame/Embed API (Spotify Embeds with the iFrame API controller)

### Takeaway
The embed controller can load a track, play, pause, resume, seek and report position, and it needs no client ID, so the five-user cap does not apply. But full-track playback depends on the visitor being logged in to Spotify in that browser, is reported to fall back to 30-second previews on mobile and Safari, and the widget may not be hidden, covered or altered.

### Cited Findings
- Controller methods: `loadEntity` (accepts a Spotify URI or a full URL; recommended for new integrations), `loadUri` (URIs only, kept for existing integrations), `play()`, `pause()`, `resume()` (resumes, or starts if playback never began), `togglePlay()`, `restart()`, `seek(seconds)`, `destroy()` (removes the Embed and its DOM element). Events: `ready`, `playback_started`, `playback_update`; the `playback_update` sample reads the position in milliseconds. — [iFrame API reference](https://developer.spotify.com/documentation/embeds/references/iframe-api)
- The iFrame API was introduced on 31 March 2022. — [Introducing the iFrame API (2022-03-31)](https://developer.spotify.com/blog/2022-03-31-iframe-api)
- Previews: "in some situations" the Embed only streams a preview clip of less than 30 seconds; without `allow="encrypted-media"` on the iframe the Embed only allows previews; modifying the iframe tag can cause the same (paraphrase). — [Embeds Troubleshooting](https://developer.spotify.com/documentation/embeds/tutorials/troubleshooting)
- Older official wording quoted in the forum: "The user must also be logged into spotify.com in their web browser and your <iframe> HTML must contain the allow="encrypted-media" attribute. In the cases where full track playback is not supported, we will play 30 second preview clips." — [Spotify Community: Spotify Play Button 30 second limit](https://community.spotify.com/t5/Other-Podcasts-Partners-etc/Spotify-Play-Button-30-second-limit/td-p/4552931)
- Forum statement: "Embeds do only play the full songs of a playlist if a user has Premium and is logged in on a desktop browser." — [Spotify Community: EMBED PLAYLISTS](https://community.spotify.com/t5/Spotify-for-Developers/EMBED-PLAYLISTS/td-p/5838936); contradicted on the Premium condition by third-party guides that say any logged-in user gets full playback and others get 30-second previews: [Microlink](https://microlink.io/tools/embed-url/spotify), [Elfsight](https://elfsight.com/tools/spotify-embed-generator/)
- One developer reports tracks forced to preview on mobile or Safari even for signed-in users, and that blocking third-party cookies stops the embed from seeing the Spotify session. — [TheKaoser/classical-portal PR #88](https://github.com/TheKaoser/classical-portal/pull/88)
- Inside Notion, full-song playback works only in the web version, in a browser already signed in to Spotify; desktop and mobile apps show previews. — [widgetsfornotion.com](https://widgetsfornotion.com/tools/embed-spotify-in-notion)
- Size: set the iframe width to 100% and make the container at least 280 pixels wide for an audio Embed; a music-video Embed needs at least 250×150 px (paraphrase). — [Creating an Embed](https://developer.spotify.com/documentation/embeds/tutorials/creating-an-embed)
- Hiding or covering: "You shall not obfuscate the Spotify Widgets in any way, whether by banner advertisements or by any other means, or alter the form or format of the Spotify Widgets from that made available by Spotify." — [Widget Terms of Use](https://developer.spotify.com/documentation/embeds/terms)
- The Widget Terms also bar integrating Spotify with "any non-interactive internet webcasting service or (ii) streams from another service", contain an "Editing, Modifying, and Altering" restriction, and have a "Games and Trivia Quizzes" section saying Spotify Content may not be built into game functionality without written approval (last two: paraphrase). Two versions of the Widget Terms are indexed (current site and an older beta site) and they are not identical. — [Widget Terms of Use](https://developer.spotify.com/documentation/embeds/terms)
- Embeds are outside the "Streaming" definition of the Developer Terms: "Please note that the use of (i) Widgets or (ii) Audio Preview Clips, are not included in the definition of Streaming for purposes of these Developer Terms." — [Spotify Developer Terms](https://developer.spotify.com/terms)

### Inferences
- R1 is met in principle (subject to browser autoplay rules). R4 is not available. No volume method appeared in the reference excerpt, so R5 ducking is probably not possible through the embed.
- For the stated audience (phones first), the embed is the weakest on the one thing that matters most: reports say mobile and Safari visitors get 30-second previews. This needs a hands-on test before any decision.
- Because Widgets are not "Streaming", the Streaming-SDA commercial ban and the development-mode user cap do not bite here; the Widget Terms and the policy's content rules still do.

### Gaps
- How often `playback_update` fires and how precise its position is: not found (search budget exhausted). Without a timestamp in the event, 30-50 ms accuracy is unlikely, but this is not sourced.
- Whether free logged-in users get full tracks in 2026: sources conflict and none is an official current statement.
- Exact wording of the Widget Terms sections on synchronisation, games and commercial use: only paraphrases were obtained.

## 3. Web API playback control of the user's active device (Spotify Connect)

### Takeaway
The player endpoints can start, pause and seek the user's own Spotify app (Premium only), but the reported position is network-delayed by hundreds of milliseconds to over a second with jitter, which is far outside the 30-50 ms target.

### Cited Findings
- Seek endpoint: "This API only works for users who have Spotify Premium. The order of execution is not guaranteed when you use this API with other Player API endpoints." `position_ms` is required; seeking past the end skips to the next song. — [Web API: Seek To Position](https://developer.spotify.com/documentation/web-api/reference/seek-to-position-in-currently-playing-track)
- Get Playback State returns `progress_ms` (may be null) and `timestamp`, a Unix millisecond timestamp of when the playback state last changed (play, pause, skip, scrub, new song) (paraphrase). — [Web API: Get Playback State](https://developer.spotify.com/documentation/web-api/reference/get-information-about-the-users-current-playback)
- Scopes: control needs `user-modify-playback-state`; reading state needs `user-read-playback-state`. — [Scopes](https://developer.spotify.com/documentation/web-api/concepts/scopes)
- Transfer Playback repeats the Premium-only restriction; the Web API overview is reported to say a Spotify Premium account is needed to use the Web API (paraphrase). — [Web API: Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback); [Web API overview](https://developer.spotify.com/documentation/web-api)
- February 2026 changelog: the User `product` field (subscription level) was removed, so an app can no longer read whether the user is Premium from the profile. — [Web API Changelog, February 2026](https://developer.spotify.com/documentation/web-api/references/changes/february-2026)
- Developer report: the `timestamp` field represents when the user started playback of the current song, so `Date.now() - timestamp` equals `progress_ms` plus client/server latency; this breaks after a manual seek. — [spotify/web-api issue #1073](https://github.com/spotify/web-api/issues/1073)
- Developer report: one visualiser hard-coded a 265 ms offset, but "the actual latency seems to fluctuate between 0 milliseconds and 1000 milliseconds". The search tool did not pin which of the returned GitHub issues this is; the two candidates are linked. — [spotify/web-api issue #1396, "Precisely Calculating Playback Progress"](https://github.com/spotify/web-api/issues/1396); [spotify/web-api issue #1203](https://github.com/spotify/web-api/issues/1203)
- Forum report: `progress_ms` "is always randomly delayed by 0.5-1.5s" and the timestamp in that response "is not working". — [Spotify Community: Web API precise playback progress](https://community.spotify.com/t5/Spotify-for-Developers/Web-API-precise-playback-progress/td-p/6130785)
- Other reports: `progress_ms` only updating on pause, play and seek; `progress_ms` sometimes null. — [Spotify Community: currently-playing returning incorrect progress_ms](https://community.spotify.com/t5/Spotify-for-Developers/currently-playing-returning-incorrect-progress-ms/td-p/5380840); [spotify/web-api issue #748](https://github.com/spotify/web-api/issues/748)
- Since 23 July 2026, development-mode quotas are counted per developer account, not per Client ID, and a 429 for an exhausted quota carries `"reason": "QUOTA_EXCEEDED"`. — [Web API Changelog, July 2026](https://developer.spotify.com/documentation/web-api/references/changes/july-2026)
- Controlling a background Spotify app still counts as streaming: ""Streaming" means using the Spotify Platform to enable playback of sound recordings available through the Spotify Service, including using the Spotify Platform to control a background Spotify application." — [Spotify Developer Terms](https://developer.spotify.com/terms)

### Inferences
- R1 is met with noticeable command latency; R2 fails (errors of 0.5-1.5 s reported, and they vary). The app cannot know the phone's real audio position through this route.
- The route is subject to the same development-mode cap (five users) and the same Streaming-SDA policy rules as the SDK.
- These developer reports are several years old; no evidence was found that accuracy improved.

### Gaps
- **Unverified background:** the rate limit is computed over a rolling 30-second window; the rate-limits page appeared in results but was not excerpted.
- Whether the player endpoints stayed available to development-mode apps after February 2026 was not confirmed from the migration guide (believed unchanged).
- How a phone's operating system mixes web-page audio with the Spotify app's audio (interruption or ducking) was not researched.

## 4. Developer access as of November 2026

### Takeaway
An independent developer can only run Spotify apps in development mode: the owner needs Premium, each app works for at most five allowlisted users, and extended quota (unlimited users) is open only to registered organisations with at least 250,000 monthly active users. No route was found that lets a free app by one person reach hundreds of users through the Web API or the Web Playback SDK.

### Cited Findings
- Current quota-modes page: "Up to 5 authenticated Spotify users can use an app that is in development mode" and "the app owner must have a Spotify Premium account for apps in development mode to function". — [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)
- Extended quota mode: apps "can be installed by an unlimited number of users and the allowlist in development mode no longer applies". — [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)
- Eligibility: "As of May 15th 2025, Spotify only accepts applications from organizations (not individuals)". Listed requirements: an established (legally registered) business entity, an active and launched service, at least 250k monthly active users, availability in key Spotify markets, commercial viability, adherence to the terms (list paraphrased). — [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)
- 15 April 2025 announcement: from 15 May 2025 extended Web API access is reserved for apps "with established, scalable, and impactful use cases"; developers who already had extended access were unaffected; applications filed before 15 May were reviewed under the old criteria. — [Updating the Criteria for Web API Extended Access (2025-04-15)](https://developer.spotify.com/blog/2025-04-15-updating-the-criteria-for-web-api-extended-access)
- Forum copy of that announcement: "The new criteria include: Having an established business entity · Operating an active and launched service · Maintaining at least 250k MAUs · Being available in key Spotify markets". — [Spotify Community: Updating the Criteria for Web API Extended Access](https://community.spotify.com/t5/Spotify-for-Developers/Updating-the-Criteria-for-Web-API-Extended-Access/td-p/6920661)
- 6 February 2026 post: "Development Mode use will require a Spotify Premium account. Developers will be limited to one Development Mode Client ID. Each Client ID will be limited to up to five authorized users." It applied to new Client IDs from 11 February and to existing ones from 9 March 2026. Development mode is described as reduced in scope to learning, experimentation and non-commercial personal projects (paraphrase). — [Update on Developer Access and Platform Security (2026-02-06)](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security)
- Stated reason: "Over time, advances in automation and AI have fundamentally altered the usage patterns and risk profile of developer access." The cap went from 25 test users (set when development mode was introduced in 2021) to five. — [TechCrunch, 2026-02-06](https://techcrunch.com/2026/02/06/spotify-changes-developer-mode-api-to-require-premium-accounts-limits-test-users/)
- Migration guide: new development-mode apps got the restrictions on 11 February 2026 and existing ones were migrated on 9 March 2026; "All Development Mode apps require the app owner to have an active Spotify Premium subscription"; "apps in extended quota mode are not affected by any of the changes described in this guide"; search results were cut from max 50 to max 10 (default 5). — [February 2026 Web API Dev Mode Changes: Migration Guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide)
- A Spotify community post says the endpoint-removal part was postponed for existing development-mode integrations, while the Premium requirement, the user cap and the one-Client-ID limit went ahead; a third-party tracker says no new date was given. — [Spotify Community: February 2026 update thread](https://community.spotify.com/t5/Spotify-for-Developers/February-2026-Spotify-for-Developers-update-thread/m-p/7361070); [checkleaked.cc](https://spotify.checkleaked.cc/spotify-web-api-alternative)
- Endpoints reported removed for development-mode apps (secondary sources): browse endpoints, new releases, artist top tracks, other users' profiles and playlists, batch fetches, market list; library write endpoints were consolidated. — [gebrielmolla19/Groupify issue #87](https://github.com/gebrielmolla19/Groupify/issues/87); [ramsayleung/rspotify issue #550](https://github.com/ramsayleung/rspotify/issues/550); [techbooky.com](https://www.techbooky.com/spotify-locks-developer-api-behind-premium-restricts-test-users/)
- March 2026: the `external_ids` field removed in February was restored for albums and tracks. — [Web API Changelog, March 2026](https://developer.spotify.com/documentation/web-api/references/changes/march-2026)
- 23 July 2026: the app limit was raised from 1 to 25 Client IDs per developer account; all development-mode Client IDs share one quota. The migration guide now says "As of July 2026, the Client IDs per developer limit has been increased to 25." — [Web API quota updates for Development Mode (2026-07-23)](https://developer.spotify.com/blog/2026-07-23-web-api-quota-updates); [Web API Changelog, July 2026](https://developer.spotify.com/documentation/web-api/references/changes/july-2026)
- A third-party guide states that after July 2026 the five-user limit still applies per development-mode app and the request quota is shared across the account (the search tool did not pin which guide; candidates linked). — [vorplabs.com](https://vorplabs.com/agent-tools/spotify-api-changes); [freeapihub.com](https://freeapihub.com/apis/spotify-web-api)
- The most recent official developer-access items found are the 23 July 2026 post and the July 2026 changelog. — [Web API Changelog, July 2026](https://developer.spotify.com/documentation/web-api/references/changes/july-2026)
- The Developer Terms are still "Version 10", effective 15 May 2025; no 2026 version was found. — [Spotify Developer Terms](https://developer.spotify.com/terms)
- Developer Terms on extended access: "If your SDA reaches a quota limit, you may be eligible to apply for extended access using the forms provided to you. You must meet (and continue to meet) all eligibility and other criteria to be considered for extended access, as determined by Spotify"; Spotify "makes no promise or guarantee that such extended access request will be approved". — [Spotify Developer Terms](https://developer.spotify.com/terms)

## 6. Beat data: Audio Analysis / Audio Features, third-party sources, shipping your own beat grid

### Takeaway
Spotify's beat, bar and tempo endpoints have been closed to new apps since 27 November 2024 and are marked deprecated, so the beat grid has to come from elsewhere. Third-party services give a single BPM value per song, not beat timestamps, so the realistic route is the developer's own analysis of lawfully obtained audio for a curated list.

### Cited Findings
- 27 November 2024: Spotify's post "Introducing some changes to our Web API" barred new use cases from Related Artists, Recommendations, Audio Features, Audio Analysis, Get Featured Playlists and Get Category's Playlists. — [Introducing some changes to our Web API (2024-11-27)](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api); [Spotify Community: Changes to Web API](https://community.spotify.com/t5/Spotify-for-Developers/Changes-to-Web-API/m-p/6541868)
- The audio-analysis reference page is labelled "Deprecated". — [Web API: Get Track's Audio Analysis](https://developer.spotify.com/documentation/web-api/reference/get-audio-analysis)
- Reports: the endpoints return 403 for apps created after November 2024; one developer whose app had a quota extension granted before November 2024 still got 403 on audio-features. — [Spotify Community: Web API Get Track's Audio Features 403 error](https://community.spotify.com/t5/Spotify-for-Developers/Web-API-Get-Track-s-Audio-Features-403-error/m-p/6916386); [Spotify Community: Access to deprecated Audio Features endpoint](https://community.spotify.com/t5/Spotify-for-Developers/Access-to-deprecated-Audio-Features-endpoint-for-personal/td-p/7419715)
- A developer in Spotify's forum reported that an existing app with a pending extension request also lost access, which conflicts with the wording of the announcement. — [Spotify Community: Changes to Web API](https://community.spotify.com/t5/Spotify-for-Developers/Changes-to-Web-API/m-p/6541868)
- 2026 developer blogs say there is still no official replacement (the search tool did not pin which blog; candidates linked). — [endpoint51.com](https://www.endpoint51.com/blog/spotify-api-2026-changes/); [dev.to](https://dev.to/birrings/spotifys-audiofeatures-api-died-in-2024-heres-what-i-built-to-replace-it-3dn3)
- "Spotify's Audio Analysis endpoint returned section boundaries, beat grids, and per-segment pitch/timbre data. No third-party API offers this." The usual workaround is running your own beat tracker; librosa's beat tracker and Essentia's RhythmExtractor2013 are named. (Vendor blog.) — [freqblog.com](https://freqblog.com/blog/spotify-audio-features-replacement-2026/)
- GetSongBPM: free API returning one BPM and one key per song, looked up by artist and title; "a link back to GetSongBPM.com is REQUIRED (website or store listing), or we will suspend your account without notice". — [GetSongBPM API](https://getsongbpm.com/api)
- Developers using GetSongBPM cite a documented 3,000 requests per hour, a required application registration and the usual half/double-tempo ambiguity (GitHub projects; the search tool did not pin which; candidates linked). — [reubenfirmin/TuneConsole issue #405](https://github.com/reubenfirmin/TuneConsole/issues/405); [Edios/HyperCycling PR #59](https://github.com/Edios/HyperCycling/pull/59); [ErikOrm/run-tracks](https://github.com/ErikOrm/run-tracks)

- Commercial BPM/key vendors advertising Spotify-compatible endpoints exist (vendor claims, untested). — [api.musicae.io](https://api.musicae.io/); [sonovault.now](https://sonovault.now/resources/spotify-audio-features-api)
- Policy limits on deriving data from Spotify itself: "Do not use the Spotify Platform or any Spotify Content to train a machine learning or AI model or otherwise ingest Spotify Content into a machine learning or AI model." Section III also bars analysing Spotify Content or the Spotify Service for purposes such as creating listenership metrics or user profiles (paraphrase). — [Spotify Developer Policy](https://developer.spotify.com/policy)
- The Developer Terms bar "stream ripping or other functionalities that make it easier for users to capture or otherwise make permanent copies of Spotify Content". — [Spotify Developer Terms](https://developer.spotify.com/terms)

### Inferences
- R3 cannot be met from Spotify. It can be met by analysing the developer's own lawful copies (purchased downloads or CDs) and shipping only numbers (tempo, beat-1 offset, beat times) keyed by Spotify track ID. No clause found prohibits shipping self-made data next to a Spotify ID; capturing Spotify's stream to analyse it would breach the stream-ripping and circumvention rules.
- Risk to manage: the developer's copy and Spotify's master of the "same" recording can differ in leading silence, edit or remaster, and one song has many track IDs. Each curated track needs a manual offset check against Spotify playback, and the stored grid should carry the track ID and duration it was verified against.
- Third-party BPM values (one number per song) help with tempo but not with where beat 1 falls, and swing-era recordings drift in tempo, so per-beat timestamps beat a fixed BPM grid.

- Licence terms of beat-tracking libraries (librosa, Essentia, madmom and similar) were not researched in this session.
- AcousticBrainz was named in the query but no result covered its status.

### Takeaway

## 8. The "virtual browser" idea

### Takeaway
Embedding open.spotify.com in an iframe is blocked by Spotify, and driving a remote browser logged in to the user's account runs against Spotify's User Guidelines (automated access, circumvention, copying and performing content) and re-transmits licensed audio from the developer's server. It would also add stream latency that defeats beat sync and cost about 0.42 US dollars per user-hour on the one priced service found.

### Cited Findings
- Framing: a compatibility table lists Spotify's regular URL as not embeddable ("open.spotify.com blocks") and says to use the embed URL; the general cause of "refused to connect" is an `X-Frame-Options` or CSP `frame-ancestors` header, which page JavaScript cannot override. — [Custom iFrame docs: Embed Blocked or Refused](https://docs.customiframe.com/troubleshooting/embed-blocked)
- Spotify User Guidelines prohibit crawling or scraping "by manual or automated means, including bots, scrapers, and spiders" to view, access or collect information, and using any part of the Services or Content to train an AI model (wording partly paraphrased). — [Spotify User Guidelines](https://www.spotify.com/us/legal/user-guidelines/)
- User Guidelines: "circumventing any technology used by Spotify, its licensors, or any third party, including any territorial or other content access restrictions applied by Spotify or its licensors". — [Spotify User Guidelines](https://www.spotify.com/us/legal/user-guidelines/)
- User Guidelines: "copying, reproducing, redistributing, "ripping," recording, transferring, performing" content (the list continues; rest not obtained). — [Spotify User Guidelines](https://www.spotify.com/us/legal/user-guidelines/)
- User Guidelines: "reverse-engineering, decompiling, disassembling, modifying, or creating derivative works, except where such restriction is expressly prohibited by applicable law." YouTube said Groovy violated its terms by "modifying the service and using it for commercial purposes". Groovy sourced about 98% of tracks from YouTube, was on over 16 million servers and had a paid tier. — [9to5Google](https://9to5google.com/2021/09/13/youtube-nukes-popular-groovy-bot-discord-music-service-for-breaking-platforms-tos/); [PC Gamer](https://www.pcgamer.com/google-has-killed-discords-best-music-bot/); [Lexology](https://www.lexology.com/library/detail.aspx?g=8e23fcae-1754-48cd-8f2b-0f518dbd96a2)
- Rythm came back in 2024 with a subscription model that shares revenue with labels and publishers, that is, as a licensed service. — [Wikipedia: Rythm (software)](https://en.wikipedia.org/wiki/Rythm_(software))
- The Developer Terms separately bar facilitating unauthorised access and "stream ripping", and "attempting to circumvent or render ineffective any geographical restrictions, including IP address-based restrictions". — [Spotify Developer Terms](https://developer.spotify.com/terms)

### Inferences
- Technically, a non-headless cloud Chrome with Widevine L3 can probably play Spotify's web player and its audio can be captured into a WebRTC stream. The obstacles are elsewhere.
- Sync: the animation would run in the user's browser while the audio arrives through a WebRTC stream with variable delay, so R2 gets worse, not better. Rendering the animation inside the remote browser would fix sync but turns the product into streamed video of Spotify playback.
- Cost: at 0.007 dollars per participant-minute, 1,000 users practising 2 hours a month is 120,000 minutes, about 770 dollars a month after the free allowance. That is incompatible with a free, donation-funded app.
- Security: the user would have to log in to Spotify inside a browser the developer controls. That is a credential-handling liability and looks to Spotify like account sharing or automation from data-centre addresses.
- Legal: the developer's server would receive licensed audio and transmit it onward to the user. The developer holds no licence for that transmission; the Groovy and Rythm cases show platforms act against exactly this pattern even when each listener could have played the content themselves. Capturing the decrypted output of a DRM player also raises anti-circumvention questions.
- Net: the idea fails on policy, law, cost and the sync requirement at once. It should be dropped.

### Gaps
- The actual response headers of open.spotify.com were not inspected (no network access to Spotify; one secondary source only).
- The password-sharing clause of the User Guidelines was not confirmed (**unverified background:** the guidelines list "providing your password to any other person or using any other person's username and password").
- Hyperbeam's own statement on DRM sites, its latency figures and its acceptable-use terms were not found. Browserbase and Kasm were not covered by any result.
- Case law on re-transmission was planned and not searched (budget exhausted). **Unverified background:** in ABC v. Aereo (US Supreme Court, 2014) and ITV Broadcasting v. TVCatchup (CJEU, C-607/11, 2013), internet re-transmission to individual users was held to be a public performance or communication to the public, in the EU case even though the users were entitled to receive the original broadcast.
- The shutdown of the shared-browser service Rabbit (2019) and how Kosmi or Hyperbeam's consumer product handle DRM services were not sourced.

## 9. Official routes to become a licensed partner

### Takeaway
The only published route is the extended-quota "partner application", which is closed to individuals and requires a registered business with 250,000 monthly active users; anything touching mixing, tempo or synchronisation has in practice been granted only to large partners through negotiated integrations. No programme was found that an independent developer with a free app could realistically enter.

### Cited Findings
- The quota-modes page describes a Quota Extension Request for "new potential partners" and says that once the Partner Application form is approved the app can be moved from development mode to extended quota mode (paraphrase). Since 15 May 2025 only organisations may apply. — [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)
- Approval is discretionary: Spotify "makes no promise or guarantee that such extended access request will be approved", and an approved extension covers only the reviewed use case; changes must be notified before use (paraphrase of the second part). — [Spotify Developer Terms](https://developer.spotify.com/terms)
- Commercial use of the Web Playback SDK needs "Spotify's prior written approval"; developers report the approval form can go unanswered for months. — [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk); [Spotify Community: Do I need approval for making a commercial app?](https://community.spotify.com/t5/Spotify-for-Developers/Do-I-need-approval-for-making-a-commercial-app/td-p/5019079)
- The licensed-integration model in practice: DJ software from AlphaTheta (rekordbox), Serato and Algoriddim (djay) got Spotify Premium streaming on 24 September 2025, with more DJ apps in September 2026. — [Spotify Newsroom, 2025-09-24](https://newsroom.spotify.com/2025-09-24/dj-software-integration-premium/)
- Spotify also runs a commercial hardware programme with its own onboarding for device makers. — [Commercial Hardware](https://developer.spotify.com/documentation/commercial-hardware)
- An accessibility developer asking for partner API access had to seek guidance in the public forum, which suggests there is no open application channel for small projects. — [Spotify Community: Requesting Guidance on Partner API Access](https://community.spotify.com/t5/Spotify-for-Developers/Accessibility-Requesting-Guidance-on-Partner-API-Access-for-NVDA/td-p/7226875)

### Inferences
- For this app the partner route is closed on three counts: not an organisation, far below 250,000 monthly active users, and a feature set (sync, overlap, tempo) that section III of the policy prohibits regardless of quota.
- A written request to Spotify costs little, but the forum record gives no example of an individual's free app being granted an exception since May 2025.

### Gaps
- What Spotify required of the DJ software partners (fees, technical terms) is not public in any source found.
- Spotify's "Open Access" and "Soloist" developer products appeared in search results by title only; their scope and relevance were not checked.
- No contact address or form for commercial partnership enquiries was confirmed.

## 10. Option-by-option fit against R1-R7

### Takeaway
No Spotify option meets the requirements together: the SDK and Connect routes are capped at five users and conflict with the content rules, the embed scales but is reported to give only previews on phones and offers no precise timing, and the virtual browser is neither permitted nor workable.

### Cited Findings
- SDK controls, iOS volume limit and commercial-approval sentence. — [Web Playback SDK Reference](https://developer.spotify.com/documentation/web-playback-sdk/reference); [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk)
- Embed controller methods and preview behaviour. — [iFrame API reference](https://developer.spotify.com/documentation/embeds/references/iframe-api); [Embeds Troubleshooting](https://developer.spotify.com/documentation/embeds/tutorials/troubleshooting)
- Connect position delays of 0.5-1.5 s. — [Spotify Community: Web API precise playback progress](https://community.spotify.com/t5/Spotify-for-Developers/Web-API-precise-playback-progress/td-p/6130785)
- Five-user development mode, organisations-only extended quota. — [Quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes)
- Synchronisation, overlap and game clauses. — [Spotify Developer Policy](https://developer.spotify.com/policy)
- Audio Analysis closed to new apps. — [Introducing some changes to our Web API (2024-11-27)](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api)

### Inferences

| Requirement | Web Playback SDK | iFrame/Embed API | Web API (Connect) | Virtual browser |
|---|---|---|---|---|
| R1 start, pause, seek from own buttons | Yes (first tap needed on mobile; Safari quirks reported) | Yes (`play`, `pause`, `resume`, `seek`) | Yes, with command latency; needs an active Spotify device | Possible only by automating Spotify's web player, which the User Guidelines prohibit |
| R2 position within 30-50 ms | Not guaranteed; position must be extrapolated; anomalies reported at start and after stalls | Unknown precision; no timestamp in the event; unlikely | No; 0.5-1.5 s delays reported | Worse: adds variable WebRTC delay |
| R3 beat grid | Not from Spotify; developer's own precomputed data | Same | Same | Same |
| R4 tempo change without pitch change | No method; altering content is prohibited | No | No | Only by tampering with the web player; prohibited |
| R5 own sounds on top, ducking | Technically yes on desktop and Android; no ducking on iOS (`setVolume` has no effect); the overlap clause prohibits it | Own sounds technically yes; no volume method found; overlap clause and Widget Terms apply | Depends on the device's audio mixing; overlap clause applies | Overlap clause plus re-transmission problem |
| R6 free app, donations, hundreds to thousands of users | No: five allowlisted users per app; extended quota closed to individuals; donation status unresolved | Scales (no client ID needed); donation status unresolved | No: same five-user cap | No: about 0.42 dollars per user-hour and not permitted |
| R7 users have a paid subscription | Required (Premium; mobile-only plans excluded) | Login required for full tracks; phones and Safari reported to get 30-second previews | Required for playback control | Not relevant |

- The policy problems (sections 5 and 7) apply to every route that uses Spotify's platform, embed included.
- The only arrangement that involves no Spotify integration at all is the user starting the song in their own Spotify app while the web app runs its animation from a tap-in or a manual "start" press. That avoids Spotify's developer rules because the app never touches Spotify, but it gives up R1 and R4 and makes R2 depend on the user's tap. It is mentioned here only as the boundary case; it was not researched.

### Gaps
- Nothing here was tested on devices, by instruction. The embed's behaviour on iOS Safari and Android Chrome for logged-in Premium users is the single most decision-relevant fact still unverified.
- All quotations need a direct check against the live Spotify pages before they are relied on in the final report (see the note at the top).
