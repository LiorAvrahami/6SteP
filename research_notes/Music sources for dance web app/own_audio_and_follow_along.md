## The user's own files: opening them, remembering them, decoding them, and how many listeners still own files

### Takeaway
Opening a local audio file works in every browser through `<input type="file">` (plus drag-and-drop on desktop). *Remembering* it is the weak point: persistent file handles exist only in Chromium (desktop 86+, Android 132+), and a private copy in OPFS/IndexedDB works everywhere but Safari deletes script-written data after seven days of browser use without interaction. MP3, AAC/M4A, WAV and FLAC decode in all current browsers; Ogg Vorbis and Opus only reached iOS with Safari 18.4; ALAC is Safari-only. I found no survey of file ownership — only revenue data (streaming 69.6% of 2025 global revenue, downloads falling for the 13th year running), which implies file owners are a small, shrinking minority.

### Cited Findings
**Opening a file**
- `<input type="file">` is supported since version 1 of Chrome, Firefox and Safari, including their mobile versions — [BCD input/file.json](https://github.com/mdn/browser-compat-data/blob/main/html/elements/input/file.json). The `accept` attribute takes `audio/*`, "meaning any audio file" — [MDN input type=file](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file).
- iOS Safari's file-input panel is built from three pickers only — the Files document picker, the photo library and the camera; WebKit's implementation contains no Music-library picker. It maps `accept="audio/*"` to the *movie* type ("UIImagePickerController doesn't allow audio-only recording, so show the video recorder for `audio/*`"), whereas specific MIME types and file extensions are converted to their own type identifiers, and that list is what the document picker is opened with — [WebKit WKFileUploadPanel.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/forms/WKFileUploadPanel.mm).
- Drag and drop: `DataTransferItem.getAsFile()` since Chrome 11, Firefox 50, Safari 5.1; dropping folders via `webkitGetAsEntry()` since Chrome 13, Firefox 50 (Firefox Android 141), Safari 11.1; `getAsFileSystemHandle()` only Chrome 86 / Chrome Android 132 — [BCD DataTransferItem.json](https://github.com/mdn/browser-compat-data/blob/main/api/DataTransferItem.json).
- File System Access API pickers (`showOpenFilePicker`, `showDirectoryPicker`): Chrome desktop 86 (2020-10-20), Chrome for Android 132 (2025-01-14); **not** in Firefox, Safari or iOS Safari (still marked experimental) — [BCD Window.json](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json), [BCD chrome_android.json](https://github.com/mdn/browser-compat-data/blob/main/browsers/chrome_android.json).
- Chrome's release post says the API, previously desktop-only, is "available on Android and in WebViews" from Chrome 132 **(search summary)** — [Chrome blog: New in Chrome 132](https://developer.chrome.com/blog/new-in-chrome-132).
- Conflict: the caniuse data file still lists Chrome for Android 157 as *not* supporting the File System Access API and gives 30.63% global usage for full support — [caniuse data native-filesystem-api.json](https://github.com/Fyrd/caniuse/blob/main/features-json/native-filesystem-api.json); contradicted by [BCD Window.json](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json) and the Chrome 132 post above (caniuse looks stale here).
- Choosing a whole folder with `<input webkitdirectory>`: Chrome 7, Firefox 50, Safari 11.1; Chrome Android 132 (before 131 only single files could be chosen), Firefox Android 142, iOS Safari 18.4 (from 11.3 to 18.3 the property "has no effect") — [BCD HTMLInputElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLInputElement.json).

**Remembering files between visits**
- File and directory handles "are serializable, which means that you can save a file or directory handle to IndexedDB"; because "permissions currently are not persisted between sessions", the page must call `queryPermission()` and, if needed, `requestPermission()` again (article version updated 2023-01-12) — [Chrome: File System Access API](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access). `queryPermission`/`requestPermission`: Chrome 86, Chrome Android 109, no Firefox, no Safari — [BCD FileSystemHandle.json](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemHandle.json).
- Origin Private File System (a private copy of the file inside the browser): `navigator.storage.getDirectory()` in Chrome 86 (Android 109), Firefox 111, Safari 15.2 (2021-12-13); `createSyncAccessHandle()` Chrome 102 / Safari 15.2 / Firefox 111; `createWritable()` reached Safari only in version 26 (2025-09-15) — [BCD StorageManager.json](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json), [BCD FileSystemFileHandle.json](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json).
- OPFS is "private to the origin of the page and not visible to the user", needs no permission prompts, and is "subject to browser storage quota restrictions" — [MDN Origin private file system](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system).
- `navigator.storage.persist()`: Chrome 55, Firefox 57, Safari 15.2; `estimate()`: Chrome 61, Firefox 57, Safari 17 — [BCD StorageManager.json](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json).
- Quotas: Safari (macOS 14 / iOS 17 and later) lets each origin store "up to around 60% of total disk" in browser apps and about 15% in other apps' web views, with an overall cap of 80% of disk; earlier Safari versions gave 1 GiB and then asked the user. Chromium: up to 60% of disk per origin. Firefox: the smaller of 10% of disk or 10 GiB in best-effort mode. Quotas are computed from total disk size, so they may not be reachable in practice — [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria); same figures on the [WebKit blog: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/) **(search summary)**.
- Eviction: under storage pressure browsers delete whole origins, least recently used first, skipping origins granted persistence. Safari additionally evicts proactively: "If an origin has no user interaction, such as click or tap, in the last seven days of browser use, its data created from script will be deleted" (when cross-site tracking prevention is on, the default) — [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- Web apps added to the Home Screen are exempt from the seven-day rule and keep their own day counter **(search summary of WebKit's 2020 announcement and press coverage)** — [iTnews](https://www.itnews.com.au/news/apple-cops-flak-for-deleting-local-browser-storage-after-7-days-539833).

- Ogg Vorbis: Chrome and Firefox always; Safari and iOS Safari fully only from 18.4 (2025-03-31); iOS 17.4-18.3 had the Vorbis codec but not the Ogg container; earlier iOS none — [caniuse ogg-vorbis](https://github.com/Fyrd/caniuse/blob/main/features-json/ogg-vorbis.json).

- `decodeAudioData()` (Chrome 14, Firefox 25, Safari 6) "only works on complete file data, not fragments", and the result is resampled to the AudioContext's sample rate — [MDN decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData), [BCD BaseAudioContext.json](https://github.com/mdn/browser-compat-data/blob/main/api/BaseAudioContext.json). Safari 17 "Added support for calculating quota based on disk space" — [Safari 17 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-17-release-notes).

### Inferences
- Memory is the main phone risk of the "decode the whole file" route: a 3-minute stereo track decoded to 32-bit float is about 63.5 MB at 44.1 kHz (69 MB at 48 kHz), a 5-minute track about 106-115 MB (arithmetic from the AudioBuffer format above). Analysis can run on a mono, down-sampled copy; playback at normal speed can use the `<audio>` element on the original compressed file.
- On iPhone the user's songs must therefore sit somewhere the Files app can see (On My iPhone, iCloud Drive, another file provider); tracks that live only in the Music app's library cannot be picked. Because of the `audio/*` → movie mapping, the input should list explicit types (for example `accept=".mp3,.m4a,.aac,.wav,.flac,audio/mpeg,audio/mp4,audio/wav,audio/flac"`) instead of `audio/*`, otherwise ordinary audio files may be unselectable and a video-capture option may appear — an expectation from reading the source, to be confirmed on a device.
- A robust "remember my songs" design does not depend on keeping the audio: store a content hash of the file together with its beat grid and offset (a few kB) in IndexedDB, optionally keep the audio in OPFS, and always offer "pick the file again". On iOS the seven-day eviction means the app should encourage "Add to Home Screen" and treat stored audio as a cache.
- On Chromium (desktop and, since 132, Android) the nicest experience is a stored directory handle ("my practice-music folder") re-authorised with one tap per session; iOS Safari has no equivalent, only a file picker each time or the OPFS copy.
- Different decoders can place the same MP3 20-40 ms apart (see the All-In-One finding in the next section), so a beat grid measured with one decoder is not automatically valid in another; the grid should be anchored by matching the audio itself (cross-correlation), not by assuming identical decoding.
- Revenue share is only a proxy for ownership, but with streaming near 70% of revenue and downloads shrinking every year since about 2012, "bring your own file" can only be one of several modes for a general audience.

## In-browser beat tracking for a whole file (libraries, jazz and swing accuracy, downbeats, cost, licences)

### Takeaway
The only open-source tracker with both strong published accuracy and a permissive licence for code *and* weights is "Beat This!" (ISMIR 2024, MIT; trained on 16 datasets including two jazz sets); ONNX exports exist (about 10 MB small, about 83 MB full) and at least one project runs it in the browser with ONNX Runtime Web. The classic JavaScript detectors return one tempo (and at best a first-beat offset), assume a steady beat and default to a 90-180 BPM window — unsuitable for drifting swing recordings at 110-200 BPM. No library outputs the 8-count phrase start, and downbeat accuracy on jazz is weak (0.63 F-measure in the one jazz-specific evaluation found), so a manual "tap on 1" correction step is unavoidable.

### Cited Findings
**Beat This! (transformer, beats and downbeats, offline)**
- Official code needs Python and PyTorch; "the code and the published model weights are released under the MIT license"; main model about 78 MB per checkpoint, small model about 8.1 MB; main models were trained on all data except GTZAN, which is the held-out test set; an optional DBN post-processor needs madmom — [CPJKU/beat_this README](https://github.com/CPJKU/beat_this/blob/main/README.md).
- Training annotations cover 16 datasets including the jazz sets **JAAH** ("Jazz Audio-Aligned Harmony"; beat annotations corrected and downbeats added by the authors) and **Filosax**, plus Ballroom, Beatles, Hainsworth, Harmonix, RWC, SMC, GTZAN and others — [CPJKU/beat_this_annotations README](https://github.com/CPJKU/beat_this_annotations/blob/main/README.md), [MTG/JAAH README](https://github.com/MTG/JAAH/blob/master/README.md).
- Reported GTZAN test scores: F1 89.1 for beats and 78.3 for downbeats, state of the art without DBN post-processing; removing the DBN lowers the continuity metrics (CMLt, AMLt) **(search summary of the paper and of benchmark listings; matches my recollection of the paper's Table 2)** — [arXiv 2407.21658](https://arxiv.org/abs/2407.21658).
- The standard beat F-measure counts a beat as correct within ±70 ms (`f_measure_threshold=0.07`) and ignores the first 5 s — [mir_eval beat.py](https://github.com/mir-evaluation/mir_eval/blob/main/mir_eval/beat.py).
- ONNX ports: a Rust port (MIT) ships a log-mel front end of about 270 kB, a small model of about 10 MB and a full FP32 model of about 83 MB; it matches the Python reference with F-measure 1.0 (full) and at least 0.99 (small) at ±70 ms; output resolution is one frame = 20 ms; on an Apple M4 laptop CPU a 4:32 file takes 4.6 s and a 13:48 file about 12 s; peak memory about 534 MiB for 5 minutes of audio with the full model; it implements only the "minimal" post-processing, no DBN — [danigb/beat-this-rs README](https://github.com/danigb/beat-this-rs/blob/main/README.md), [its CHANGELOG](https://github.com/danigb/beat-this-rs/blob/main/CHANGELOG.md). A C++ port bundles a roughly 97 MB ONNX model (opset 14) — [mosynthkey/beat_this_cpp README](https://github.com/mosynthkey/beat_this_cpp/blob/main/README.md).
- Browser use: a Hugging Face model packages Beat This! as ONNX for ONNX Runtime Web's WebGPU backend and notes the WASM backend gives identical results but runs much slower; a Hugging Face Space ("Loop Maestro") loads onnxruntime-web and uses Beat This! in the page **(search summaries)** — [musetric/beat-this-onnx](https://huggingface.co/musetric/beat-this-onnx), [Loop Maestro](https://huggingface.co/spaces/jorisvaneyghen/loop_maestro).
- Runtime cost: `onnxruntime-web` 1.31.1 (MIT, published 2026-10-26) ships a 14.5 MB CPU WebAssembly binary (`ort-wasm-simd-threaded.wasm`) and a 28.8 MB WebGPU ("jsep") binary — [npm onnxruntime-web](https://www.npmjs.com/package/onnxruntime-web).
- Platform prerequisites: WebAssembly SIMD in Chrome 91, Firefox 89, Safari 16.4; WebGPU in Chrome Android 121, Safari and iOS Safari 26, Firefox 141 (desktop, partial), not Firefox Android; SharedArrayBuffer (needed for WASM threads) in Chrome Android 89, Safari 15.2 — [BCD fixed-width-SIMD.json](https://github.com/mdn/browser-compat-data/blob/main/webassembly/fixed-width-SIMD.json), [BCD GPU.json](https://github.com/mdn/browser-compat-data/blob/main/api/GPU.json), [BCD SharedArrayBuffer.json](https://github.com/mdn/browser-compat-data/blob/main/javascript/builtins/SharedArrayBuffer.json).

**Other machine-learning trackers (Python only; useful for the developer's offline preparation, R6)**
- madmom: source code BSD, but "all model and data files are distributed under the Creative Commons Attribution-NonCommercial-ShareAlike 4.0 license" — [CPJKU/madmom README](https://github.com/CPJKU/madmom/blob/main/README.rst).
- BeatNet: CC BY 4.0; joint beat, downbeat, tempo and meter; four modes (microphone streaming, real-time, online, offline with madmom's DBN); expects 22,050 Hz input; 50 frames per second — [mjhydri/BeatNet README](https://github.com/mjhydri/BeatNet/blob/main/README.md).
- All-In-One (beats, downbeats, song structure): trained on the Harmonix Set (8-fold); its README warns that "using a different MP3 decoder can yield different offsets … variations of about 20~40ms, which is problematic for tasks requiring precise timing like beat tracking, where the conventional tolerance is just 70ms" — [mir-aidj/all-in-one README](https://github.com/mir-aidj/all-in-one/blob/main/README.md).

**Libraries that run in the browser today**
- Essentia.js: AGPL-3.0; latest npm release 0.1.3 dates from 2021-06-24; WebAssembly binary 1.94 MB (about 2.5 MB as a single ES module) — [npm essentia.js](https://www.npmjs.com/package/essentia.js), [MTG/essentia.js README](https://github.com/MTG/essentia.js/blob/master/README.md). Essentia itself is "available under an open licence, Affero GPLv3, for non-commercial applications" with commercial licences on request; its ML models are CC BY-NC-SA 4.0 — [Essentia licensing](https://github.com/MTG/essentia/blob/master/doc/sphinxdoc/licensing_information.rst).
- Essentia's beat trackers (`RhythmExtractor2013` with the "multifeature" or "degara" method) need 44,100 Hz input and output beat positions, BPM and a confidence between 0 and 5.32, where 1.5-3.5 means "good confidence, accuracy around 80% in AMLt measure" and below 1 means the signal "is hard for the employed candidate beat trackers" — [beattrackermultifeature.cpp](https://github.com/MTG/essentia/blob/master/src/algorithms/rhythm/beattrackermultifeature.cpp), [rhythmextractor2013.cpp](https://github.com/MTG/essentia/blob/master/src/algorithms/rhythm/rhythmextractor2013.cpp). Essentia's tutorial says the algorithm relies on statistics of the whole track and is therefore not suited to real-time detection **(search summary)** — [Essentia beat detection tutorial](https://essentia.upf.edu/tutorial_rhythm_beatdetection.html).
- aubio: GPL v3 or later; "tempo tracking and beat detection" — [aubio README](https://github.com/aubio/aubio/blob/master/README.md). `aubiojs` (aubio compiled with Emscripten; pitch and tempo detection; 204 kB; last published 2022-11-08) — [npm aubiojs](https://www.npmjs.com/package/aubiojs).
- `web-audio-beat-detector` (MIT, 16 kB bundle, v8.2.39 of 2026-08-26): returns the tempo of an AudioBuffer, and `guess()` adds "the offset of the first beat"; expects 90-180 BPM by default; "not as complex (and expensive to compute) as many others. But it yields surprisingly good results especially for electronic music" — [README](https://github.com/chrisguttandin/web-audio-beat-detector/blob/master/README.md), [npm](https://www.npmjs.com/package/web-audio-beat-detector).
- `realtime-bpm-analyzer` (Apache-2.0, v6.2.1 published 2026-11-17, AudioWorklet, about 129 kB): tempo only, for files, streams and microphone; reports within 90-180 BPM by default, so "a track at about 180 BPM or faster can read at half"; "music without a steady beat is the hard case: expect a lower confidence, a wrong reading or none" — [npm realtime-bpm-analyzer](https://www.npmjs.com/package/realtime-bpm-analyzer).
- `@audio/beat` (MIT, pure JavaScript, 2026): spectral-flux onsets, autocorrelation or comb-filter tempo, and a dynamic-programming beat tracker after Ellis (2007); companion `@audio/mir-downbeat` scores each bar phase "by bass energy, onset strength and chroma flux" (a heuristic, default 4 beats per bar) — [npm @audio/beat](https://www.npmjs.com/package/@audio/beat), [npm @audio/mir-downbeat](https://www.npmjs.com/package/@audio/mir-downbeat).
- BeatDetektor: MIT, a 2009 C++/JavaScript BPM detection library — [README](https://github.com/cjcliffe/beatdetektor/blob/master/README). Meyda: MIT, an "audio feature extraction library" (no beat tracker of its own) — [meyda README](https://github.com/meyda/meyda/blob/main/README.md).
- Superpowered's proprietary web SDK lists "bpm detection … beatgrid detection" among its features — [Superpowered web SDK README](https://github.com/superpoweredSDK/web-audio-javascript-webassembly-SDK-interactive-audio/blob/master/README.md).

**Evidence on jazz and swing**
- Jazz Trio Database (about 45 hours of jazz piano-trio recordings annotated by an automated pipeline on source-separated audio; TISMIR 2024): mean beat F-measure 0.97 against ground truth, but downbeat F-measure only 0.63 with high variance **(search summary; the summary did not say which tracker produced the figures)** — [TISMIR article](https://transactions.ismir.net/articles/10.5334/tismir.186), [dataset README](https://github.com/HuwCheston/Jazz-Trio-Database/blob/main/README.md).
- A thesis comparing librosa's dynamic-programming tracker, Essentia's multi-feature tracker and madmom's RNN on jazz drums and double bass found that every algorithm produced octave (half/double tempo) errors and off-beat detections, with madmom's RNN generally best **(search summary)** — [DiVA record](https://www.diva-portal.org/smash/record.jsf?pid=diva2:1701786).

### Inferences
- For unknown user files the realistic pipeline is: decode → mono 22 kHz → Beat This! (small model, about 10 MB, plus the 14.5 MB runtime, both cacheable) in a Web Worker → fit a smooth tempo curve through the detected beats → show the result and let the user fix "which beat is 1" and "where the 8-count starts" by tapping. Cheap DSP detectors can serve as an instant preview but not as the grid.
- Published accuracy overstates what the app needs: scores use a ±70 ms window, the app wants 30-50 ms; the network's frame is 20 ms; and decoder offsets add up to 20-40 ms. Refining each beat to the nearest onset peak and smoothing the tempo curve should recover most of this, but it has to be tested on swing recordings.
- Swing-specific failure modes to design for: (1) half/double tempo at 180-200 BPM (default 90-180 windows in the JavaScript detectors make this likely); (2) locking onto the off-beat (hi-hat and hand claps on 2 and 4); (3) bar phase (1 versus 3) — downbeat scores of 0.63-0.78 mean many songs will have a wrong "1"; (4) the 8-count (two-bar) phrase is not modelled by any library found.
- Speed on phones is unknown. The only hard number is desktop-class: about 60 times faster than real time on an M4 CPU (the README's table does not name the model; the tool's default is the full one). Single-threaded WebAssembly on a mid-range phone could be one to two orders of magnitude slower, so a 3-minute song may take from several seconds (small model, WebGPU) to more than a minute (full model, WASM). This is an estimate, not a measurement.
- Licences shape the stack: Essentia.js (AGPL), aubio (GPL) and BTrack (GPL) are usable only if the whole app is released under a compatible copyleft licence; madmom's and Essentia's models are non-commercial share-alike; Beat This!, ONNX Runtime Web, `@audio/beat`, `web-audio-beat-detector` are permissive.
- Best division of labour for R6: the developer runs Beat This! (or madmom) offline for the curated list and hand-corrects the grids; in-browser analysis is the fallback for files that cannot be matched to the curated list.

### Gaps
- Per-dataset Beat This! results (JAAH, Filosax), GTZAN jazz-only results and the small model's scores were not retrievable (arXiv blocked). No published evaluation specific to swing-era big-band recordings or to swung-eighth feel was found.
- No measured inference time or memory for Beat This! (or any neural tracker) in a phone browser; the Essentia.js papers' browser benchmarks (TISMIR 2021) could not be opened.
- MIREX result tables were not consulted.

## Matching a user's file to a known recording so a prepared beat grid can be reused

### Takeaway
This is practical and can run entirely in the browser: a fingerprint (Chromaprint WASM, 100-300 kB, or Olaf's 75 kB WASM module) says *which* curated recording the file is, and a cross-correlation of compact features can then give the time offset to about 10 ms (the accuracy the BBC states for its MFCC cross-correlation tool). Chromaprint alone is too coarse for alignment (one fingerprint item every 124 ms), and re-masters or transfers at a slightly different speed need a matcher that also estimates the time factor.

### Cited Findings
- Chromaprint describes itself as "designed to identify near-identical audio … not a general purpose audio fingerprinting solution. It trades precision and robustness for search performance. The target use cases are full audio file identification, duplicate audio file detection and long audio stream monitoring" — [rusty-chromaprint README (quoting Chromaprint)](https://github.com/darksv/rusty-chromaprint/blob/main/README.md).
- Chromaprint's own code is MIT, but because it bundles FFmpeg parts "as a whole, Chromaprint should be therefore considered to be licensed under the LGPL 2.1" — [Chromaprint LICENSE.md](https://github.com/acoustid/chromaprint/blob/master/LICENSE.md).
- Chromaprint analyses audio at 11,025 Hz with 4,096-sample frames and an overlap of 4096 − 4096/3 samples — [fingerprinter_configuration.cpp](https://github.com/acoustid/chromaprint/blob/master/src/fingerprinter_configuration.cpp), [fingerprinter_configuration.h](https://github.com/acoustid/chromaprint/blob/master/src/fingerprinter_configuration.h).
- Browser builds exist: `@unimusic/chromaprint` (MIT wrapper, Chromaprint compiled to WASM, 104 kB binary, 2025-07), `rusty-chromaprint-wasm` (MIT, 294 kB binary, 2026-03), `chromaprint-web` (2026-10, marked unlicensed) — [npm @unimusic/chromaprint](https://www.npmjs.com/package/@unimusic/chromaprint), [npm rusty-chromaprint-wasm](https://www.npmjs.com/package/rusty-chromaprint-wasm), [npm chromaprint-web](https://www.npmjs.com/package/chromaprint-web).
- The Rust port can compare two fingerprints and list their common segments with start and end times in each file and a score (example: 0:04.83-0:19.44 in file 1 matches 0:00.00-0:14.61 in file 2, score 0.69) — [rusty-chromaprint README](https://github.com/darksv/rusty-chromaprint/blob/main/README.md).
- The public AcoustID service maps a fingerprint and duration to recording identifiers and metadata; the Python client needs an API key, limits itself to 3 queries per second, and decodes only the first 120 seconds of a file — [pyacoustid README](https://github.com/beetbox/pyacoustid/blob/master/README.rst).
- Olaf (landmark fingerprinting in portable C): compiles to "a small (about 75KB) WebAssembly module" that "runs in an AudioWorklet which resamples the audio to 16kHz" and matches microphone input, a test query or a local file in the browser, with an in-memory index; matches report `query_offset`, `reference_start` and `reference_stop`; a file counts as matched at 20 or more matching fingerprints; its evaluation includes a "time-accuracy check (fraction of correct hits whose reported position lands within 100 ms of the true cut offset)" and distortions including 0.5/1/3% tempo, pitch and speed changes; 100,000 tracks (340 days of audio) fit in a 15 GB index; licence AGPL-3.0; the README warns about patents US7627477 B2 and US6990453 — [Olaf README](https://github.com/JorenSix/Olaf/blob/master/README.md), [Olaf evaluation notes](https://github.com/JorenSix/Olaf/blob/master/eval/README.md), [Olaf LICENSE](https://github.com/JorenSix/Olaf/blob/master/LICENSE).
- Panako (Java, AGPL-3.0) is built for recordings whose speed differs: it tolerates pitch-shift, time-stretch and speed changes (its self-test applies a random speed-up between 93% and 107%) and reports a "time factor" and "frequency factor" per match — [Panako README](https://github.com/JorenSix/Panako/blob/master/README.textile).
- Offset finding by cross-correlation: the BBC's audio-offset-finder cross-correlates standardised MFCCs after resampling to 8 kHz; "the accuracy is typically to within about 0.01s"; a standard score above ten "is likely to be correct", below five unlikely (Python with FFmpeg) — [bbc/audio-offset-finder README](https://github.com/bbc/audio-offset-finder/blob/master/README.md). Another alignment package states "correlation is more precise than fingerprints and will always give a best alignment unlike fingerprinting, which can return no alignment" — [audalign README](https://github.com/benfmiller/audalign/blob/main/README.md).
- Why an offset step is always needed: "any audio edits, including re-encoding, will change the timing" — [osu! wiki: How to time songs](https://github.com/ppy/osu-wiki/blob/master/wiki/Guides/How_to_time_songs/en.md); and MP3 decoders differ by 20-40 ms — [all-in-one README](https://github.com/mir-aidj/all-in-one/blob/main/README.md).

### Inferences
- Chromaprint's time resolution is one item per 1,365 samples at 11,025 Hz = 123.8 ms (computed from the constants above), so a Chromaprint match fixes the offset to about ±60 ms at best — enough to identify the recording, not enough for R2.
- A workable two-step design without distributing any audio: (1) identify the recording with a fingerprint computed in the browser and compared against fingerprints shipped with the app for the curated list (no network service needed for a list of tens or hundreds of songs; AcoustID is an optional extra that also needs a key and is meant for whole-file lookups); (2) refine the offset by cross-correlating the file's onset-strength envelope with a stored envelope of the reference (about 100 frames per second × 1 byte ≈ 18 kB for three minutes), giving roughly 10 ms. If the correlation peak is weak, or drifts across the song, the file is a different master or speed, and the app should fall back to analysis.
- Swing-era recordings exist in many transfers and re-masters with different lead-in silence, speed (and sometimes different takes under the same title). Step 2 must therefore test for a speed ratio (correlate at the start and at the end of the song) and the beat grid must be stretchable by that ratio.
- Olaf's index size works out at about 150 kB per track (15 GB / 100,000 tracks), so a curated list of 100 songs is on the order of 15 MB before compression — loadable on demand per song family; but its AGPL licence and the patent warning are real constraints.

### Gaps
- No published accuracy for Chromaprint on re-masters or for any of these tools on historical swing transfers. No browser benchmark for fingerprinting a full song on a phone (Olaf states 80 times real time for queries on a desktop index).
- AcoustID's terms (free for non-commercial use, as I recall) were not re-read; acoustid.org was unreachable.

## Time-stretching in the browser

### Takeaway
Two routes meet R4. The built-in route — `<audio>` with `playbackRate` and `preservesPitch` — works in every current browser, uses WSOLA in Chrome and Apple's "spectral" music algorithm in Safari, and costs nothing to ship, but leaves the app with two clocks (and in Safari before version 27 the element's `currentTime` only advanced in steps). The library route — Signalsmith Stretch (MIT, 111 kB, AudioWorklet + WASM) inside the Web Audio graph — lets the app schedule "song position X at audio-clock time T at rate R", which solves R1, R2, R4 and R5 on one clock. Rubber Band (GPL/commercial) and Superpowered (proprietary, licence required before public launch) are harder to adopt; no measured phone CPU figures were found for any of them.

### Cited Findings
**Built-in: `HTMLMediaElement.playbackRate` + `preservesPitch`**
- `preservesPitch` defaults to `true`; unprefixed in Chrome 86, Firefox 101, Safari and iOS Safari 17.2 (2023-12-11), with `webkitPreservesPitch` available in Safari since version 4; `playbackRate` itself is universal — [BCD HTMLMediaElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLMediaElement.json), [MDN preservesPitch](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preservesPitch).
- "The audio is muted when the fast forward or slow motion is outside a useful range (for example, Gecko mutes the sound outside the range 0.25 to 4.0)" — [MDN playbackRate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playbackRate).
- Chrome's implementation is Waveform Similarity Overlap-and-Add (WSOLA) with a 20 ms overlap-add window and a ±30 ms search interval; "audio at very low or very high playback rates are muted to preserve quality"; with `preservesPitch = false` it resamples instead — [Chromium audio_renderer_algorithm.cc](https://github.com/chromium/chromium/blob/main/media/filters/audio_renderer_algorithm.cc), [audio_renderer_algorithm.h](https://github.com/chromium/chromium/blob/main/media/filters/audio_renderer_algorithm.h). Chrome accepts rates from 0.0625 to 16 — [html_media_element.h](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/html/media/html_media_element.h).
- WebKit on Apple platforms selects `AVAudioTimePitchAlgorithmSpectral` whenever pitch is preserved and the rate is not 1 (for its "best all-around" and "best for music" settings; `TimeDomain` only for "best for speech"; `Varispeed` when pitch is not preserved) — [WebKit MediaSessionManagerCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/cocoa/MediaSessionManagerCocoa.mm). Apple documents Spectral as "a highest-quality time pitch algorithm that's suitable for music … the most computationally intensive", rates 1/32 to 32, and TimeDomain as "modest quality … suitable for voice" — [Apple: spectral](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/spectral), [Apple: timeDomain](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/timedomain).
- "The browser does not apply timer rounding to `currentTime`" — [MDN currentTime](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime). But until Safari 27 (2026-09-14) Safari's value was coarse: that release "Fixed `HTMLMediaElement.currentTime` to report smoothly progressing values instead of updating only at fixed intervals", "Fixed `currentTime` on iOS to update more frequently during media playback" and fixed a stale `currentTime` after the playback rate changed from zero — [Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes).
- Safari 17.2 "Added unprefixed support for `preservesPitch`"; Safari 27 "Fixed an issue where `preservesPitch` and `playbackRate` were not correctly handled on an `HTMLMediaElement` connected to an `AudioContext` via `createMediaElementSource`", and fixed `HTMLMediaElement.volume` having no effect on an element connected to an AudioContext — [Safari 17.2 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-17_2-release-notes), [Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes).

**Libraries**
- Signalsmith Stretch: official Web Audio release "using WASM/AudioWorklet", MIT, v1.3.2 (2025-06-27), one 111 kB JavaScript file. It plays buffers the page adds (`addBuffers`, also incrementally) and is driven by `schedule({output, input, rate, semitones, loopStart, loopEnd, …})`, where `output` is an AudioContext time and `input` a position in the song; "the node compensates for its own latency"; `latency()` tells how far ahead to schedule; `configure({blockMs, intervalMs, splitComputation})` and a "cheaper" preset trade quality for CPU. The C++ README says time-stretching "sounds best for more modest changes (between 0.75x and 1.5x)" and that `splitComputation` spreads the work to avoid CPU spikes at the cost of one extra interval of latency — [npm signalsmith-stretch](https://www.npmjs.com/package/signalsmith-stretch), [signalsmith-stretch README](https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/README.md).
- SoundTouchJS: rewritten 2026 as `@soundtouchjs/*` (MPL-2.0, "moved off of the LGPL"; v2.1.1 of 2026-08-03; AudioWorklet processor 71 kB); the legacy `soundtouchjs` package stays LGPL-2.1. Its worklet README explains that SoundTouch's time-stretcher "operates on small 128-sample blocks in the AudioWorklet. At higher tempos, it can't produce enough output samples per block, causing audible gaps", so tempo is changed through the source's `playbackRate` while the node corrects pitch; it exposes underrun metrics; a separate phase-vocoder worklet targets "smoother extreme-ratio time-stretching" — [SoundTouchJS README](https://github.com/cutterbl/SoundTouchJS/blob/master/README.md), [npm @soundtouchjs/audio-worklet](https://www.npmjs.com/package/@soundtouchjs/audio-worklet), [npm soundtouchjs](https://www.npmjs.com/package/soundtouchjs).
- Rubber Band: GPL (v2 or later) or a paid commercial licence; the R3 ("Finer") engine "produces higher-quality results than R2 for most material … However, it uses much more CPU than the R2 engine" — [Rubber Band README](https://github.com/breakfastquay/rubberband/blob/master/README.md). `rubberband-wasm` 3.3.0 (GPLv2, 259 kB WASM, 2024-12-23) — [npm rubberband-wasm](https://www.npmjs.com/package/rubberband-wasm), [rubberband-wasm README](https://github.com/Daninet/rubberband-wasm/blob/master/README.md).
- Bungee: phase-vocoder C++ library, MPL-2.0, built for continuously changing speed including zero and negative; the npm wrapper `bungee-pitch-shift` (MIT, 2025-10, 64.5 kB WASM + 121 kB processor) states about 40 ms latency and Safari 14.1+ — [Bungee README](https://github.com/bungee-audio-stretch/bungee/blob/main/README.md), [Bungee LICENSE](https://github.com/bungee-audio-stretch/bungee/blob/main/LICENSE), [npm bungee-pitch-shift](https://www.npmjs.com/package/bungee-pitch-shift).
- Phaze is a real-time **pitch-shifter** AudioWorklet (phase vocoder), not a time-stretcher by itself; its README dates from January 2021 — [olvb/phaze README](https://github.com/olvb/phaze/blob/master/README.md).
- Tone.js `GrainPlayer` (MIT) uses granular synthesis to "adjust pitch and playback rate independently" — [Tone.js GrainPlayer.ts](https://github.com/Tonejs/Tone.js/blob/main/Tone/source/buffer/GrainPlayer.ts).
- Superpowered Web SDK: includes time stretching and pitch shifting and a "real-time (not rendered), low-latency time-stretching in the browser" demo; licence: "licensed separately on a case-by-case basis … Free license may be available at our sole discretion … may not launch publicly and/or without a license"; npm package 27 MB unpacked (v2.8.2, 2026-09-09) — [Superpowered web SDK README](https://github.com/superpoweredSDK/web-audio-javascript-webassembly-SDK-interactive-audio/blob/master/README.md), [npm @superpoweredsdk/web](https://www.npmjs.com/package/@superpoweredsdk/web).
- AudioWorklet (needed by all of these): Chrome 66, Firefox 76, Safari and iOS Safari 14.1 — [BCD AudioWorklet.json](https://github.com/mdn/browser-compat-data/blob/main/api/AudioWorklet.json). Older iOS versions had worklet defects: Safari 17.6 "Fixed multiple cases of audio distortion occurring when using AudioWorklets" — [Safari 17.6 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-17_6-release-notes); Safari 26.0 "Fixed stale audio buffer data after seeking when playing sound through an AudioContext" — [Safari 26 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes).

### Inferences
- Recommended architecture for own files: decode once, play through the Web Audio graph; at rate 1.0 use a plain `AudioBufferSourceNode` (no CPU cost, bit-exact), and switch to Signalsmith Stretch only when the user changes tempo. Song position is then a simple function of `AudioContext.currentTime`, and the metronome and voice are scheduled on the same clock (see the next section).
- The app's slow limit (-30%, i.e. 0.70×) lies just outside Signalsmith's stated sweet spot (0.75×-1.5×); +15% is inside. Expect some softening of transients at 0.70×; offering 0.75× as the lowest "good quality" step would stay inside the documented range.
- The built-in route is the low-effort fallback: on iOS it gets Apple's music-grade spectral algorithm; on Android Chrome it gets WSOLA with a 20 ms window, a time-domain method that is usually better on speech than on dense big-band textures at -30% (general signal-processing expectation, not a listening test).
- With the built-in route the song runs on the media element's clock and the app's sounds on the AudioContext clock; the app must continuously map `audio.currentTime` to audio-context time and re-fit when they drift, so R2 is "probably achievable" rather than guaranteed. On iPhones still running iOS 26 or older it is doubtful: `currentTime` there updates only at intervals (fixed in Safari 27), and routing the element through Web Audio broke pitch-preserved rate changes (also fixed in Safari 27). This is the strongest argument for the library route on iOS.

### Gaps
- No measured CPU load on phones for Signalsmith Stretch, Rubber Band, Bungee or SoundTouchJS, and no accessible listening-test comparison (Bungee's comparison page and Signalsmith's demo were unreachable). Needs a device test, especially on low-end Android.
- Firefox's built-in algorithm was not checked. Superpowered pricing unknown.

## Precise scheduling of the app's own sounds and the animation against the music (clocks, latency, calibration)

### Takeaway
Sound-to-sound sync is easy: schedule everything on the Web Audio clock (`AudioContext.currentTime`) a little ahead of time. The hard part is sound-to-screen: the animation must be driven by *what is being heard*, which needs `getOutputTimestamp()` and `outputLatency` — supported in all three engines now (Safari got `outputLatency` only in 18.4, March 2025) but of uncertain accuracy with Bluetooth. Every rhythm game therefore also gives the user a manual offset; this app needs one too.

### Cited Findings
- Timer callbacks "can easily be skewed by tens of milliseconds or more by layout, rendering, garbage collection"; the standard pattern is a timer that wakes every 25 ms and schedules Web Audio events for the next 100 ms, and visuals should read the audio clock rather than their own timestamps — [web.dev: A tale of two clocks](https://web.dev/articles/audio-scheduling).
- `outputLatency` is "the interval between the time the UA requests the host system to play a buffer and the time at which the first sample in the buffer is actually processed by the audio output device"; it "depends on the platform and the connected audio output device", may change while running, and should be queried "frequently when accurate synchronization is required". `baseLatency` is the context's own buffering (example: 2 × 128 frames at 44.1 kHz ≈ 5.8 ms). The difference between `currentTime` and `getOutputTimestamp().contextTime` "cannot be considered as a reliable output latency estimation" — [Web Audio API spec source](https://github.com/WebAudio/web-audio-api/blob/main/index.bs).
- Support: `getOutputTimestamp()` Chrome 57, Firefox 70, Safari 14.1; `outputLatency` Chrome 102 (2022-05-24), Firefox 70, Safari and iOS Safari 18.4 (2025-03-31); `baseLatency` Chrome 58, Firefox 70, Safari 14.1; `latencyHint` option Chrome 58, Safari 14.1, not Firefox — [BCD AudioContext.json](https://github.com/mdn/browser-compat-data/blob/main/api/AudioContext.json).
- `outputLatency` "provides an estimate of audio hardware's output latency (for example, that of Bluetooth earbuds or of an external USB audio interface)" and is meant for synchronising Web Audio output with other media — [web.dev: Synchronize audio and video playback on the web](https://web.dev/articles/audio-output-latency).
- Chrome reports `outputLatency` quantised to 8 ms unless the page holds microphone permission, in which case it has 1 ms precision — [Chromium audio_context.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/modules/webaudio/audio_context.cc).
- Typical device latency (older notes by a Firefox audio engineer): about 10 ms on Windows, "very very low on OSX and iOS (a few milliseconds)", 30-40 ms on Linux/PulseAudio, and on Android "between 12.5ms on a Galaxy Nexus … up to 150ms on some very cheap devices" — [Web Audio API performance and debugging notes](https://padenot.github.io/web-audio-perf/).
- Bluetooth: music uses the A2DP profile; "in most cases, Android itself has a latency between 30-100 ms. Most of the latency comes from buffering on various headsets"; the call profile (SCO) "has worse audio quality but lower latency" — [Oboe wiki: Bluetooth Audio](https://github.com/google/oboe/wiki/TechNote_BluetoothAudio). Touch-screen input adds "around 15-30 msec" — [OboeTester usage notes](https://github.com/google/oboe/blob/main/apps/OboeTester/docs/Usage.md).
- Reported Safari problems **(search summaries, old reports, current status unknown)**: with a Bluetooth speaker the AudioContext clock advanced 1.09 s per real second in Safari 15 while `getOutputTimestamp().performanceTime` stayed correct — [WebKit bug 232728](https://bugs.webkit.org/show_bug.cgi?id=232728); after iOS 15.1 `getOutputTimestamp()` returned implausible `contextTime` values — [Apple Developer Forums thread 696356](https://developer.apple.com/forums/thread/696356).
- On iOS, WebKit asks for a hardware buffer of one render quantum (128 frames) when Web Audio is active and for about 20 ms chunks when capturing — [WebKit MediaSessionManagerCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/cocoa/MediaSessionManagerCocoa.mm). WebKit's iOS output-latency figure is the system audio session's `outputLatency` — [WebKit AudioSessionIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/ios/AudioSessionIOS.mm) — which Apple describes as "the latency for audio output, in seconds", warning that "using an AirPlay-enabled device for your audio content can result in a 2-second delay" — [Apple AVAudioSession.outputLatency](https://developer.apple.com/documentation/avfaudio/avaudiosession/outputlatency).
- How a rhythm game with user-supplied songs handles calibration: a global "universal offset" for the player's device plus a per-song "local offset" adjustable during play in 5 ms or 1 ms steps, an "Offset Wizard" to find the global value, and a test mode that reports e.g. "Mistimed Hits: 69% (ave 25ms late)" so the offset can be corrected by that amount; under 3-5 ms is treated as negligible — [osu! wiki: Universal offset](https://github.com/ppy/osu-wiki/blob/master/wiki/Offset/Universal_offset/en.md), [Local offset](https://github.com/ppy/osu-wiki/blob/master/wiki/Offset/Local_offset/en.md), [How to time songs](https://github.com/ppy/osu-wiki/blob/master/wiki/Guides/How_to_time_songs/en.md).
- Keeping the screen awake while practising (Screen Wake Lock): Chrome 84, Firefox 126, Safari 16.4; on iOS it did not work in Home Screen web apps until 18.4 — [BCD Navigator.json](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json).

### Inferences
- With the song inside the Web Audio graph, the relative timing of song, metronome and voice is sample-accurate by construction; only the screen needs compensation: heard position = position scheduled for `getOutputTimestamp().contextTime` (or `currentTime − outputLatency`), minus a user offset. A 60 Hz display adds up to ±8 ms, Chrome's 8 ms quantisation another few, so 30-50 ms is realistic on the phone speaker or wired headphones.
- Bluetooth is the open risk: latency is typically much larger than the wired case and the app depends on how truthfully the system reports it. Because beats repeat, a constant error of one whole beat is invisible, but an error of 100-200 ms at 160 BPM (beat = 375 ms) puts the feet visibly off. Hence: show the reported latency, offer a ±300 ms slider, and offer a "tap along" or "does the flash match the click?" calibration; store the offset per output device where possible.
- Tapping calibrations inherit touch latency (15-30 ms) and human anticipation, so a visual-versus-click comparison adjusted by the user is the safer calibration for an animation.
- The spoken step names and metronome samples should be decoded into AudioBuffers and started with `start(when)`; speech synthesis or `<audio>` elements cannot be scheduled to the sample (and on iOS an audible media element changes the audio-session category — see the microphone section).

### Gaps
- No current measurements of `outputLatency` accuracy on iOS 27 or Android with Bluetooth; no typical Bluetooth figures from a primary source (commonly quoted 150-300 ms for A2DP is from memory, unverified). The WebKit Bluetooth clock bug's status is unknown.
- How precisely `HTMLMediaElement.currentTime` tracks audible output was found only for Safari (coarse before version 27; see the time-stretching section); nothing for Chrome or Firefox.

## Microphone follow-along (the music plays elsewhere; the browser listens)

### Takeaway
Listening through the microphone works technically in all browsers, but two facts limit it. First, on an iPhone the same device almost certainly cannot play music in another app while Safari records: WebKit's source switches the audio session to "play and record" without the mixing option, and Apple documents that such a session interrupts other apps' audio — so iOS needs a second device or speaker (to be confirmed on a device). On Android, Chromium's source shows Chrome avoids putting the phone into call mode only if all microphone processing is switched off. Second, real-time beat tracking is much weaker than offline tracking (about 75-80% beat F-measure and about 46% for downbeats on clean audio), and no ready-made browser port of a real-time beat-phase tracker was found. The stronger variant is "recognise the song and its position by fingerprint, then use the prepared grid".

### Cited Findings
**Browser APIs, constraints, permissions**
- `getUserMedia()` works only in secure contexts (HTTPS or localhost) and always requires user permission; browsers "must ask at least the first time" — [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia); supported in Chrome 53, Firefox 36, Safari and iOS Safari 11 — [BCD MediaDevices.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json).
- Constraints: `echoCancellation` Chrome 59, Firefox 50, Safari 11; `noiseSuppression` and `autoGainControl` Chrome 67, Firefox 55, **not supported in Safari**; `channelCount` and `latency` constraints not in Safari — [BCD MediaStreamTrack.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaStreamTrack.json). `echoCancellation: false` means "no audio is removed" — [MDN echoCancellation](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation).
- Feeding the microphone into analysis: `AudioContext.createMediaStreamSource()` Chrome 22, Firefox 25, Safari 11 — [BCD AudioContext.json](https://github.com/mdn/browser-compat-data/blob/main/api/AudioContext.json).

**iOS Safari: audio-session behaviour**
- WebKit chooses the iOS audio-session category from what the page does: any active audio capture → `PlayAndRecord` (mode VideoChat); else an audible `<audio>`/`<video>` element → `MediaPlayback`; else Web Audio only → `AmbientSound` — [WebKit MediaSessionManagerCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/cocoa/MediaSessionManagerCocoa.mm). For `PlayAndRecord` it sets the options AllowBluetooth, AllowBluetoothA2DP, AllowAirPlay and usually DefaultToSpeaker — not MixWithOthers — [WebKit AudioSessionIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/ios/AudioSessionIOS.mm).
- Apple: with `playAndRecord` (and with `playback`) "your app's audio is nonmixable—activating your session will interrupt any other audio sessions which are also nonmixable" unless `mixWithOthers` is set; `ambient` is "appropriate for 'play-along' apps, such as a virtual piano that a user plays while the Music app is playing … audio from other apps mixes with your audio. Screen locking and the Silent switch … silence your audio" — [Apple: playAndRecord](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord), [Apple: ambient](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient), [Apple: playback](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playback), [Apple: mixWithOthers](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/mixwithothers).
- Apple's category table (archived guide, updated 2017): Ambient — silenced by the Ring/Silent switch and screen locking: yes; interrupts non-mixable apps' audio: no; output only. Playback — not silenced; interrupts non-mixable audio "Yes by default; no by using override switch". PlayAndRecord — not silenced; interrupts "Yes by default; no by using override switch"; input and output. The same guide says recording and playback apps "typically interrupt other system audio when their audio sessions are activated", while games should use the ambient categories because users "often … want the audio from another app to continue playing" — [Apple Audio Session Programming Guide: categories and modes](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/AudioSessionCategoriesandModes/AudioSessionCategoriesandModes.html), [Apple: audio guidelines by app type](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/AudioGuidelinesByAppType/AudioGuidelinesByAppType.html).
- The Audio Session API (`navigator.audioSession.type`: auto, playback, transient, transient-solo, ambient, play-and-record) exists in Safari and iOS Safari 16.4+, not in Chrome, and in Firefox only as a preview — [BCD AudioSession.json](https://github.com/mdn/browser-compat-data/blob/main/api/AudioSession.json). In "auto" mode an AudioContext defaults to "ambient", a media element to "playback", a microphone track to "play-and-record", and the highest-priority active type wins — [MDN Audio Session API](https://developer.mozilla.org/en-US/docs/Web/API/Audio_Session_API). The specification says a microphone track is ended if the session type is anything other than play-and-record or auto, and classes playback, play-and-record and transient-solo as "exclusive" types — [Audio Session spec source](https://github.com/w3c/audio-session/blob/main/index.bs). In WebKit the page-set type overrides the automatic category — [WebKit DOMAudioSession.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/audiosession/DOMAudioSession.cpp).
- Apple's release notes show this area is still being repaired: Safari 16.4 "Added support for a subset of the AudioSession Web API"; Safari 16.5 "Fixed non-audible AudioContext preventing the audio session to change from play-and-record after stopping capture"; Safari 26.4 (macOS) fixed `getUserMedia` "with echo cancellation disabled" unintentionally affecting existing audio tracks; Safari 27 "Fixed the WebProcess `AudioSession` to remain active while microphone capture is live"; Safari 27.2 (2026-10-26) "Fixed an issue where `getUserMedia()` requests for audio permanently failed with `NotAllowedError` after the system audio service was reset" — [Safari 16.4](https://developer.apple.com/documentation/safari-release-notes/safari-16_4-release-notes), [Safari 16.5](https://developer.apple.com/documentation/safari-release-notes/safari-16_5-release-notes), [Safari 26.4](https://developer.apple.com/documentation/safari-release-notes/safari-26_4-release-notes), [Safari 27](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes), [Safari 27.2](https://developer.apple.com/documentation/safari-release-notes/safari-27_2-release-notes) release notes.
- Field reports **(search summaries of several WebKit Bugzilla reports and Apple forum threads; the pages were not opened, so which report says what is uncertain)**: Safari's microphone capture stops transmitting when Safari is no longer visible; after another app used the microphone, capture in Safari could stay broken until the tab was reopened or the page reloaded; opening the audio input caused other audio (even music playing in another browser) to pause or stall briefly, and to duck — candidate reports: [WebKit bug 215965 "getUserMedia causes stall in audio output / unexpected audio ducking"](https://bugs.webkit.org/show_bug.cgi?id=215965), [WebKit bug 204681](https://bugs.webkit.org/show_bug.cgi?id=204681), [WebKit bug 226620](https://bugs.webkit.org/show_bug.cgi?id=226620), [Apple Developer Forums: "iOS 26.1 beta Safari audio input is broken"](https://developer.apple.com/forums/thread/802555).

**Android Chrome: audio mode and audio focus**
- "By default, the audio manager for Android creates streams intended for real-time VoIP sessions and therefore sets the audio mode to MODE_IN_COMMUNICATION. However, the user might have asked for a special mode where all audio input processing is disabled, and if that is the case we avoid changing the mode" (the switch happens only if the capture parameters carry effects); while communication mode is on, Chrome's own output streams use the voice-communication usage instead of media — [Chromium audio_manager_android.cc](https://github.com/chromium/chromium/blob/main/media/audio/android/audio_manager_android.cc), [AudioManagerAndroid.java](https://github.com/chromium/chromium/blob/main/media/base/android/java/src/org/chromium/media/AudioManagerAndroid.java).
- Chrome requests Android audio focus for media-session players: `AUDIOFOCUS_GAIN` for "persistent" players and `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` for "transient" ones; a player is transient if its duration is known and at most 5 seconds; persistent audio "should pause all other playbacks", transient audio plays on top while others duck — [AudioFocusDelegate.java](https://github.com/chromium/chromium/blob/main/content/public/android/java/src/org/chromium/content/browser/AudioFocusDelegate.java), [media_content_type.cc](https://github.com/chromium/chromium/blob/main/media/base/media_content_type.cc), [media_session_impl.cc](https://github.com/chromium/chromium/blob/main/content/browser/media/session/media_session_impl.cc), [Chromium audio focus notes](https://github.com/chromium/chromium/blob/main/docs/media/audio_focus.md).
- The browser-side manager for Web Audio contexts only records audible time and notifies the frame; it contains no media-session or audio-focus request — [audio_context_manager_impl.cc](https://github.com/chromium/chromium/blob/main/content/browser/media/webaudio/audio_context_manager_impl.cc).

**Real-time (causal) beat trackers and their accuracy**
- BeatNet (CRNN + particle filter) has a microphone "streaming mode"; its authors advise feeding "as loud input as possible … given all models are trained on the datasets containing mastered songs" — [BeatNet README](https://github.com/mjhydri/BeatNet/blob/main/README.md).
- Online results on GTZAN reported in a follow-up paper's comparison table **(search summary)**: beat F-measure BeatNet 75.44, Böck FF 74.18, Böck ACF 64.63, aubio 57.09; BeatNet downbeat F-measure 46.49; BeatNet needed 8.87 s of computation per 30 s excerpt with 1,000-1,750 particles; another listing gives BeatNet 80.64 for beats under a different setup — [arXiv 2111.00704 (1D state space)](https://arxiv.org/abs/2111.00704), [arXiv 2108.03576 (BeatNet)](https://arxiv.org/abs/2108.03576). The follow-up "jump-reward" tracker is CC BY 4.0 Python on top of BeatNet's network — [1D-StateSpace README](https://github.com/mjhydri/1D-StateSpace/blob/main/README.md).
- BTrack: "a causal beat tracking algorithm intended for real-time use", C++ with Python and Vamp wrappers, default hop 512 and frame 1024 samples, exposes "beat due in current frame"; licence GPL v3 — [BTrack README](https://github.com/adamstark/BTrack/blob/master/README.md). An npm registry search on 2026-11-17 for "btrack" returned no port — [npm search](https://www.npmjs.com/search?q=btrack).
- "A Real-Time Beat Tracking System with Zero Latency and Enhanced Controllability" (predominant local pulse; TISMIR 2024) has a single-file Python implementation that captures the microphone — [groupmm/real_time_plp README](https://github.com/groupmm/real_time_plp/blob/main/README.md).
- In the browser today: `aubiojs` exposes aubio's `Tempo` object — [npm aubiojs](https://www.npmjs.com/package/aubiojs); `realtime-bpm-analyzer` gives a live BPM reading (not beat positions) from the microphone — [npm realtime-bpm-analyzer](https://www.npmjs.com/package/realtime-bpm-analyzer); `@uln/impulse` (MIT, WASM, 2026-01) extracts "BPM, beats, frequency bands" from streams — [npm @uln/impulse](https://www.npmjs.com/package/@uln/impulse); `beat-tracker` (MIT, pure JavaScript, 2025-12) — [npm beat-tracker](https://www.npmjs.com/package/beat-tracker). Essentia's main beat extractor is not real-time (see the beat-tracking section).

**Recognise-and-sync by fingerprint (instead of tracking beats)**
- Olaf's browser module matches microphone input inside an AudioWorklet, and its optional live page "recognize[s] microphone audio continuously and automatically play[s] the reference in sync": it sends rolling windows of up to 15 s every 2.5 s, gives priority to the newest five seconds, uses "capture frame timestamps and a shared AudioContext clock [to] compensate for request and decoding delays", fades out after ten seconds without confirmation, and notes that "headphones avoid feeding the reference playback back into the microphone" — [Olaf README](https://github.com/JorenSix/Olaf/blob/master/README.md).

### Inferences
- iPhone, same device: starting capture makes Safari's session `PlayAndRecord` without mixing, so the music app is interrupted; if the user restarts the music, the music app's own non-mixable session interrupts Safari's capture. Conclusion: microphone follow-along on an iPhone only works when the music comes from *another* device (speaker, laptop, second phone). This follows from the source and Apple's documentation but should be confirmed on a device.
- iPhone, no microphone: an app that plays its sounds only through Web Audio gets the "ambient" category, which mixes on top of Spotify or Apple Music playing in the background — exactly what tap-tempo mode needs. Caveats from the same sources: ambient audio is muted by the Ring/Silent switch and by screen lock; any audible `<audio>` element (for example a voice clip played that way) flips the page to "playback" and pauses the other app. In own-files mode the reverse is wanted: set `navigator.audioSession.type = "playback"` so the Silent switch does not mute the song.
- Android, same device: request the microphone with `echoCancellation`, `noiseSuppression` and `autoGainControl` all `false`. Per Chromium's source this keeps the system out of communication mode, so the other app keeps playing as normal media; the unprocessed signal is also what a beat tracker or fingerprinter needs. With default constraints the phone enters call mode (call volume, altered routing, Bluetooth switching to the low-quality call profile), which degrades the music. The app's own sounds should come from Web Audio; long `<audio>` clips would take audio focus and pause the music, clips of 5 s or less would duck it.
- Acoustic reality: the microphone only hears music played through a speaker. Users with headphones cannot use this mode at all, and with a speaker the app's own metronome and voice leak back into the microphone (no echo cancellation), which disturbs a beat tracker more than a fingerprint matcher.
- Latency budget for a tracker: input buffering (about 20 ms chunks on iOS per WebKit; unknown on Android), sound travel (about 3 ms per metre), analysis hop (about 12-20 ms), plus output latency for the app's own sounds. Trackers that predict the next beat can cancel a constant delay, but the constant must be calibrated.
- Beat tracking alone cannot deliver R3: with online downbeat F-measure around 46% on clean recordings, "beat 1" and the 8-count need a tap from the user anyway. Fingerprint position-sync against the curated list delivers the whole prepared grid (beat 1, 8-counts, tempo drift) but only for curated songs, with about 100 ms raw precision that needs cross-correlation refinement, and with Olaf's AGPL and patent caveats.

### Gaps
- No measurements of time-to-lock, or of accuracy through a phone speaker, room noise and a phone microphone, for any tracker; no evaluation of real-time trackers on swing. No ready-made browser port of BeatNet or BTrack was found (npm search only; GitHub search was not available).
- Microphone input latency in iOS Safari and Android Chrome was not found. Whether Chrome on Android requests audio focus for Web Audio output was not exhaustively verified (only the files cited were read).
- A search summary mentioned a 2026 WebKit report that page audio crackles on iOS 27 while a microphone stream with echo cancellation is open; I could not open the bug to confirm number or status.

## Tab or system audio capture (`getDisplayMedia` with audio)

### Takeaway
Only Chromium desktop browsers deliver audio from screen sharing: tab audio on all desktop systems, whole-system audio on Windows, ChromeOS and (per current Chromium source) macOS 14.2+. Firefox and Safari return video only, and no phone browser supports it. It is therefore a desktop-only extra — but where it works it gives a clean digital signal, so the "recognise and align" method would be at its most precise.

### Cited Findings
- `getDisplayMedia()`: Chrome 72, Firefox 66, Safari 13; **not** in Chrome for Android or Firefox for Android; BCD lists iOS Safari from version 27 (2026-09-14) — [BCD MediaDevices.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json). Apple's Safari 27 release notes do not announce it for iOS (they mention `getDisplayMedia()` only in a quality fix), so the iOS entry is unconfirmed; in any case BCD lists no audio capture for Safari — [Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes).
- Audio capture through it: Chrome 74+ only ("On Windows and ChromeOS, the entire system audio can be captured when sharing an entire screen. On Linux and macOS, only the audio of a tab can be captured"); Firefox no; Safari no; Chrome Android no — [BCD MediaDevices.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json).
- Newer than that BCD note: Chromium's source reports system loopback capture as supported on Windows, ChromeOS, and macOS when the CoreAudio tap is available (macOS 14.2 or later) or via ScreenCaptureKit below macOS 15; per-application audio capture is enabled by default on Windows 11 and macOS 14.2+; on Linux a PulseAudio loopback for screen sharing exists but its feature flag is disabled by default — [Chromium media_switches.cc](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc). A developer blog dates macOS system-audio sharing to Chrome 141 on macOS 14.2+ **(search summary)** — [Pipe blog](https://blog.addpipe.com/getdisplaymedia-allows-capturing-the-screen-with-system-sounds-on-chrome-on-macos).
- Options: `systemAudio` (Chrome 105), `windowAudio` (Chrome 141, partial), `suppressLocalAudioPlayback` (Chrome 109; whether the captured tab keeps playing through the speakers), `restrictOwnAudio` (Chrome 141; filters the capturing tab's own sound out of a system capture) — all Chromium-only and experimental — [BCD MediaDevices.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json), [BCD MediaStreamTrack.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaStreamTrack.json), [MDN MediaTrackConstraints](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints).
- "Capturing audio is always optional, and even when web content requests a stream with both audio and video, the returned MediaStream may still have only one video track, with no audio" — [MDN Using the Screen Capture API](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Capture_API/Using_Screen_Capture). The call needs transient user activation, and "the go-ahead permission to use getDisplayMedia() cannot be persisted for reuse. The user must be prompted for permission every time" — [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia).
- Firefox's audio-sharing tracking bug is still open, and a 2026 explainer states Firefox and Safari implement the video part but ignore the audio request, and that mobile browsers have no audio capture **(search summaries)** — [Mozilla bug 1541425](https://bugzilla.mozilla.org/show_bug.cgi?id=1541425), [tab audio sharing explained](https://livesuggest-web.pages.dev/blog/tab-audio-sharing-explained/). An April 2026 standards-list message notes `getDisplayMedia` cannot capture system audio on its own, without a display surface **(search summary)** — [public-webrtc archive](https://lists.w3.org/Archives/Public/public-webrtc/2026Apr/0028.html).

### Inferences
- Flow on desktop Chrome/Edge: the user clicks "follow a tab", picks the tab playing the music (a web player) and ticks "share tab audio"; the page analyses the audio track with the same fingerprint-and-correlate code as the own-files matcher. No acoustic path, no room noise, no leakage of the app's own sounds (they are in a different tab), and the capturing page can keep `suppressLocalAudioPlayback` off so the music stays audible.
- The price is a screen-sharing prompt on every session, a "sharing" indicator, and zero coverage on phones — the app's main target. It is worth building only after the matching code exists for other modes.

### Gaps
- Whether DRM-protected web players' audio (Encrypted Media Extensions, e.g. Widevine) is delivered or silenced in tab or system capture was not confirmed from any source. Hints only: Chromium's audio renderer treats encrypted streams in the same rendering path (it merely uses a larger buffer for them) — [audio_renderer_impl.cc](https://github.com/chromium/chromium/blob/main/media/renderers/audio_renderer_impl.cc), [audio_renderer_algorithm.cc](https://github.com/chromium/chromium/blob/main/media/filters/audio_renderer_algorithm.cc) — and the loopback code that feeds tab-audio capture contains no reference to encryption or DRM — [loopback_stream.cc](https://github.com/chromium/chromium/blob/main/services/audio/loopback_stream.cc). That suggests decrypted audio reaches the captured output, but it is a reading of a few files, not a test, and says nothing about what a service's terms allow.
- Legal status: no legal source was retrieved. Open questions for a legal check: whether transient in-memory analysis of the user's own playback (nothing stored, nothing transmitted) counts as a "recording" or "copy" under copyright law in the relevant countries, and whether streaming services' terms of use prohibit capturing their output regardless of copyright law.
- Capture latency (delay between playback and captured samples) was not found.

## Tap-tempo and manual sync

### Takeaway
Tapping is the one follow-along method that works on every device, with headphones, with any player and without permissions; on iPhone the app's sounds can mix over the other app's music. Its limits are precision and drift: a tempo tapped over 8-16 beats is good for only a few seconds, and live swing recordings drift, so the interface must make continuous correction cheap ("tap on 1" to re-anchor, nudge buttons), exactly as DJ software and rhythm-game editors do.

### Cited Findings
- DJ software (Mixxx): tap tempo uses a moving interquartile mean over up to 80 tap intervals, resets when a gap exceeds 2 s (30 BPM), needs at least 4 taps before it reports, and rounds within 1/12 BPM — [Mixxx tapfilter.cpp](https://github.com/mixxxdj/mixxx/blob/main/src/util/tapfilter.cpp), [Mixxx bpmcontrol.cpp](https://github.com/mixxxdj/mixxx/blob/main/src/engine/controls/bpmcontrol.cpp).
- Mixxx's manual controls after detection: the user can "tap with the beat to set the BPM", "stretch, compress or shift the beatgrid in case it was not detected correctly", press a beat-grid adjust button that "adjusts the track beat-grid so that the current position is marked as a beat" (for when the tempo is right but the beat markers are misaligned), and "nudge" playback temporarily faster or slower like touching a turntable — [Mixxx manual: user interface](https://github.com/mixxxdj/manual/blob/main/source/chapters/user_interface.rst).
- Rhythm-game editor (osu!): tap along for "half a minute … a minute at maximum" to get an approximate BPM and offset; then set the offset with arrows in 1, 2 or 10 ms steps, listening at reduced speed; then check the BPM "somewhere near the end of the track, where the difference between the song tempo and metronome is accumulated and easily audible"; songs with "concerts, live performances, songs with audible acceleration/deceleration" need several timing sections, each with its own BPM and offset — [osu! wiki: How to time songs](https://github.com/ppy/osu-wiki/blob/master/wiki/Guides/How_to_time_songs/en.md), [osu! wiki: Timing tab](https://github.com/ppy/osu-wiki/blob/master/wiki/Client/Beatmap_editor/Timing/en.md).
- Touch-screen latency is "around 15-30 msec" — [OboeTester usage notes](https://github.com/google/oboe/blob/main/apps/OboeTester/docs/Usage.md).
- On iOS the "ambient" audio category is the one meant for playing along with the Music app, and an AudioContext gets it by default — [Apple: ambient](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient), [MDN Audio Session API](https://developer.mozilla.org/en-US/docs/Web/API/Audio_Session_API).

### Inferences
- Convergence (least-squares line through N tap times, assuming independent tap errors of 25 ms standard deviation — an assumed value): the tempo error is 25 ms × √(12 / (N(N²−1))) per beat, i.e. 3.9 ms/beat for 8 taps, 1.4 ms/beat for 16, 0.48 ms/beat for 32, 0.17 ms/beat for 64. At 160 BPM the prediction is 50 ms off after about 5 s (8 taps), 14 s (16 taps), 39 s (32 taps), 111 s (64 taps). The phase at the middle of the tapping window is known to 25/√N ms (6 ms for 16 taps). So tapping alone cannot hold 30-50 ms for a three-minute song even if the band's tempo were perfectly steady — and it is not.
- Practical design that follows: (1) "tap on every beat" for the first 8 counts sets tempo and phase, with the first tap of the gesture defining "1"; (2) while dancing, a single large "1" button re-anchors the phase and feeds a slow tempo correction (a phase-locked loop), so one tap every phrase or two keeps the animation locked through drift; (3) "earlier / later" nudge buttons in about 10-20 ms steps and "half / double" tempo buttons; (4) subtract a calibrated constant for touch latency and human anticipation; (5) show a pulsing beat indicator so the user can see the error before fixing it.
- Tap mode gives no R1 and no R4 (the other app controls playback and speed), R2 only to roughly ±30-80 ms right after a tap and worsening between taps, R3 only as far as the user taps it, R5 fully.
- A hybrid is attractive: the tap supplies bar phase ("1") and a tempo prior, and — where a microphone is permitted and can hear the music — a light beat tracker supplies the continuous fine correction that human tapping cannot.

### Gaps
- No primary source retrieved on human tapping accuracy (from memory: the sensorimotor-synchronisation literature reports taps typically preceding the beat by some tens of milliseconds and tap-to-tap variability of a few percent of the beat interval; verify before citing). The 25 ms figure above is an assumption.
- Tap interfaces of metronome and dance apps (Soundbrenner, Pro Metronome, DJ apps such as djay, rekordbox, Traktor) could not be opened; only Mixxx and osu! are documented here.

## Recognising which song is playing so a prepared beat grid can be loaded

### Takeaway
A web page cannot ask the system what another app is playing; it has to hear the music (microphone or captured tab audio) and fingerprint it. Apple's ShazamKit does this with exactly the right outputs (position in the reference and speed difference) but only in native iOS/macOS and Android apps. For a curated list, an in-browser fingerprint index (Olaf compiles to a 75 kB WASM module) can do the job without any paid service; commercial web recognition services exist but their prices and terms could not be checked.

### Cited Findings
- ShazamKit is a framework for iOS 15+, iPadOS, macOS 12+, tvOS, watchOS and visionOS, with a separate Android library (an AAR file); Apple's documentation lists no web or JavaScript version — [Apple ShazamKit](https://developer.apple.com/documentation/shazamkit), [ShazamKit for Android](https://developer.apple.com/shazamkit/android/).
- A ShazamKit match includes "the timecode in the reference recording that matches the start of the query" (`matchOffset`), "the updated timecode in the reference recording that matches the current playback position of the query audio" (`predictedCurrentMatchOffset`) and `frequencySkew` (0.05 means the query plays 5% higher/faster; "no match returns if the frequency skew is too large") — [matchOffset](https://developer.apple.com/documentation/shazamkit/shmatchedmediaitem/matchoffset), [predictedCurrentMatchOffset](https://developer.apple.com/documentation/shazamkit/shmatchedmediaitem/predictedcurrentmatchoffset), [frequencySkew](https://developer.apple.com/documentation/shazamkit/shmatchedmediaitem/frequencyskew).
- ShazamKit supports custom catalogs of the developer's own reference signatures; a signature "is much smaller than the original audio" and "it's not possible to convert the signature back to the recording"; Apple's own example is an app that follows a teaching video by the matched timecode, including when the student skips forward or back — [Apple ShazamKit](https://developer.apple.com/documentation/shazamkit), [SHCustomCatalog](https://developer.apple.com/documentation/shazamkit/shcustomcatalog).
- Open-source equivalent that runs in a web page: Olaf (details and caveats in the matching and microphone sections) — [Olaf README](https://github.com/JorenSix/Olaf/blob/master/README.md).
- Chromaprint's stated target use cases are "full audio file identification, duplicate audio file detection and long audio stream monitoring" (so, on my reading, not short noisy microphone excerpts) — [rusty-chromaprint README](https://github.com/darksv/rusty-chromaprint/blob/main/README.md).
- AudD (commercial service): the official TypeScript/Node.js SDK (`@audd/sdk`, MIT, v1.5.15 of 2026-10-13) identifies music "from a short audio clip, a long audio file, or a live stream"; it needs an API token from the vendor's dashboard; a result carries artist, title and a `timecode`; the long-file endpoint returns where each song plays in the submitted file plus raw millisecond offsets within "AudD's internal 12-second scan fragment", with some fields reserved for "a Startup plan or higher"; for browsers it offers only a token-less long-poll consumer for which "your server derives the category and ships it to the browser" — [npm @audd/sdk](https://www.npmjs.com/package/@audd/sdk).
- ACRCloud (commercial service): an unofficial 2019 Node module shows the access model — sign up "for a free trial", create a recognition project, and receive a `host`, `access_key` and `access_secret`; the API accepts a raw audio file or an audio fingerprint as the request body — [npm acrcloud](https://www.npmjs.com/package/acrcloud).
- The Media Session API lets a page provide "metadata for display by the user agent for the media **your web app** is playing" and receive media-key actions; it offers nothing for reading other apps' sessions — [MDN Media Session API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API).

### Inferences
- For a curated list, recognition and position-finding are the same operation (a fingerprint match returns both), so a general "what song is this?" service adds little: a song outside the curated list has no prepared grid anyway.
- The fingerprints of the curated recordings are derived data, not audio, and (as Apple notes for its own signatures) cannot be turned back into the recording — which is what makes shipping them with a free app plausible. Whether that is legally clean in every country was not researched.
- If the developer ever wraps the web app as a native app, ShazamKit custom catalogs would give recognition, position and speed skew on both iOS and Android without the AGPL question.

### Gaps
- ACRCloud, AudD and similar services: current prices, free allowances and terms of use could not be opened (vendor sites unreachable; search budget exhausted), and I found no official ACRCloud browser SDK in the npm registry (the listed packages are an unofficial Node module and a Cordova plugin). From memory, unverified: both services charge per request beyond a small free allowance. Both access models above need a secret token, which a static, server-less web app cannot keep private.
- Not verified: other indirect ways to learn what is playing (for example a scrobbling service's "now playing" API, or a streaming service's own "currently playing" web API) — these belong to the streaming-service part of the research.

## Real products and projects that work this way, and what they show

### Takeaway
Only open-source or documented examples could be checked: they show that (1) rhythm games with user-supplied songs rely on human-made timing plus per-device and per-song offsets, (2) DJ software pairs automatic analysis with tap, shift and stretch controls for the beat grid, and (3) recognise-and-sync from the microphone and neural beat tracking in the browser both already exist as working demos. The commercial practice tools named in the brief could not be researched from this session.

### Cited Findings
- osu! (rhythm game, songs supplied by the community): timing is made by people — tap for an approximate BPM and offset, refine in 1-10 ms steps, add timing sections where the tempo changes; players then apply a universal offset for their device and a local offset per song — [osu! wiki: How to time songs](https://github.com/ppy/osu-wiki/blob/master/wiki/Guides/How_to_time_songs/en.md), [Offset](https://github.com/ppy/osu-wiki/blob/master/wiki/Offset/en.md), [Universal offset](https://github.com/ppy/osu-wiki/blob/master/wiki/Offset/Universal_offset/en.md).
- Mixxx (DJ software, the user's own files): automatic BPM and beat-grid detection with visible controls to shift, stretch or re-anchor the grid, tap tempo, and nudge — [Mixxx manual: user interface](https://github.com/mixxxdj/manual/blob/main/source/chapters/user_interface.rst).
- Olaf's live page: continuous microphone recognition with the reference played in sync (rolling 15 s windows every 2.5 s) — [Olaf README](https://github.com/JorenSix/Olaf/blob/master/README.md).
- In-browser analysis on the user's own files with nothing uploaded: a "Key and BPM finder" built on `@audio/beat` — [npm @audio/beat](https://www.npmjs.com/package/@audio/beat); a Hugging Face Space using Beat This! through onnxruntime-web **(search summary)** — [Loop Maestro](https://huggingface.co/spaces/jorisvaneyghen/loop_maestro).
- In-browser real-time time-stretching demos: Superpowered's — [Superpowered web SDK README](https://github.com/superpoweredSDK/web-audio-javascript-webassembly-SDK-interactive-audio/blob/master/README.md); Signalsmith's "interactive web demo" — [signalsmith-stretch README](https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/README.md).
- Apple's ShazamKit documentation includes a sample named "ShazamKit Dance Finder with Managed Session" and describes syncing an app to media by matched timecode (native only) — [Apple ShazamKit](https://developer.apple.com/documentation/shazamkit).

### Inferences
- The mature products' pattern is consistent: automatic analysis is treated as a first draft, and the product's quality lies in fast correction tools (tap, shift, stretch, per-song offset) and a device-latency calibration. A dance-practice app with a curated list can do better than these because its grids are hand-checked once by the developer.
- None of the checked examples follows *another app's* playback on a phone; the working follow-along examples either hear the room (Olaf) or own the audio (osu!, Mixxx).

### Gaps
- Not researched (sites and app stores unreachable): Moises, Anytune, Amazing Slow Downer, Transcribe!, Soundbrenner, web DJ apps, and commercial rhythm games with custom songs. From memory, unverified: the slow-down practice apps work on DRM-free files the user owns (subscription downloads are DRM-protected and unavailable to them); Moises uploads the file to a server for stem separation, chord and beat detection; metronome apps offer tap tempo and, in some cases, microphone BPM detection. Verify before use.

## Ranked assessment: which approaches are realistic for this app

### Takeaway
Realistic, in order: (1) **own files played inside the Web Audio graph**, with the beat grid obtained by matching the file to the curated list and, failing that, by in-browser neural beat tracking plus a manual fix-up — the only approach that meets R1-R5 on phones; (2) **tap-and-nudge follow-along** as the universal fallback for music playing in any other app; (3) **fingerprint position-sync by microphone** for curated songs, a second-phase feature limited by iOS and by licensing; (4) **desktop tab-audio capture**, precise but desktop-Chromium-only; (5) microphone beat tracking on its own and (6) paid recognition services are not worth building first.

### Cited Findings
- One clock for song, clicks and voice is available only when the song is in the Web Audio graph; Signalsmith Stretch schedules song position against AudioContext time and compensates its own latency (MIT, 111 kB) — [npm signalsmith-stretch](https://www.npmjs.com/package/signalsmith-stretch).
- Built-in pitch-preserving rate change exists everywhere (Chrome 86, Firefox 101, Safari 17.2 unprefixed / earlier prefixed) — [BCD HTMLMediaElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLMediaElement.json). But before Safari 27 (2026-09-14) the media element's `currentTime` updated "only at fixed intervals" in Safari, and pitch-preserved rate changes were mishandled when the element was routed through an AudioContext — [Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes).
- Beat This! weights and code are MIT and the training data include jazz; reported GTZAN F1 89.1 (beats) / 78.3 (downbeats) at ±70 ms **(search summary)** — [beat_this README](https://github.com/CPJKU/beat_this/blob/main/README.md), [arXiv 2407.21658](https://arxiv.org/abs/2407.21658). Jazz downbeat tracking measured at 0.63 **(search summary)** — [TISMIR Jazz Trio Database](https://transactions.ismir.net/articles/10.5334/tismir.186).
- File handles persist only in Chromium; Safari evicts script-written storage after seven days of browser use without interaction — [BCD Window.json](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json), [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- iOS: capture forces a non-mixable play-and-record session; Web Audio alone is "ambient" and mixes with other apps — [WebKit MediaSessionManagerCocoa.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/cocoa/MediaSessionManagerCocoa.mm), [Apple: playAndRecord](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playandrecord), [Apple: ambient](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient).
- Android Chrome avoids call mode only when all input processing is disabled — [Chromium audio_manager_android.cc](https://github.com/chromium/chromium/blob/main/media/audio/android/audio_manager_android.cc).
- Screen-share audio: Chromium desktop only; nothing on phones — [BCD MediaDevices.json](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json).
- Online beat tracking: about 75-80 beat F-measure and 46 downbeat F-measure on GTZAN **(search summary)** — [arXiv 2111.00704](https://arxiv.org/abs/2111.00704).
- Streaming is 69.6% of 2025 recorded-music revenue; downloads have declined 13 years running **(search summary)** — [Music Business Worldwide](https://musicbusinessworldwide.com/10-quick-and-crucial-takeaways-from-ifpis-global-music-report-2026).

### Inferences
| Rank | Approach | R1 control | R2 position | R3 beat grid | R4 tempo | R5 own sounds | Phones | Main risks |
|---|---|---|---|---|---|---|---|---|
| 1 | Own file in Web Audio graph (AudioBuffer; Signalsmith Stretch when rate ≠ 1); grid from curated match, else Beat This! + manual fix | yes | yes (one clock; screen offset via `outputLatency` + user slider) | prepared grid if matched; otherwise draft needing "tap on 1" | yes (0.75-1.15× comfortably; 0.70× at reduced quality) | yes, sample-accurate | iOS, Android, desktop | few users own files; 60-110 MB decoded per song; unknown stretch CPU on low-end phones; Safari storage eviction; analysis time and 25 MB download for unmatched files |
| 1b | Same, but simplest build: `<audio>` + `playbackRate`/`preservesPitch` | yes | probable (two clocks, needs continuous mapping) | as above | yes (quality: good on iOS, WSOLA on Android) | yes, loosely synced | all | drift between media and audio clocks; less control |
| 2 | Tap tempo + "tap on 1" re-anchor + nudge, music in any other app | no | ±30-80 ms after a tap, drifting between taps | as tapped by the user | no | yes (Web Audio only; iOS "ambient") | all, incl. headphones | user effort; live-band drift; iOS Silent switch mutes ambient audio |
| 3 | Microphone + fingerprint position-sync against the curated list (optionally with a beat tracker for fine correction) | no | about 100 ms raw, better with correlation refinement | full prepared grid | no | yes, but leaks into the microphone | Android same-device (processing off); iOS only with a second device; needs a speaker | AGPL and patent caveats of Olaf (or writing an own matcher); permission prompt; noise; no headphones |
| 4 | Desktop tab or system audio capture + the same matcher | no (user controls the other tab) | good (digital path) | full prepared grid | no | yes | none (desktop Chromium only) | share prompt each session; DRM behaviour unconfirmed; legal question open |
| 5 | Microphone beat tracking alone (no song identity) | no | fair on steady music | beats only; "1" and 8-count unreliable | no | yes, leaks | as 3 | accuracy on swing unknown; no ready browser port; needs taps anyway |
| 6 | Paid recognition service (or native ShazamKit) | no | service-dependent | only for curated songs | no | yes | web: needs server-side key; ShazamKit: native only | cost, keys, terms; adds little over an own index |

- Suggested build order for one developer: (a) own-file player on the Web Audio clock with `outputLatency` compensation, a calibration slider, and the manual grid editor ("tap on 1", shift, half/double) — the editor is needed by every other mode; (b) tap-and-nudge follow-along reusing that editor; (c) curated-list matcher (fingerprint + cross-correlation) for own files; (d) in-browser Beat This! for unmatched files; (e) only then microphone or tab-capture sync, which reuse the matcher from (c).
- Decisions that need a device test before committing: Signalsmith Stretch CPU on a low-end Android phone and an older iPhone; `outputLatency` truthfulness with Bluetooth on iOS 27 and Android; whether Spotify/Apple Music keep playing under a Web-Audio-only page on iOS (expected yes) and under a processing-free microphone capture on Android (expected yes); Beat This! small-model speed in a phone browser; Beat This! accuracy on the curated swing list (compare against the hand-made grids the developer already needs for R6).

### Gaps
- The ranking rests on several unmeasured quantities (listed in the last bullet above) and on search summaries for the accuracy figures; the arXiv papers, MIREX tables, TISMIR articles, IFPI/RIAA reports, WebKit/Chromium bug trackers and all commercial product sites could not be opened in this session.
- Legal questions (shipping fingerprints of commercial recordings; analysing captured playback) and the size of the file-owning audience remain open and could change the order of ranks 3 and 4, or the value of rank 1.
