# YouTube IFrame Player API (embedded YouTube videos, YouTube Music content and "Topic" art tracks) as the music engine of a beat-synchronised web app: state as of 17 November 2026

**Use case these notes are judged against.** A free web app by one independent developer for practising swing-dance steps: an animation of two dancers' feet must stay on the beat of a song played from an embedded YouTube player, in phone browsers (iOS Safari, Android Chrome) and on desktop. Requirements: R1 start, pause and seek from the app's own buttons; R2 know the playback position to about 30-50 ms; R3 a beat grid per song prepared in advance for a curated list of videos; R4 slow down or speed up by about -30% to +15% without changing pitch; R5 play the app's own sounds (metronome, spoken step names) over the music and briefly lower the music under the voice; R6 free app with an optional donation button, a few hundred to a few thousand users; R7 a curated song list, each song being one YouTube video ID.

**How the evidence was gathered (read before using any quotation).**
- Date of all retrieval: 17 November 2026.
- Opening web pages directly was not possible. The session's network policy blocked every ordinary website, including developers.google.com and www.youtube.com. No policy page was read in full.
- "Search excerpt" means text that the web search tool displayed on 17 November 2026 as an excerpt of the named page. Text in quotation marks is the excerpt as displayed. It should match the live page closely, but small differences are possible, and surrounding sentences were not visible.
- "Package file" means text I read directly in a public package downloaded from the npm or PyPI registry on 17 November 2026. Version and publication date are given. These are primary sources for what current libraries do, and several of them copy wording from Google's reference pages.

## 1. Controls: play, pause, seek, volume, playback position, duration, state events and buffering

### Takeaway
Every control R1 needs exists as a documented function, but each is an asynchronous message to a cross-origin iframe and none has a documented precision. Position has to be polled (the documented API has no time event), developers report the value as coarse and frozen during buffering, and seeks land on keyframes, so a beat-synced app must run its own interpolated clock and re-anchor it on every state change.

### Cited Findings

**What the documented API offers**
- The player object exposes `playVideo()`, `pauseVideo()`, `stopVideo()`, `seekTo(seconds, allowSeekAhead)`, `mute()`, `unMute()`, `isMuted()`, `setVolume(volume)` and `getVolume()` ("An integer between 0 and 100"), `getPlaybackRate()`, `setPlaybackRate(suggestedRate)`, `getAvailablePlaybackRates()`, `getVideoLoadedFraction()` ("A number between 0 and 1 of how much the player has buffered"), `getPlayerState()`, `getCurrentTime()` and `getDuration()`. Events are `onReady`, `onStateChange`, `onPlaybackQualityChange`, `onPlaybackRateChange`, `onError`, `onApiChange` and `onAutoplayBlocked` (package file: type definitions that transcribe the official reference, version 0.3.0, registry date 4 Oct 2026) — [@types/youtube](https://www.npmjs.com/package/@types/youtube); [official reference](https://developers.google.com/youtube/iframe_api_reference)
- Player states delivered by `onStateChange` and `getPlayerState()`: -1 unstarted, 0 ended, 1 playing, 2 paused, 3 buffering, 5 video cued (package file) — [@types/youtube](https://www.npmjs.com/package/@types/youtube)
- `getCurrentTime()` is documented only as: "Returns the elapsed time in seconds since the video started playing." No resolution or update rate is stated (search excerpt, and identical wording in the package file) — [official reference](https://developers.google.com/youtube/iframe_api_reference); [@types/youtube](https://www.npmjs.com/package/@types/youtube)
- `getDuration()` "will return 0 until the video's metadata is loaded, which normally happens just before the video starts playing"; a library example shows a fractional value (`351.521`), so times are floating-point seconds (package file: README that reproduces the official wording, version 3.6.1, 2022) — [yt-player](https://github.com/feross/yt-player)
- `seekTo`: "The player will advance to the closest keyframe before that time unless the player has already downloaded the portion of the video to which the user is seeking." If the player is paused when `seekTo` is called it stays paused; from other states it plays. "The allowSeekAhead parameter determines whether or not the player will make a new request to the server if seconds is beyond the currently loaded video data." (package file and search excerpts of the official wording) — [yt-player](https://github.com/feross/yt-player); [older official reference page](https://developers.google.com/youtube/js_api_reference)
- The `start` parameter has the same keyframe caveat: "the player will look for the closest keyframe to the time you specify. This means that sometimes the play head may seek to just before the requested time, usually no more than around two seconds." (package file reproducing the official parameter text) — [yt-player](https://github.com/feross/yt-player); [player parameters](https://developers.google.com/youtube/player_parameters)
- `getVolume()` "will return the volume even if the player is muted" (package file) — [yt-player](https://github.com/feross/yt-player)
- `onError` codes: 2 invalid parameter, 5 HTML5 player error, 100 video not found (removed or private), 101 "The owner of the requested video does not allow it to be played in embedded players", 150 "This error is the same as 101. It's just a 101 error in disguise!" (package file and search excerpt) — [@types/youtube](https://www.npmjs.com/package/@types/youtube); [official reference](https://developers.google.com/youtube/iframe_api_reference)
- A newer failure, "error 153", appears when the embedding page sends no HTTP Referer: "viewers attempting to watch embedded YouTube videos will encounter blocked playback and an error screen ("error 153")" (search excerpt). The type definitions and the Video.js error map (both current in late 2026) do not list 153 — [YouTube Help: Embed videos and playlists](https://support.google.com/youtube/answer/171780?hl=en); [Simon Willison, 1 Dec 2025](https://simonwillison.net/2025/Dec/1/youtube-embed-153-error/); [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- `onAutoplayBlocked` "fires any time the browser blocks autoplay or scripted video playback features"; the listed causes include unmuted playback without user interaction and a missing Permissions Policy for autoplay on a cross-origin iframe (search excerpt) — [official reference](https://developers.google.com/youtube/iframe_api_reference)
- Control is by JSON messages posted to the iframe: a page sends `{"event":"listening"}`, receives messages such as `onReady` and `info.playerState`, and sends commands as `{event:'command', func:'playVideo', args:[]}`. The embed URL must carry `enablejsapi=1` (package file, version 1.0.3, Jan 2025) — [youtube-iframe-ctrl](https://www.npmjs.com/package/youtube-iframe-ctrl)
- The `origin` parameter: "Embedding domain. Set it whenever `enablejsapi` is `1`." (package file, version 10.5.0, 16 Nov 2026) — [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- Loading a new video resets settings: "calling functions to cue or load videos or playlists (cueVideoById, loadVideoById, etc.) will reset the playback rate to 1" (search excerpt) — [official reference](https://developers.google.com/youtube/iframe_api_reference)

**Precision of the position, and how developers get smooth time**
- The documented API has no time-update event. One wrapper advertises that it "Adds the all-important 'timeupdate' event, which the YouTube API lacks" (default callback interval 1000 ms); Google's own old web component says "YouTube API does not send events for video progress so we have to call getCurrentTime() manually" — [yt-player](https://github.com/feross/yt-player); [google-youtube component](https://www.webcomponents.org/element/@google-web-components/google-youtube/elements/google-youtube); [SitePoint forum](https://www.sitepoint.com/community/t/youtube-iframe-api-fire-an-event-every-5-minutes/373343)
- Current libraries poll. The Video.js 10 YouTube adapter calls `getCurrentTime()`, `getDuration()` and `getVideoLoadedFraction()` every 50 ms and raises its own `timeupdate` when the value changes (package file, 16 Nov 2026) — [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- The same adapter accepts a seek as applied once the reported time is within 1 second of the requested time (`SEEK_TOLERANCE = 1`) and has either moved off its pre-seek value or 1000 ms have passed (`SEEK_SETTLE_TIMEOUT`). A full second of tolerance is a design allowance for seeks that do not land exactly (package file) — [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- Mux's `<youtube-video>` element listens to two events that are not in the documented list, `onVideoProgress` (used to raise `timeupdate`) and `onVolumeChange`, and also checks position every 50 ms (package file, version 1.9.1, Oct 2026) — [youtube-video-element](https://www.npmjs.com/package/youtube-video-element)
- An undocumented route: the embed posts `infoDelivery` messages whose `info.currentTime` field is "emitted very frequently"; a developer gist reads them instead of polling. The accompanying demo notes that "the YouTube Iframe Player API doesn't expose any way to listen for time change updates" (search excerpts) — [gist](https://gist.github.com/zavan/75ed641de5afb1296dbc02185ebf1ea0); [CodePen](https://codepen.io/zavan/pen/PoGQWmG); [Medium article](https://medium.com/@mihauco/youtube-iframe-api-without-youtube-iframe-api-f0ac5fcf7c74)
- Developer reports of coarseness: a developer who built a rhythm game on a YouTube embed writes that the API "gives you a video player, not a clock" and that `getCurrentTime()` "is coarse. It updates in chunks and freezes while buffering"; the published solution uses a two-source beat clock (player time plus wall clock), a look-ahead metronome scheduler, and a wall-clock fallback when the embed is blocked (search excerpt; publication date not shown) — [DEV Community post](https://dev.to/leviyi/syncing-a-rhythm-game-to-a-youtube-iframe-a-metronome-on-someone-elses-player-3la0)
- A Video.js fix titled "keep current time updating during playback" was needed because coarse time jumps from the YouTube player were being misread as seeks (search excerpt) — [videojs/v10 pull request 2744](https://github.com/videojs/v10/pull/2744)
- A wrapper's documentation suggests polling `getCurrentTime()` about every 100 ms when sub-second display is wanted — [react-native-youtube-iframe docs](https://lonelycpp.github.io/react-native-youtube-iframe/elapsed-time/)
- General background on browser media clocks: a 2018 W3C mailing-list thread describes `currentTime` as jittery and not timestamped, and says good synchronisation depends on an interpolated clock (search excerpt) — [W3C public-web-and-tv, June 2018](https://lists.w3.org/Archives/Public/public-web-and-tv/2018Jun/0040.html)
- Buffering and first-play delay are acknowledged by a long-running product: Soundslice's help says its overlay sound can be out of step with a YouTube recording because "YouTube buffering can also cause a brief delay, especially on the first play after loading", and advises pressing Pause then Play (search excerpt) — [Soundslice help: synth overlay](https://www.soundslice.com/help/en/player/advanced/313/synth-overlay/)
- Buffering is visible as state 3; the Video.js adapter maps it to the standard `waiting` event and state 1 to `playing` (package file) — [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- How a specialist product stores timing against a real recording: in Soundslice "the sync points set the timing" for real recordings, tempo markings affect only synthetic playback, and the metronome's pulse over a recording follows those syncpoints (search excerpts, tool's paraphrase) — [Soundslice help: playback speed](https://www.soundslice.com/help/en/player/basic/5/playback-speed/); [Soundslice help: metronome](https://www.soundslice.com/help/en/player/basic/8/metronome/)

### Inferences
- R1 is met by documented functions. Because every command is a message to another origin, nothing takes effect at the moment it is called. The app should treat `onStateChange` plus an advancing `getCurrentTime()` as the truth, never the moment its own button was pressed.
- R2 needs a clock built by the app: sample `getCurrentTime()` often (every animation frame or every 50 ms), store each new value with `performance.now()`, extrapolate between samples using the current playback rate only while the state is "playing", and re-anchor on every state change, seek and rate change. This is the pattern the rhythm-game developer and the 2018 W3C thread describe.
- The 30-50 ms target is plausible on desktop but is not supported by any documented guarantee. The API gives no timestamp for when a position sample was taken, so each sample carries an unknown delay (message passing plus the embed's internal update interval). Expect to need a per-device offset setting that the user can adjust.
- After `seekTo`, the app must read back where playback actually resumed. The keyframe rule, the "around two seconds" note and the 1-second tolerance in Video.js all point to seeks that can miss the requested time.
- A fixed beat grid is expressed in media time, so pauses, buffering and seeks do not invalidate it as long as the animation is driven from the reported position and not from wall-clock time since "play".
- For R3, one tempo plus the time of beat 1 is unlikely to be enough. Swing-era bands did not play to a click, so the tempo wanders and a constant grid slides off the music within a minute or two (my knowledge of the repertoire, not a sourced finding). Soundslice's model of many sync points along the recording is the safer data format: a list of beat or bar times per video.

### Gaps
- I found no measurement of how often `getCurrentTime()` changes in 2026 browsers, or of its error against the audible sound. This needs a short test on the target phones (log the value every animation frame and look at the step size).
- Recollection, unverified: recent versions of YouTube's IFrame API script keep a copy of the position pushed from the iframe several times a second and, while playing, add the wall-clock time elapsed since the last push. If so, the value is smoother than the "coarse" reports suggest. I could not confirm this because the script could not be fetched.
- `infoDelivery` messages and `onVideoProgress` are undocumented. Nothing guarantees they will keep working.
- How position, duration and state behave while an advertisement is playing was not found (see section 4).
- The official reference page itself could not be opened, so the function list rests on the type definitions and library documentation that copy it.

## 2. Playback rate: setPlaybackRate, available rates, arbitrary values, pitch, and how practice tools get fine speed control

### Takeaway
Officially `setPlaybackRate` takes a "suggested" rate and `getAvailablePlaybackRates` lists quarter steps, but two current sources (Video.js, November 2026, and Soundslice's help) say the embed actually plays any rate from 0.25 to 2 in steps of 0.05. R4's range is therefore reachable as 0.70, 0.75 ... 1.15, but not arbitrary values such as 1.07, and the 0.05 granularity is undocumented behaviour that could change.

### Cited Findings
- Official wording (reproduced in a library README): "This function sets the suggested playback rate for the current video. If the playback rate changes, it will only change for the video that is already being played." Loading another video resets the rate to 1 — [yt-player](https://github.com/feross/yt-player)
- Official rule for unsupported values (search excerpt, lightly paraphrased by the tool): if the suggested rate is not a supported value, the player rounds it "down to the nearest supported value in the direction of 1". The parameter is named `suggestedRate`, and the tool's summary of the page advises listening for `onPlaybackRateChange` and reading `getPlaybackRate()` rather than trusting the value passed in — [official reference](https://developers.google.com/youtube/iframe_api_reference)
- `getAvailablePlaybackRates()` "returns an array of numbers ordered from slowest to fastest playback speed. Even if the player does not support variable playback speeds, the array should always contain at least one value (1)." Example rates in the documentation are 0.25, 0.5, 1, 1.5 and 2 (package file) — [yt-player](https://github.com/feross/yt-player)
- Video.js 10, source comment in the YouTube adapter published 16 Nov 2026: "YouTube plays any rate from 0.25 to 2, rounded down to a step of 0.05, though `getAvailablePlaybackRates` lists only quarter steps." The adapter sets its range to minimum 0.25 and maximum 2 (package file) — [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- Video.js documentation gives a worked example: "YouTube rounds rates down to a step of 0.05, so asking for 1.13 plays at 1.1." (search excerpt) — [Video.js playback-rate feature page](https://videojs.org/docs/framework/html/reference/api/feature-playback-rate); [Video.js youtube-video page](https://videojs.org/docs/framework/html/reference/components/youtube-video)
- Soundslice (a music-notation site that plays YouTube videos in step with the score; launched in 2012 according to the parallel researcher's notes) tells users whose chosen speed is not applied exactly: "You are probably using a YouTube video recording. Those are rounded down to the nearest fifth percentage. This is due to a limitation set by YouTube." (search excerpt) — [Soundslice help: changing playback speed](https://www.soundslice.com/help/en/player/basic/5/playback-speed/)
- History from Soundslice (search excerpt of a post the tool dates to 2017): the YouTube player "traditionally has allowed only 50% and 100% speeds"; YouTube then added 75% in the embedded player and Soundslice began offering 125%, 150% and 200% for YouTube videos. Soundslice's own embed accepts a `speed` value from 25 to 200 — [Soundslice blog](https://www.soundslice.com/blog/50/new-speed-changing-interface-organization-accounts-and-more/); [Soundslice embed options](https://www.soundslice.com/help/en/embedding/customizing/32/playback-options/)
- Soundslice's "speed training" (tempo rises after each loop) works with YouTube videos (search excerpt) — [Soundslice blog: speed training](https://www.soundslice.com/blog/215/introducing-speed-training/)
- A common bug: `setPlaybackRate` silently does nothing if given a string; passing a number fixes it (2019 Stack Overflow thread, read through a mirror) — [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/54301800/youtube-iframe-api-setplaybackrate-not-working)
- The API revision history notes that variable playback rates are only supported in the HTML5 player (search excerpt) — [IFrame API revision history](https://developers.google.com/youtube/iframe_api_revision_history)
- YouTube's own player interface has a custom speed slider in 0.05 steps from 0.25 to 2.0 (news report about the YouTube interface, not about the API) — [PhoneArena](https://www.phonearena.com/news/youtube-access-custom-playback-speeds_id165814)
- Pitch: browsers have a media-element property, `preservesPitch`, that governs pitch correction when speed changes. It is supported in Chrome 86+, Firefox 101+ and Safari 17.2+, with the older `webkitPreservesPitch` in Safari from version 4 and iOS 3.2 (package file: MDN browser compatibility data 8.1.9, 12 Nov 2026) — [MDN: preservesPitch](https://developer.mozilla.org/docs/Web/API/HTMLMediaElement/preservesPitch); [@mdn/browser-compat-data](https://www.npmjs.com/package/@mdn/browser-compat-data)
- An older review of Soundslice, written when YouTube offered only half and full speed, says speed-changed audio often has audible artifacts (tool's paraphrase) — [Mark Heath](https://www.markheath.net/post/soundslice)

### Inferences
- For R4 the app should offer only exact multiples of 0.05 between 0.70 and 1.15 (ten steps), send them as numbers, and display the value returned by `onPlaybackRateChange` or `getPlaybackRate()`, not the value requested.
- A request for 0.85 should play at 0.85. A request for 1.07 would play at 1.05. For values below 1 the two descriptions ("rounded down to a step of 0.05" and "in the direction of 1") could disagree, which is another reason to send only exact steps.
- Pitch should be preserved because pitch correction is the browser default for media elements (my understanding of the HTML standard; not re-checked in this session), not because YouTube's documentation promises it. The quality of the time-stretching differs between browsers and is most audible at the slow end (0.70).
- The beat grid stays valid at any rate because it is in media time. The app's own metronome and voice cues must be scheduled with beat intervals divided by the current rate.
- The parallel researcher's notes on precedents describe YouTube speed as "a fixed set of speeds". The evidence above refines that: the set is a 5% grid from 25% to 200%, not only the quarter steps the API lists.

### Gaps
- No Google page was found that documents the 0.05 granularity. It rests on Video.js and Soundslice. I could not test it in a browser in this session.
- Whether iOS Safari and Android Chrome honour 0.05 steps identically to desktop was not found.
- No official statement on pitch preservation in the embedded player was found.

## 3. Phone browsers: starting playback, inline play, volume, a second audio source, background and lock screen, latency

### Takeaway
Starting from the app's own button works on phones only under conditions: on iPhone and iPad Safari the player iframe must already be loaded before the tap, and on Chrome the iframe needs `allow="autoplay"`. The largest phone-specific limit for this app is that iOS ignores volume changes on media elements, so the music cannot be lowered under the voice on iPhone or iPad (only muted); in addition, embedded playback is reported to stop when the page is hidden (a developer report for Android Chrome; nothing sourced for iOS).

### Cited Findings

**Starting playback from a tap**
- Google's reference, "Mobile considerations" (quoted in a library README): "The HTML5 `<video>` element, in certain mobile browsers (such as Chrome and Safari), only allows playback to take place if it's initiated by a user interaction (such as tapping on the player)." (package file, version 3.4.0, Nov 2025) — [react-player](https://www.npmjs.com/package/react-player); [official reference, mobile considerations](https://developers.google.com/youtube/iframe_api_reference#Mobile_considerations)
- Chrome: a cross-origin iframe needs autoplay permission delegated by the top page with `allow="autoplay"`; "top frames can delegate autoplay permission to their iframes to allow autoplay with sound"; a blocked `play()` is rejected with `NotAllowedError` (search excerpt) — [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay); [Chromium autoplay notes](https://www.chromium.org/audio-video/autoplay)
- The `allow="autoplay"` iframe permission is supported in Chrome and Chrome for Android from version 64 and Firefox from 74, and is not supported in Safari or Safari on iOS (package file: MDN compatibility data, 12 Nov 2026) — [@mdn/browser-compat-data](https://www.npmjs.com/package/@mdn/browser-compat-data)
- iPhone and iPad Safari, from the maintainer of a widely used lightweight embed (release 0.4.0 published 16 Nov 2026): "Safari on iOS/iPadOS blocks audible playback when the YouTube iframe is created after a tap. To make one-tap playback work with sound, `lite-youtube` automatically prepares the hidden iframe and IFrame Player API ahead of time on iPhone and iPad Safari". The code comment reads "iPhone and iPad Safari need the YouTube iframe loaded before the tap", and the tap handler then calls `playVideo()` on the already-ready player (package file) — [lite-youtube-embed](https://github.com/paulirish/lite-youtube-embed)
- In the same library, other mobile browsers and desktop Safari create the player after the tap and call `playVideo()` in `onReady`; plain desktop browsers just insert an iframe with `autoplay=1` (package file) — [lite-youtube-embed](https://www.npmjs.com/package/lite-youtube-embed)
- A developer report concerning iOS 15: autoplay through the IFrame API failed even though the user had tapped earlier on a previous screen (search excerpt; no fix recorded) — [Jitsi community thread](https://community.jitsi.org/t/youtube-autoplay-not-working-on-ios-in-iframe-api/111377)
- Muted start: the `mute` parameter is described as "Whether or not to start the video muted. Some browsers require this set to 1 for autoplay to work (e.g. Chrome)." (package file) — [@types/youtube](https://www.npmjs.com/package/@types/youtube)
- Inline playback: `playsinline` controls "whether videos play inline or fullscreen in an HTML5 player on iOS"; the type definitions note the default is fullscreen, and current wrappers (Video.js, lite-youtube-embed, yt-player) all set `playsinline=1` (package files) — [@types/youtube](https://www.npmjs.com/package/@types/youtube); [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video)
- Referer requirement that often bites in app shells and webviews: "API Clients that use the YouTube embedded player (including the YouTube IFrame Player API) must provide identification through the HTTP Referer request header." A page must not send `Referrer-Policy` values that suppress it; `strict-origin-when-cross-origin` works; Chrome extension pages do not send it and get error 153 (search excerpts; lite-youtube-embed sets `referrerPolicy = 'strict-origin-when-cross-origin'` with the comment "Required by Youtube to fix Error 153") — [Simon Willison, 1 Dec 2025](https://simonwillison.net/2025/Dec/1/youtube-embed-153-error/); [Chromium extensions group](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/OUJad0q-d_g); [lite-youtube-embed](https://www.npmjs.com/package/lite-youtube-embed)
- Safari's "Prevent Cross-Site Tracking" setting is reported to stop some embedded YouTube players from working on iPhone and iPad unless the user is signed in to YouTube in Safari (one blogger's fix, Nov 2024) — [Felix Wong](https://felixwong.com/2024/11/solved-embedded-youtube-videos-not-playing-in-safari-ipad-iphone/)

**Volume, mute and lowering the music (R5)**
- On Safari for iOS the media `volume` property "returns a value and is writable; however, the value is always 1, and setting a value has no effect on the volume of the media object" (package file: MDN compatibility data, 12 Nov 2026) — [MDN: HTMLMediaElement.volume](https://developer.mozilla.org/docs/Web/API/HTMLMediaElement/volume); [@mdn/browser-compat-data](https://www.npmjs.com/package/@mdn/browser-compat-data)
- Apple's own forum, about a YouTube-embed watch-party app: "it's not possible to directly change the volume because iOS does not support changing the volume via JavaScript, unlike macOS. Setting volume doesn't do anything and getting it always returns 1." (search excerpt) — [Apple Developer Forums](https://developer.apple.com/forums/thread/713772)
- The same effect reported against the YouTube API specifically: "setVolume(50) function is working in browser and android, but not working in ios"; an older question reports the same on iPad (search excerpts) — [youtube-player issue 76](https://github.com/gajus/youtube-player/issues/76); [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/31147753/youtube-iframe-embed-can-t-control-audio-on-ipad)
- WebKit deliberately protects volume from being set on iOS (bug title: "Clean up code that protects volume from being set on iOS") — [WebKit bug 241657](https://bugs.webkit.org/show_bug.cgi?id=241657)
- Muting does work on iOS: one answer reports that `muted` works where `volume` does not (anecdotal, iOS 15) — [Stack Overflow mirror](https://kaweah.freedombox.rocks/kiwix/stackoverflow.com_en_all_2023-11/questions/27296391/is-there-any-possibility-to-control-html5-audio-volume-on-ios)

**A second audio source from the page at the same time**
- It is done in production: Soundslice plays its own metronome and synthesised notes over YouTube recordings. "You'll hear a metronome beat on top of the audio — both with real recordings or with synthetic playback", and synth overlay "works with any type of recording: MP3, YouTube or other video" (search excerpts) — [Soundslice help: metronome](https://www.soundslice.com/help/en/player/basic/8/metronome/); [Soundslice help: synth overlay](https://www.soundslice.com/help/en/player/advanced/313/synth-overlay/)
- iPhone silent switch: "On Safari for iOS, audio is allowed to play when the device's mute switch is enabled, but only for HTML5 audio tags, and not for Web Audio." A user tap is still required before any sound (package file, 2022) — [unmute-ios-audio](https://github.com/feross/unmute-ios-audio)
- Page audio is locked until a user gesture on mobile browsers: "audio on mobile browsers and Chrome/Safari is locked until a sound is played within a user interaction, and then it plays normally the rest of the page session" (package file, 2023) — [howler.js](https://github.com/goldfire/howler.js)
- The Audio Session API lets a page declare its audio type (playback, ambient, transient). It is implemented only in Safari (16.4 and later, including iOS); Chrome does not have it and Firefox has it only as a preview (package file: MDN compatibility data) — [MDN: AudioSession](https://developer.mozilla.org/docs/Web/API/AudioSession); [@mdn/browser-compat-data](https://www.npmjs.com/package/@mdn/browser-compat-data)
- A developer note on iPad Safari: setting the session type to "playback" makes Web Audio ignore silent mode but also pauses other apps' audio, and needed iPadOS 17.5 or later in that test (search excerpt; single source) — [GitHub issue](https://github.com/Larront/grimoire/issues/244)
- Unstable interplay between Web Audio and media elements on iOS has been reported over the years, for example Web Audio staying silent until a media element played, then later playing for a second and stopping (blog posts from 2020 onward) — [Adactio 2020](https://adactio.com/journal/17709); [Adactio update](https://adactio.com/journal/19929)
- Output latency of the page's own sounds can be read from `AudioContext.outputLatency` in Chrome 102+, Firefox 70+ and Safari 18.4+ (package file: MDN compatibility data) — [MDN: outputLatency](https://developer.mozilla.org/docs/Web/API/AudioContext/outputLatency)
- Spoken step names through the browser's speech synthesiser are available in Safari on iOS and Chrome for Android but not in Android WebView (package file: MDN compatibility data) — [MDN: SpeechSynthesis](https://developer.mozilla.org/docs/Web/API/SpeechSynthesis)

**Tab in the background, screen lock**
- Android Chrome, developer report: a YouTube embed "pauses when the tab is in the background"; the author attributes the pause to the embedded player itself reacting to the page being hidden, says it does not restart without a user tap, and found that silent keep-alive audio and Media Session controls did not override it (search excerpt of a GitHub issue; date not shown) — [GitHub issue](https://github.com/DhruvHarani1/vega/issues/5)
- A news report states that YouTube limits background play on mobile to Premium subscribers and has been closing browser workarounds — [AOL article](https://www.aol.com/articles/popular-youtube-background-playback-workaround-163304730.html)
- YouTube's policies forbid building background play: an API client must not "create, include, or promote features that play content, including audio or video components, from a background player" (search excerpt; see section 5) — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- The Screen Wake Lock API (keeps the screen from locking while the page is visible) is supported in Chrome 84+ and in Safari on iOS from 16.4, with full support including Home Screen web apps from 18.4 (package file: MDN compatibility data) — [MDN: WakeLock](https://developer.mozilla.org/docs/Web/API/WakeLock)

### Inferences
- R1 on iPhone and iPad: create the visible player when the song is chosen, wait for `onReady`, and call `playVideo()` directly inside the tap handler of the app's Play button. Creating the player in response to the tap is the pattern that Safari blocks. On Android Chrome add `allow="autoplay"` to the iframe.
- If the browser still blocks the start, `onAutoplayBlocked` fires and the user has to tap YouTube's own play button, which is one more reason the player must stay visible and uncovered.
- R5 ducking is not possible on iPhone or iPad through the player: `setVolume` has no effect there. The only options are to mute and unmute the music, to leave the music at full level and make the voice clips loud and clear, or to accept ducking on desktop and Android only.
- R5 mixing: the app's sounds and the embed both play, but on iPhone the silent switch silences Web Audio while the YouTube video keeps sounding, so a user can hear music with no metronome or voice. The app should unlock audio on the first tap and, in Safari, consider declaring a "playback" audio session.
- Locking the phone or switching apps will stop the music, and policy forbids engineering around that. A practice app should request a screen wake lock while a song is playing and show a clear "tap to resume" state after any interruption.
- Latency: the music and the app's own sounds leave through the same device, so Bluetooth delay affects both. What needs calibrating is the difference between the position YouTube reports and what is heard, against the app's audio clock. A simple user-adjustable offset per device covers this.

### Gaps
- iOS Safari behaviour when the screen locks or Safari goes to the background with a YouTube embed playing: no direct source found. Recollection, unverified: the video pauses and stays paused until the user taps play.
- Whether calls made a moment after a tap (from a timer or a promise, for example after a spoken count-in) still count as user-initiated on iOS was not found. The search tool offered, from general knowledge and without a source, that the call may need to run synchronously inside the tap handler.
- Whether starting the next song automatically (`loadVideoById` with no new tap) is allowed on iOS Safari and Android Chrome was not found.
- The test matrix that lite-youtube-embed's README refers to (`autoplay.md`) could not be opened.
- No source measured audio delay of the YouTube embed against Web Audio on phones.

## 4. Advertising and availability: ads on embedded music, embedding blocks, regional and age restrictions, Topic art tracks, stability of video IDs, official checks

### Takeaway
The embedding site cannot switch off or predict ads; embedded videos follow the same ad settings as on YouTube and interfering with ads is prohibited. Whether a given music video plays in an embed is decided per video by the owner and by rights claims, the official `status.embeddable` flag is explicitly not sufficient, and I found no figures on how often music (including Topic art tracks) is blocked, so every curated video ID has to be tested in a real embed and monitored.

### Cited Findings

**Ads**
- YouTube Help, "Ads on embedded videos": embedded videos follow "the same ad-enablement settings" as on youtube.com; only YouTube and the video owner earn from those ads, the embedding site gets no share; a creator cannot turn ads off for embeds only, but can turn off embedding (search excerpt, partly paraphrased by the tool) — [YouTube Help](https://support.google.com/youtube/answer/132596?hl=en)
- The embedder must not "modify, interfere with, replace, or block advertisements placed or served by YouTube or by YouTube API Services" (search excerpt) — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Google's compliance guide lists as its first prohibited example: "Restricting ads from playing in your API service when they would otherwise play on YouTube or in an embedded video." (search excerpt) — [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)
- A university notice about embeds in its learning platform: the ads "are controlled by YouTube and cannot be disabled" by instructors, students or administrators — [UC Berkeley](https://rtl.berkeley.edu/node/1130)
- The embed loads advertising infrastructure even in privacy mode: a lightweight embed pre-connects to `googleads.g.doubleclick.net` and `static.doubleclick.net` for the youtube-nocookie.com player, with the comment "Not certain if these ad related domains are in the critical path" (package file) — [lite-youtube-embed](https://www.npmjs.com/package/lite-youtube-embed)
- YouTube Premium: only forum-level evidence. One Hacker News commenter (2024) says they pay for Premium and that it relies on third-party cookies to keep ads off embedded videos; another says there were then "no ads in embedded videos whether you have paid for premium or not"; another says YouTube's systems evaluate the embedding site and its content before turning on in-stream ads. These conflict and none is official — [Hacker News comment](https://news.ycombinator.com/item?id=40144199); [Hacker News thread](https://news.ycombinator.com/item?id=40143242)

**Embedding disabled, age restriction, region**
- Data API, `status.embeddable`: "This value indicates whether the video can be embedded on another website. Note: Even if the uploader's settings allow embedding, videos may still be blocked from playback in embedded players due to platform policies or third-party claims (such as Content ID)." (search excerpt) — [Data API videos resource](https://developers.google.com/youtube/v3/docs/videos)
- Rights owners have a separate control: YouTube's "Restrict embedding" help describes domain allow and block rules that content owners can apply to videos they own and videos they claim (search excerpt) — [YouTube Help: Restrict embedding](https://support.google.com/youtube/answer/6301625?hl=en)
- "Age-restricted videos can't be watched on most 3rd party websites. These videos will redirect viewers back to YouTube when played." (search excerpt); introduced in September 2020 — [YouTube Help: Embed videos and playlists](https://support.google.com/youtube/answer/171780?hl=en); [YouTube Help: Age-restricted content](https://support.google.com/youtube/answer/2802167); [9to5Google, 22 Sep 2020](https://9to5google.com/2020/09/22/youtube-age-restricted-videos/)
- Region: `contentDetails.regionRestriction` holds either an `allowed` list ("If this property is present and a country is not listed in its value, then the video is blocked from appearing in that country. If this property is present and contains an empty list, the video is blocked in all countries.") or a `blocked` list ("If this property is present and a country is not listed in its value, then the video is viewable in that country."). Google's generated client library labels the structure "DEPRECATED Region restriction of the video", while the main reference page still presents it as a normal property (package file: Google's official client, version 40.1.0, 12 Nov 2026, and search excerpt) — [@googleapis/youtube](https://www.npmjs.com/package/@googleapis/youtube); [Data API videos resource](https://developers.google.com/youtube/v3/docs/videos)
- Other official fields useful for screening: `contentDetails.licensedContent` ("indicates whether the video is licensed content"), `contentDetails.contentRating.ytRating` ("A rating that YouTube uses to identify age-restricted content"), `status.privacyStatus`; `search.list` has `videoEmbeddable` and `videoSyndicated` filters (package file) — [@googleapis/youtube](https://www.npmjs.com/package/@googleapis/youtube)
- At run time a blocked video shows as error 101 or 150 ("The owner of the requested video does not allow it to be played in embedded players"), a removed or private video as error 100. One wrapper groups these as an "unplayable" event so the app can move on (package files) — [@types/youtube](https://www.npmjs.com/package/@types/youtube); [yt-player](https://github.com/feross/yt-player)

**Topic channels and art tracks**
- An art track is an automatically generated video made of the sound recording and the album art, placed on an auto-generated "Topic" channel. Distributors state that these are generated by YouTube and that the distributor cannot edit or claim the channel (search excerpts of distributor help pages) — [Symphonic](https://support.symdistro.com/hc/en-us/articles/115000437283-YouTube-Art-Tracks); [DistroKid](https://support.distrokid.com/hc/en-us/articles/360013534834-Using-DistroKid-for-YouTube-vs-Uploading-It-to-YouTube-Directly); [The Source](https://support.the-source.eu/kb/a255/youtube-art-tracks-and-topic-channels-on-youtube.aspx)
- YouTube's internal player data carries a per-video flag for embeds: the documentation sample of an unofficial YouTube Music library shows `"playabilityStatus": {"status": "OK", "playableInEmbed": true, ...}` for a song (package file, version 1.12.3) — [ytmusicapi](https://pypi.org/project/ytmusicapi/)

### Inferences
- Ads cannot be avoided by choice of parameters, and blocking them breaks policy. A pre-roll simply delays the song; the app must start its animation from the reported position once the state is "playing", never from the tap.
- Label-owned and claimed recordings are the videos most likely to carry ads and embedding rules, because the owner, not the uploader, sets them. Old swing recordings uploaded by collectors may behave differently from label art tracks, and can change when a claim is added.
- Premium cannot be relied on to remove ads inside an embed on phones: the embed has to recognise the viewer's YouTube sign-in from inside a third-party page, which Safari's tracking prevention is reported to interfere with.
- Screening procedure for a curated list: (1) `videos.list` with `status` and `contentDetails` for each ID (embeddable, privacy, region, age rating); (2) play each ID once in an embed on the real production domain, because the `embeddable` flag is explicitly insufficient; (3) repeat the API check on a schedule; (4) handle errors 100, 101 and 150 at run time with a message and an alternative video for the same song.
- A beat grid belongs to one specific upload. If a video is removed and replaced by another upload of the same recording, its start offset (and sometimes its speed) will differ, so the grid must be re-aligned.

### Gaps
- No statistics were found on how often embedding is disabled for music, for label official videos, or for Topic art tracks, and no source stated whether art tracks are embeddable as a rule. Searches on this returned only generic troubleshooting pages. Recollection, unverified: many label official videos and a share of art tracks return error 150 on third-party sites, and others play; it varies by label and by video.
- No study of how long music video IDs survive (removal rates over years) was retrieved; the search could not be run.
- How often embedded music videos show pre-roll ads, whether mid-roll ads occur on short tracks, and how the API reports state and position during an ad were not found. Recollection, unverified: since a terms change in November 2020 YouTube may run ads on videos from channels outside its partner programme, so an unmonetised uploader is no guarantee of no ads; a YouTube Help page titled "Updated Terms of Service FAQs" appeared in results but its text was not retrieved — [YouTube Help](https://support.google.com/youtube/answer/10090902?hl=en)
- No official statement on whether Premium members see ads in third-party embeds.
- The meaning of the `videoSyndicated` filter and whether "syndication" settings explain blocked art tracks could not be confirmed.

## 5. Rules: what the YouTube API Services terms, Developer Policies, Required Minimum Functionality and YouTube Terms of Service say, and whether this use breaches them

### Takeaway
A visible, uncovered player of at least 200 by 200 pixels, driven through the documented functions, with the app's animation beside it, conflicts with no clause I could retrieve and matches the pattern of long-running products such as Soundslice (section 7). The clear prohibitions are hiding, shrinking, covering or altering the player, playing from a player that is not on screen, touching ads, and charging for or gating playback; the unresolved risk is the audio clause ("separate, isolate, or modify the audio or video components ... you must not apply alternate audio tracks to videos"), which does not mention added sounds but could be read against a metronome and voice laid over the music.

### Cited Findings

All policy quotations below are search excerpts retrieved on 17 November 2026. The search tool reported the policy pages as last updated about 64 days earlier (mid-September 2026); a 2026 GitHub pull request that cites them describes the Developer Policies and Required Minimum Functionality pages as last updated in October 2026 — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies); [GitHub pull request](https://github.com/BenArtzi4/Sound-Clash/pull/401)

**Who is bound**
- "API Client means a website or software application (including a mobile application) developed by you that accesses, or uses, the YouTube API Services." (EMEA version of the terms; regional versions exist for EMEA, APAC and Russia alongside the main one) — [API Services Terms of Service (EMEA)](https://developers.google.com/youtube/terms/api-services-terms-of-service-emea); [API Services Terms of Service](https://developers.google.com/youtube/terms/api-services-terms-of-service)
- The embedded player is treated as part of this: "API Clients that use the YouTube embedded player (including the YouTube IFrame Player API) must provide identification through the HTTP Referer request header." — [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)
- "API Clients must also comply with the Requirements for Minimum Functionality for YouTube API Services ("RMF")." — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Changes: YouTube gives notice "by posting the changes at the revision history page, emailing the address associated with your credentials, or otherwise notifying you. The changes will not apply retroactively, and will become effective no sooner than 30 calendar days after posting." — [Terms revision history](https://developers.google.com/youtube/terms/revision-history)

**Player size and visibility**
- "Embedded players must have a viewport that is at least 200px by 200px. If the player displays controls, it must be large enough to fully display the controls without shrinking the viewport below the minimum size." The same page recommends at least 480 by 270 pixels for 16:9 players — [official reference](https://developers.google.com/youtube/iframe_api_reference); [player parameters](https://developers.google.com/youtube/player_parameters); [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)
- Autoplay and scripted playbacks: a client must not start an automatic or scripted playback "until the player is visible and more than half of the player is visible on the page or screen"; "A page or screen must not have more than one YouTube player that automatically plays content simultaneously."; "Any YouTube thumbnail that initiates a playback must be at least 120 pixels wide and 70 pixels tall." — [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)
- Nested iframes (policy update of 2 June 2022): "the YouTube player must not be situated in a nested or hierarchical iframe lineage to circumvent YouTube policies or otherwise obfuscate the source of use." — [Terms revision history](https://developers.google.com/youtube/terms/revision-history)
- Hiding YouTube's control bar is an official option, distinct from covering it: the `controls` player parameter has the value 0 for "Player controls do not display" (package file) — [@types/youtube](https://www.npmjs.com/package/@types/youtube); [player parameters](https://developers.google.com/youtube/player_parameters)

**Overlays and obscuring the player**
- "You must not display overlays, frames, or other visual elements in front of any part of a YouTube embedded player, including player controls. Similarly, you must not use overlays, frames or other visual elements to obscure any part of an embedded player, including player controls." — [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)
- The compliance guide is softer: it accepts overlays for user consent or for playback controls such as mute, full screen, play and pause, provided they do not conflict with the YouTube player's own interface elements (tool's paraphrase of the guide). The guide says of itself that it "does not replace any existing documents" — [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)

**Modifying the player or playback**
- An API client must not "modify, build upon, or block any portion or functionality of a YouTube player" — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Guide: "Don't use our API to re-create YouTube (e.g. don't clone, mimic, modify, or reduce standard YouTube features)"; a service must not diminish or remove features that are part of the standard experience, "such as captions, volume controls, etc." — [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)
- The older YouTube Terms of Service (archived 2018 version) said: "If you use the Embeddable Player on your website, you may not modify, build upon, or block any portion or functionality of the Embeddable Player, including but not limited to links back to the YouTube website." Whether this sentence is still in the current terms was not confirmed — [YouTube Terms, 2018 archive](https://www.youtube.com/t/terms?archive=20180525)

**Audio and video components; background and audio-only play**
- API clients must not "separate, isolate, or modify the audio or video components of any YouTube audiovisual content made available as part of, or in connection with, YouTube API Services." The policy's own example: "you must not apply alternate audio tracks to videos". (The first phrase was my search string, which the tool confirmed as matching the page; the example was displayed by the tool.) — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- They must not "promote separately the audio or video components" of such content (phrase confirmed as near-verbatim) — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- They must not "create, include, or promote features that play content, including audio or video components, from a background player", defined as a player that is not displayed in the page, tab or screen that the user is viewing — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Guide examples of what not to do: "Offer users the ability to download or separate audio tracks or allow users to modify the audio or video portions of a video", for example an API service that offers MP3 files of audio taken from a video; allowing background play, for example videos that keep playing when the service's window is closed or minimised — [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)
- How other developers read these rules (the search tool dates one of these three items to 2026; the others carried no date): one project summarises "YouTube policy prohibits separating audio from video, hidden/background playback, and modifying/obscuring the embedded player"; another changed its app to "show the YouTube player in the app"; a third enforced "one visible player, buttons off the picture, at least 200 x 200". These are developers' readings, not rulings — [Macamp issue 17](https://github.com/holgerkrupp/Macamp/issues/17); [Cr8-audio pull request 170](https://github.com/Cr8-audio/app/pull/170); [Sound-Clash pull request 401](https://github.com/BenArtzi4/Sound-Clash/pull/401)

**Money: charging, advertising, sponsorship**
- The Developer Policies' user-experience section says API clients must not charge users to watch content in an embedded YouTube player (tool's paraphrase) and "API Clients must not otherwise gate access to a video"; they also must not "offer or provide incentives, rewards, or other compensation to users for engaging with YouTube Applications" — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Guide: "you also cannot charge people a fee for services that are offered free of charge on YouTube" — [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)
- API clients must not "sell advertising, sponsorships, or promotions that are placed on or within YouTube audiovisual content or the YouTube player without YouTube's prior written approval". On pages that show YouTube API data, selling them is barred "unless other data, content, or material not obtained from YouTube appears on the same page and offers enough independent value to justify such sales if the YouTube API Data were removed" — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- YouTube Terms of Service: users may not "use the Service to: (a) sell any advertising, sponsorships, or promotions placed on, around, or within the Service or Content, other than those allowed in the Advertising on YouTube policies (such as compliant product placements)"; nor sell them on a page that contains only YouTube content or where that content is the primary basis for the sales, the example given being "selling ads on a webpage where YouTube videos are the main draw" — [YouTube Terms of Service](https://www.youtube.com/t/terms)

**YouTube Terms of Service on access through the player**

**Precedent bearing directly on added sounds**
- Soundslice plays its own metronome "on top of the audio" of YouTube recordings and offers a "synth overlay" that plays synthesised notes together with "any type of recording: MP3, YouTube or other video" (launched in a blog post titled "New: Play synth and real recordings at the same time") — [Soundslice help: metronome](https://www.soundslice.com/help/en/player/basic/8/metronome/); [Soundslice help: synth overlay](https://www.soundslice.com/help/en/player/advanced/313/synth-overlay/); [Soundslice blog](https://www.soundslice.com/blog/265/new-play-synth-and-real-recordings-at-the-same-time/)

### Inferences

**Does a beat-synced animation next to a visible player breach any clause?** None of the retrieved clauses restricts what is shown beside the player or reacting to its position. The clauses concern what is in front of the player, the player's size and visibility, and its functions. This matches the pattern of Soundslice and similar products. No clause about "synchronising" other content with YouTube content appeared in any excerpt.

**Does playing the page's own metronome and voice over the video's sound breach any clause?** Not explicitly. The YouTube audio is not separated, isolated or altered; it plays unmodified from the YouTube player, and lowering it uses the documented volume function. The nearest rule is the ban on modifying audio components with the example of "alternate audio tracks", which reads as aimed at replacing or re-tracking a video's sound. A strict reader could still argue that mixing a constant click and voice over the music changes what the user hears of the content. I rate this a moderate, unresolved risk, reduced by Soundslice offering the same thing openly as a documented feature, and lowest if the added sounds are optional, clearly the app's own, and the user can switch them off.

**Verdict against the use case**

| Requirement | Does it work? | Policy position |
|---|---|---|
| R1 app's own play, pause, seek | Yes on desktop and Android Chrome; yes on iPhone and iPad if the player is loaded before the tap (section 3) | Allowed: these are the documented functions. The player must be more than half visible when a scripted start happens, and its own controls must stay uncovered |
| R2 position within 30-50 ms | Partly: no documented precision; needs polling plus interpolation and a per-device offset (section 1) | No issue |
| R3 beat grid per video, prepared in advance | Yes as data keyed by video ID in media time | The grid must not be produced by downloading or recording YouTube audio (Terms: no "download" or other use except as permitted). Tap the beats against the embedded player, or analyse a lawfully owned copy and align it by ear |
| R4 tempo -30% to +15%, same pitch | Yes in 5% steps (undocumented granularity); pitch kept by browser default (section 2) | Allowed: speed is a player function |
| R5 own sounds over the music, ducking | Sounds: yes. Ducking: desktop and Android only; impossible on iPhone and iPad, where only mute works (section 3) | Not addressed explicitly; moderate risk under the audio-components clause |
| R6 free, donation button, small scale | No key or quota for the player | Must not charge for or gate playback, must not sell ads or sponsorships where YouTube content is the main draw. A voluntary donation is not mentioned by any retrieved clause. Needs a privacy policy and a link to YouTube's terms |
| R7 curated video IDs | Yes, but each ID can be blocked, restricted, removed or carry ads (section 4) | Allowed; do not block ads |

**Other points**
- The user's own use must be personal and non-commercial. A teacher playing songs from the app to a class is the kind of use the terms' example ("publicly screen videos or stream music") excludes. The app can say so, but cannot prevent it.
- The safest page layout is: one player, at least 200 by 200 pixels, always on screen while music plays (for example fixed above the animation), nothing drawn over it, YouTube's controls either left on or hidden only through the official `controls` parameter, and no audio-only or minimised mode.
- An app whose stated purpose is "music player for dancing" sits closer to the products YouTube has acted against than an app whose stated purpose is "step trainer that follows a video you choose". How the product presents itself affects risk even when the code is identical.

- Recollection, unverified: the current documents contain no clause on synchronising other content with YouTube content. Absence from search excerpts is not proof.
- The date and version of the current YouTube Terms of Service were not shown. A PDF of the United States terms dated 15 December 2023 appeared in search results (address only, text not read).
- The exact sentence about charging for embedded playback was only paraphrased by the search tool.
- No clause or official statement about donation buttons was found either way.

## 6. API key and quota: the IFrame player alone, and the Data API for checking videos

### Takeaway
The IFrame player needs no API key, no sign-in and has no quota; its only identification requirement is the HTTP Referer header. Checking videos through the YouTube Data API needs a key from a Google Cloud project, costs 1 unit per `videos.list` call, and a curated list of a few hundred songs fits easily inside the default 10,000 units a day.

### Cited Findings
- "The YouTube IFrame Player API service, which lets you embed videos in a website, does not require authorization just as users do not need to log in to the YouTube website to watch a video." (search excerpt from Google's YouTube developer policy pages; the tool did not show which page) — [Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- Current libraries load the script `https://www.youtube.com/iframe_api` and create `new YT.Player(...)` with no key or credential anywhere in the call (package files: lite-youtube-embed 0.4.0, Video.js adapter 10.5.0, Mux element 1.9.1) — [lite-youtube-embed](https://www.npmjs.com/package/lite-youtube-embed); [@videojs/youtube-video](https://www.npmjs.com/package/@videojs/youtube-video); [youtube-video-element](https://www.npmjs.com/package/youtube-video-element)
- The embedding page identifies itself through the HTTP Referer header; "In some environments, the browser will automatically set HTTP Referer, and API Clients need only ensure they are not setting the Referrer-Policy in a way that suppresses the Referer value." (search excerpt) — [Simon Willison quoting the requirement, 1 Dec 2025](https://simonwillison.net/2025/Dec/1/youtube-embed-153-error/); [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)
- Data API: "API key. Your API key identifies your project and provides you with API access, quota, and reports. Required unless you provide an OAuth 2.0 token." (package file: Google's official client, 12 Nov 2026) — [@googleapis/youtube](https://www.npmjs.com/package/@googleapis/youtube)
- A `videos.list` call costs 1 unit. "All API requests, including invalid requests, incur at least a one-point quota cost." "Daily quotas reset at midnight Pacific Time (PT)." (search excerpts) — [Quota calculator](https://developers.google.com/youtube/data/determine_quota_cost); [videos.list](https://developers.google.com/youtube/v3/docs/videos/list)
- Default allocation in 2026: 100 `search.list` calls, 100 `videos.insert` calls, and 10,000 units a day shared by all other methods. A June 2026 revision note says the API is moving to more granular quotas, starting with those two methods. More quota is requested through a quota extension form (search excerpts) — [Data API overview](https://developers.google.com/youtube/data/getting-started); [Data API revision history](https://developers.google.com/youtube/data/revision_history)
- The `status` and `contentDetails` information can be read without user sign-in, with a key alone (tool's paraphrase: these properties "can also be retrieved with unauthenticated requests") — [Data API videos resource](https://developers.google.com/youtube/v3/docs/videos)

### Inferences
- For a few hundred to a few thousand users the player imposes no cost or registration. The developer never has to create a Google Cloud project unless they choose to use the Data API.
- The Data API check should run on the developer's side on a schedule (a script or a small server job), not in every visitor's browser, so the key is not exposed and quota use stays tiny: even one call per video per day for 500 videos is 500 units.
- Using the Data API makes the developer a registered API user with a project that YouTube can audit, and brings the Data API's own rules on storing and refreshing data. Using only the player keeps the footprint smaller, at the price of having no official availability check.

### Gaps
- Recollection, unverified: `videos.list` accepts up to 50 video IDs per call, which would cut the cost to about 10 units for 500 videos. The official client's text for `videos.list` says only "Return videos with the given ids"; the 50-ID limit is stated there for the newer `videos.batchGetStats` method ("The number of IDs specified cannot exceed 50") — [@googleapis/youtube](https://www.npmjs.com/package/@googleapis/youtube)
- Recollection, unverified: requests for more quota trigger a compliance audit of the application.
- Rules on how long Data API results may be stored were not retrieved.

## 7. Precedents: sites that synchronise their own material with an embedded YouTube player, and cases where YouTube acted

### Takeaway
Synced content beside a visible, unmodified player is a long-established pattern, and one such product (Soundslice) also plays its own metronome and synthesised notes over YouTube audio. Every enforcement case I could confirm involved audio taken out of, or played without, the visible player (Streamus 2015, Discord music bots 2021, Musi 2024).

### Cited Findings

**Operating products and experiments**
- Soundslice synchronises notation with YouTube videos through "syncpoints", changes speed through the YouTube player, and layers its own metronome and synth sound over the recording (details and quotations in sections 2, 3 and 5). Its help pages warn that timing against YouTube is harder: a December 2024 update rewrote the metronome for MP3 and non-YouTube video, but "for YouTube, it's a bit trickier and is still on our to-do list" (search excerpt) — [Soundslice blog, Dec 2024](https://www.soundslice.com/blog/282/new-features-dec-12/); [Soundslice help: metronome](https://www.soundslice.com/help/en/player/basic/8/metronome/)
- A rhythm game synchronised to a YouTube iframe, with a published three-module solution (player engine, two-source beat clock, look-ahead metronome scheduler), described as putting "a metronome on someone else's player" — [DEV Community post](https://dev.to/leviyi/syncing-a-rhythm-game-to-a-youtube-iframe-a-metronome-on-someone-elses-player-3la0)
- Other small projects using an embed as the clock for rhythm play: a four-key web rhythm game that uses `getCurrentTime()` directly, a "YouTube embed beat sync experiment", and "YouTube Rhythm Hero Pro" (titles from search results; pages not read) — [READ_RHYTHM](https://github.com/agussstd/READ_RHYTHM); [beat sync experiment](https://fodi.itch.io/construct-3-youtube-embed-beat-sync-experiment); [YouTube Rhythm Hero Pro](https://ocuc.itch.io/youtuberhythmheropro)
- A music-practice tool that displays the current time of a YouTube player notes that it "has to keep polling the YouTube player for the time" — [youtube-current-time](https://github.com/music-practice-tools/youtube-current-time)
- Open-source projects keep adjusting their YouTube features to the rules (visible player, nothing over it, minimum size, no hidden playback); at least one of these changes is from 2026, which shows the rules are live concerns for small developers — [Sound-Clash pull request 401](https://github.com/BenArtzi4/Sound-Clash/pull/401); [Cr8-audio pull request 170](https://github.com/Cr8-audio/app/pull/170); [Macamp issue 17](https://github.com/holgerkrupp/Macamp/issues/17)

**Where YouTube acted**
- Streamus (2015), a Chrome extension with about 300,000 installs that played YouTube videos as background music: YouTube told the developer to fix it by 17 July 2015 or lose his API keys; reports say YouTube pointed to terms that "do not allow separate playback of audio and video, or advertisements to be blocked". The developer withdrew it around 14 July 2015 — [Tubefilter](https://www.tubefilter.com/2015/07/21/streamus-youtube-music-chrome-extension-takedown/); [The Next Web](https://thenextweb.com/news/how-youtube-killed-an-extension-with-300000-users); [Music Ally](https://musically.com/2015/07/22/google-nukes-streamus-music-plug-chrome-browser/)
- Discord music bots (2021): Groovy shut down on 30 August 2021 after a cease-and-desist letter; Rythm received one about a week later, was given seven days and shut down on 15 September 2021. Wikipedia records the stated ground as violating YouTube's terms and "using it for commercial purposes"; reports describe the bots as re-streaming YouTube audio without its ads. Rythm returned in 2024 with licensed music — [9to5Google](https://9to5google.com/2021/09/13/youtube-nukes-popular-groovy-bot-discord-music-service-for-breaking-platforms-tos/); [Music Ally](https://musically.com/2021/09/13/youtube-shuts-down-music-bot-rythm/); [Digital Music News](https://www.digitalmusicnews.com/2021/09/13/rythm-discord-bot-shut-down-by-youtube/); [Wikipedia: Rythm](https://en.wikipedia.org/wiki/Rythm_(software))
- Musi, a free iPhone music app built on YouTube streams: Apple removed it on 24 September 2024 after a complaint from YouTube's legal team in July 2024; Musi sued Apple and lost, the judge holding that Apple could remove the app under its developer agreement and sanctioning Musi's lawyers; the search tool's summary of 2026 consumer articles says the app was still unavailable in June 2026 — [TorrentFreak](https://torrentfreak.com/musi-sues-apple-over-app-store-removal-following-youtube-complaint-241007/); [Complete Music Update](https://completemusicupdate.com/apple-wins-legal-battle-with-musi-after-judge-rules-music-apps-lawsuit-was-not-the-paradigm-of-candor/); [Music Business Worldwide](https://www.musicbusinessworldwide.com/musi-was-kicked-off-the-app-store-over-copyright-infringement-allegations-now-its-accusing-apple-of-a-backchannel-scheme-to-remove-it/); [FreeYourMusic](https://freeyourmusic.com/blog/musi-alternatives); [PeepsTune](https://www.peepstune.com/why-some-musi-fans-said-they-wouldnt-update-their-iphones-and-what-happened-next/)

### Inferences
- The dividing line in the confirmed cases is the player, not the companion content: products that keep the official player visible and in charge (ads included) have continued, while products that deliver YouTube audio without the visible player were stopped.
- Scale and positioning mattered in the enforcement cases: Streamus had about 300,000 installs, the Discord bots and Musi were far larger, and all were presented as ways to listen to music. A step-practice tool with a few thousand users is far from that profile, but the rules apply at any size.
- Soundslice's own remarks show that tight metronome timing against a YouTube embed is hard even for a specialist team. That supports treating R2 as the main technical risk.

### Gaps
- Not searched by me because the search budget ran out: Chordify and other chord sites, lyrics and karaoke sites, language-learning subtitle tools, DJ-style "mix two YouTube videos" sites, dance-practice loop and mirror sites, YouTube Vanced, Invidious. The parallel researcher's notes in the same folder (`precedents_from_similar_products.md`, section 2) cover Soundslice's history since 2012, Chordify since 2013, LyricsTraining, AllKaraoke, Invidious (June 2023) and an account of YouTube API audits, with sources. They did not cover DJ sites or dance-practice sites either.
- I found no report of YouTube acting against a product that kept the player visible and added its own synced content or sounds. Absence of reports is not approval.
- The court ruling in the Musi case rests on trade-press reports; I did not see the order or its date.

## 8. YouTube Music specifically: is there a separate API or embed?

### Takeaway
I found no official YouTube Music API or YouTube Music embed; the only "YouTube Music API" is an unofficial library that imitates the web client. YouTube Music songs are YouTube videos with ordinary video IDs (art tracks and official music videos), so everything goes through the standard YouTube embed and the standard rules, with the same per-video embedding restrictions.

### Cited Findings
- The best-known library describes itself as "ytmusicapi: Unofficial API for YouTube Music" and says "It emulates YouTube Music web client requests using the user's cookie data for authentication." (package file, version 1.12.3) — [ytmusicapi on PyPI](https://pypi.org/project/ytmusicapi/); [ytmusicapi repository](https://github.com/sigma67/ytmusicapi)
- In that library every song or video is identified by a `videoId`, and YouTube Music's internal type labels are `MUSIC_VIDEO_TYPE_ATV` (which the library maps to "song"), `MUSIC_VIDEO_TYPE_OMV`, `MUSIC_VIDEO_TYPE_UGC` and `MUSIC_VIDEO_TYPE_OFFICIAL_SOURCE_MUSIC` (package file) — [ytmusicapi on PyPI](https://pypi.org/project/ytmusicapi/)
- Songs delivered by distributors appear on YouTube as art tracks on auto-generated Topic channels (see section 4) — [Symphonic](https://support.symdistro.com/hc/en-us/articles/115000437283-YouTube-Art-Tracks); [DistroKid](https://support.distrokid.com/hc/en-us/articles/360013534834-Using-DistroKid-for-YouTube-vs-Uploading-It-to-YouTube-Directly)
- Google's official client for the YouTube Data API (version 40.1.0, 12 Nov 2026) has no YouTube Music resource: the word "music" does not occur anywhere in its API description file (package file, checked by text search) — [@googleapis/youtube](https://www.npmjs.com/package/@googleapis/youtube)
- An open-source player project has an issue titled "Add policy-compliant YouTube provider and document YouTube Music limitations", noting the bans on separating audio, hidden playback and modifying the player (search excerpt; date not shown) — [Macamp issue 17](https://github.com/holgerkrupp/Macamp/issues/17)

### Inferences
- The letters ATV, OMV and UGC most likely stand for art-track video, official music video and user-generated content. This is my reading of the labels, not a documented definition.
- For the app, "YouTube Music content" simply means choosing video IDs that happen to be art tracks or official music videos. They are played with the same `youtube.com/embed/VIDEO_ID` player, checked with the same Data API fields, and are subject to the owner's embedding and region rules.
- Using the unofficial library in a product would mean automated access to YouTube outside the official API. My recollection (not among the retrieved excerpts) is that the Terms of Service restrict automated access; either way it is not a route for this app.
- Art tracks have one practical advantage for a beat grid: they are normally the distributor's own audio file of the recording with no spoken intro or video edit, so their timing should be stable. Their disadvantage is that the owner's embedding policy decides whether they play at all.

### Gaps
- No Google page was retrieved that states outright that there is no public YouTube Music API. The conclusion rests on its absence from Google's developer pages in search results and from the official client library.
- Whether music.youtube.com pages can be framed, and whether a video ID copied from YouTube Music always plays in the standard embed, were not tested or sourced. Recollection, unverified: music.youtube.com refuses to be embedded, and the same ID usually opens on youtube.com.
- Whether Topic art tracks are embeddable as a rule remains unanswered (see section 4).
