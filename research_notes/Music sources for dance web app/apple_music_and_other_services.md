## Key question 1: Apple Music, MusicKit on the Web (MusicKit JS v3): controls, playbackRate, position reporting, Web Audio, browsers, non-subscribers, access requirements

### Takeaway
MusicKit on the Web is the only route found (outside Spotify and YouTube) that an independent developer can obtain by self-service today and that plays full-length mainstream-catalogue tracks for a signed-in subscriber inside a third-party web page, with play, pause, seek, volume and a settable `playbackRate`; the price is the USD 99/year Apple Developer Program. The audio element lives in the page's own DOM rather than in an iframe, but Apple still labels the web product "Beta", documents no supported browsers, gives no precision guarantee for the playback position, and on iPhone the music volume cannot be changed from JavaScript.

### Cited Findings

**Status of the product**
- Apple's overview: "Apple Music content can play directly in the browser. With MusicKit on the Web, users can stream songs, music videos, and radio from Apple Music on your website using MusicKit Web Components or a player you've customized using JavaScript." In the page markup the "Web" section carries a badge reading "Beta" (page fetched 17 Nov 2026). — [Apple MusicKit overview](https://developer.apple.com/musickit/)
- WWDC22 session: "MusicKit on the Web makes it easy to bring Apple Music to your applications using JavaScript. You can discover Apple Music content, let subscribers sign in to access personalized features and play content directly on your website." and "MusicKit on the web must be configured with a token you generate". — [WWDC22 session 10148](https://developer.apple.com/videos/play/wwdc2022/10148/)
- Apple DTS engineer (early Nov 2026): the Getting Started page "documents one script URL, Apple's hosted `https://js-cdn.music.apple.com/musickit/v3/musickit.js`. The documentation doesn't describe a way to check which build that URL served." The `MusicKit.configure()` reference "lists `developerToken` and `app.name` as required, and `app.build`, `app.icon`, `bitrate`, and `storefrontId` as optional." — [Apple forum thread 853567](https://developer.apple.com/forums/thread/853567)
- Developers report that the v3 URL currently serves a build that calls itself `3.2526.0-prerelease.x` (Jul and Nov 2026); in Jul 2022 it was `3.2226.3-prerelease`. — [Apple forum thread 837028](https://developer.apple.com/forums/thread/837028); [Apple forum thread 709713](https://developer.apple.com/forums/thread/709713)
- v3 has breaking changes against v1: "`MusicKit.configure()` now returns a promise". - Self-hosting or bundling the library is not allowed: "You may use MusicKit JS only as a stand-alone library in Your Application, website, or web application and only as permitted in the Documentation (e.g., You agree not to recombine MusicKit JS with any other JavaScript code or separately download and re-host it)." — [Apple Developer Program License Agreement, 3.3.6(D)](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)

- The same typings list on the player: `volume` (settable, "A number indicating the current volume of the music player"), `mute()`, `currentPlaybackTime` ("The current position of the playhead"), `currentPlaybackDuration`, `currentPlaybackProgress`, `currentPlaybackTimeRemaining`, `isPlaying`, `playbackState`, `playbackRate` (read-only in the v1 typings: "The current playback rate for the player"), `canSupportDRM` ("The music player has EME loaded"). — [DefinitelyTyped MusicKit.Player.d.ts](https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/types/musickit-js/MusicKit.Player.d.ts)

This value ranges between 0, which would be muting the audio, and 1, which would be the loudest possible." — [Apple forum thread 771715](https://developer.apple.com/forums/thread/771715)

**Tempo change, `playbackRate` (R4)**
- A developer's dump of MusicKit JS instance state after `setQueue` lists "volume=1 playbackRate=1" (May 2026), so the property exists on the instance of the library Apple currently serves. — [Apple forum thread 825925](https://developer.apple.com/forums/thread/825925)
- Cider, an open-source Apple Music client built on MusicKit JS (Electron/Chromium), ships a "change playback rate" dialog: a range input with `min="0.25"`, `:max="2"`, `:step="0.05"` whose handler runs `this.$root.mk.playbackRate = newValue` on the MusicKit instance. This shows the property is writable and is used for subscription playback in a shipping third-party client. — [Cider audio-playbackrate.ejs](https://github.com/ciderapp/Cider/blob/main/src/renderer/views/components/audio-playbackrate.ejs)
- The developer of a musician-practice app that runs MusicKit.js (v2) inside WKWebView on iOS/macOS, and the same JavaScript in a Chromium-based Android WebView, reports (Jun 2026): "Changing HTMLAudioElement.playbackRate during playback also appears to interrupt playback briefly" and seeks to a nearby buffered position cause "an audible interruption or hitch" on Apple platforms, while the Android Chromium WebView "exhibits significantly smoother seek behavior and supports near-seamless looping". — [Apple forum thread 829729](https://developer.apple.com/forums/thread/829729); [Apple forum thread 829734](https://developer.apple.com/forums/thread/829734)
- Apple DTS engineer's answer to that developer (Jun 2026): "MusicKit's public APIs (MusicKit.js and the native MusicKit framework) document playback and metadata access for Apple Music catalog content. Sample-accurate audio manipulation isn't part of either API surface." For sample-accurate looping of Apple Music content the advice was to file a feedback request. — [Apple forum thread 829734](https://developer.apple.com/forums/thread/829734)
- Pitch is kept by the browser, not by MusicKit: `preservesPitch` "determines whether or not the browser should adjust the pitch of the audio to compensate for changes to the playback rate"; it defaults to `true`. Unprefixed support: Chrome 86, Firefox 101, Safari 17.2 (prefixed `webkitPreservesPitch` since Safari 4). — [MDN source: preservesPitch](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/preservespitch/index.md); [MDN browser-compat-data HTMLMediaElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLMediaElement.json)

**Playback position and events (R2)**
- Event names in the typings: `playbackTimeDidChange` ("the current playback time has changed"), `playbackProgressDidChange` (payload `{ progress }`), `playbackStateDidChange` (`{ oldState, state }`), `playbackDurationDidChange`, `playbackVolumeDidChange`, `mediaCanPlay`, `mediaPlaybackError`, `mediaItemDidChange`, `queueItemsDidChange`, `queuePositionDidChange`, `authorizationStatusDidChange`. Playback states: `none, loading, playing, paused, stopped, ended, seeking, waiting, stalled, completed`. — [DefinitelyTyped MusicKit.Events.d.ts](https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/types/musickit-js/MusicKit.Events.d.ts); [DefinitelyTyped MusicKit.Player.d.ts](https://github.com/DefinitelyTyped/DefinitelyTyped/blob/master/types/musickit-js/MusicKit.Player.d.ts)
- Cider listens to `MusicKit.Events.playbackTimeDidChange`, `playbackStateDidChange` and `queueItemsDidChange` and reads `mk.currentPlaybackTime` and `mk.currentPlaybackTimeRemaining`. — [Cider vueapp.js](https://github.com/ciderapp/Cider/blob/main/src/renderer/main/vueapp.js)
- "The 'playbackVolumeDidChange' listener event does not include the actual volume that the volume has changed to" (Jan 2025). — [Apple forum thread 771715](https://developer.apple.com/forums/thread/771715)
- The underlying element can be reached: "MusicKit JS dynamically creates and manages an `<audio>` element internally when playback begins", reachable through the private path `music._player._currentPlayer.audio`, where `audio.currentTime = 10` and `audio.volume = 0.1` work (Jan 2025). Cider finds the same element in the DOM as `document.getElementById("apple-music-player")`. — [Apple forum thread 771715](https://developer.apple.com/forums/thread/771715); [Cider audio.js](https://github.com/ciderapp/Cider/blob/main/src/renderer/audio/audio.js)
- General browser behaviour for any media element: `timeupdate` "will be thrown between about 4Hz and 66Hz"; for `currentTime`, "The browser does not apply timer rounding", but "The update frequency depends on the browser and media playback pipeline. As a result, successive reads can return the same `currentTime` even when `Date.now()` has advanced. The number of decimal places in the value does not indicate how often it updates or how accurately it matches the audio or video being presented." — [MDN source: timeupdate event](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/timeupdate_event/index.md); [MDN source: currentTime](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/currenttime/index.md)
- Cider compensates output latency when it syncs lyrics to MusicKit playback: `app.lyricOffset = CiderAudio.context.baseLatency + (CiderAudio.context.outputLatency ? ... : 0)`. — [Cider audio.js](https://github.com/ciderapp/Cider/blob/main/src/renderer/audio/audio.js)

**Routing into Web Audio**
- Cider sets `document.getElementById("apple-music-player").crossOrigin = "anonymous"` and then calls `CiderAudio.context.createMediaElementSource(mediaElem)`, feeding its gain, equaliser and spatial-effect nodes from MusicKit's audio element (Electron/Chromium build with Widevine). — [Cider audio.js](https://github.com/ciderapp/Cider/blob/main/src/renderer/audio/audio.js)
- On Apple's native side the audio is sealed: "The content is DRM-protected, SystemMusicPlayer and ApplicationMusicPlayer render audio outside the app's audio graph, and MusicKit has no metering API" (developer, Oct 2026). A community answer (Aug 2026): "due to fairplay DRM, accessing raw audio streams for mixing via MusicKit is not permitted, and Apple does not provide any public API for it." — [Apple forum thread 852190](https://developer.apple.com/forums/thread/852190); [Apple forum thread 807456](https://developer.apple.com/forums/thread/807456)

**DRM and browser behaviour**
- Apple DTS engineer (early Nov 2026): "The MusicKit on the Web documentation doesn't describe supported browsers or environments, headless or otherwise." — [Apple forum thread 852793](https://developer.apple.com/forums/thread/852793)
- Full tracks need the browser's protected-media support (EME). In stock Electron, where `navigator.requestMediaKeySystemAccess` is missing, authorisation and queueing work but "playbackTime stays at 0 and no audio plays", while "Chrome played successfully" with the same token and page (May 2026). — [Apple forum thread 825925](https://developer.apple.com/forums/thread/825925)
- "HarmonyOS WebView does not support FairPlay or Widevine EME, so full-song DRM playback through MusicKit JS does not work on this platform" (developer, Sep 2026). — [Apple forum thread 844525](https://developer.apple.com/forums/thread/844525)
- Insecure origins fall back to previews: "pages served over http from servers that aren't `localhost` will not try to play DRM content" and played 30-second previews instead (accepted answer, Jul 2021). — [Apple forum thread 683958](https://developer.apple.com/forums/thread/683958)
- Chrome problems with the old library: "I have abandoned MusicKit JS V1 and switched to V3, this seems to be more reliable. With V1 the DRM implementation is causing issues for me in Chrome while Safari is working fine." (Jan 2025). — [Apple forum thread 771759](https://developer.apple.com/forums/thread/771759)
- iPhone, background and lock screen. Apple media engineer (Mar 2022): "MusicKit JS is unable to play continuously on iOS in the background. The technical limitation here is that we rely on the `MediaElement` in iOS for playback, which allows defining a single media asset as the source. The queue is managed in the main JavaScript thread, which is not active while the browser is backgrounded, including when the phone is locked." — [Apple forum thread 699926](https://developer.apple.com/forums/thread/699926)
- iPhone, volume. Apple's Safari guide: "On iOS devices, the audio level is always under the user's physical control. The `volume` property is not settable in JavaScript. Reading the `volume` property always returns 1." Current compatibility data for Safari on iOS: "`volume` returns a value and is writable; however, the value is always 1, and setting a value has no effect on the volume of the media object." Since MusicKit's `volume` is "set directly on the HTMLMediaElement", ducking through `music.volume` cannot work in iOS Safari. — [Apple Safari HTML5 Audio and Video Guide, iOS-specific considerations](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/Using_HTML5_Audio_Video/Device-SpecificConsiderations/Device-SpecificConsiderations.html); [MDN browser-compat-data HTMLMediaElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLMediaElement.json); [Apple forum thread 771715](https://developer.apple.com/forums/thread/771715)
- Autoplay rule that applies to every option in these notes: media with sound is "allowed to autoplay only if" (among others) "The user has interacted with the site (by clicking, tapping, pressing keys, etc.)". — [MDN source: autoplay guide](https://github.com/mdn/content/blob/main/files/en-us/web/media/guides/autoplay/index.md)
- Track-to-track gaps: a site playing Apple Music albums through MusicKit JS reports "a noticeable gap between every track" in Chrome and Safari, unlike the native app (Jul 2026, unanswered). Not relevant for single-song practice. — [Apple forum thread 837992](https://developer.apple.com/forums/thread/837992)
- Android: Apple's native "MusicKit for Android" is a separate SDK; the docs say "Automatic Music User Token management is not available for Android" (that sentence is about native Android apps, not the browser). No Apple statement about Chrome on Android was found. — [Apple MusicKit overview](https://developer.apple.com/musickit/); [User Authentication for MusicKit](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit)
- Reliability in Nov 2026: two threads report `authorize()` failing with `AUTHORIZATION_ERROR` right after the user clicks Allow (Chrome, Edge, Safari). Apple DTS says the three feedback reports involved are still "open and under investigation". One developer fixed it on their site: a `Referrer-Policy: no-referrer` header broke the hand-back of the token, and "Changing the header to 'Referrer-Policy: strict-origin' fixed it immediately". — [Apple forum thread 837028](https://developer.apple.com/forums/thread/837028); [Apple forum thread 853567](https://developer.apple.com/forums/thread/853567)

**What the developer needs, and cost**
- "To make requests to the Apple Music API, you need to authorize yourself as a trusted developer and member of the Apple Developer Program. The header of every Apple Music API request requires a signed developer token." The token is a JWT signed with ES256, with `kid` (key ID), `iss` (Team ID), `iat`, and `exp` that "must not be greater than `15777000` (6 months in seconds)"; "Optional, but recommended for web clients, use the origin claim (`origin`)". — [Generating Developer Tokens](https://developer.apple.com/documentation/applemusicapi/generating-developer-tokens)
- Setup: register a media identifier, create a Media Services private key; "The identifier description is displayed as the app name to users when requesting access to Apple Music." "Required role: Account Holder or Admin." — [Create a media identifier and private key](https://developer.apple.com/help/account/capabilities/create-a-media-identifier-and-private-key/)
- Price: "$99 annual membership" (individual or organisation). The fee waiver is only for nonprofits, accredited educational institutions and government entities, and the applicant must "Not be an individual, sole proprietor, or single-person business". — [Apple Developer Program](https://developer.apple.com/programs/); [Fee waivers](https://developer.apple.com/help/account/membership/fee-waivers/)
- User token: "MusicKit automatically manages Music User Token for Apple platforms and for web apps." A third-party project that uses the same token flow notes "This token will expire and needs to be re-authenticated manually after 180 days." — [User Authentication for MusicKit](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit); [Music Assistant docs, Apple Music](https://github.com/music-assistant/music-assistant.io/blob/main/src/content/docs/music-providers/apple-music.md)
- An unanswered forum question (Sep 2025) asks whether individual (not organisation) accounts can ship full-track playback; nothing in the licence agreement or the token documentation distinguishes the two account types. — [Apple forum thread 798921](https://developer.apple.com/forums/thread/798921); [Apple Developer Program License Agreement](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/)

### Inferences
- R1 is met: play, pause, stop and `seekToTime` are public API; the first `play()` must come from a user tap both because of browser autoplay rules and because the licence requires that "users must initiate playback".
- R2 is plausible but unproven. The best available time source is the `<audio>` element's `currentTime`, read every animation frame, with an offset for output latency (the approach Cider takes for lyrics). Reaching the element uses either a private field or a DOM id that Apple does not document, so it can break without notice. MDN's caveat means 30-50 ms accuracy has to be measured per browser; no source found gives a measured figure for MusicKit JS on iOS Safari or Android Chrome.
- R4 is technically available on desktop and Android Chromium through `music.playbackRate` (range used by Cider 0.25 to 2, which covers -30% to +15%), with pitch preserved by the browser. On iOS/WebKit a rate change causes a short audible interruption, so the app should change tempo only while paused or between phrases.
- R5 (own sounds on top): the app's metronome and voice can play through its own Web Audio context beside MusicKit's element. Ducking via `music.volume` should work on desktop and Android but not on iPhone. Routing the Apple audio through a Web Audio gain node works in Chromium (Cider) but is undocumented and could be read as "modifying" the content; whether it works with FairPlay in Safari is unknown.
- Seeking on iPhone produces an audible hitch, so looping a short passage will not be seamless there.
- The combination "Beta badge, prerelease build served from the only allowed URL, no browser support statement, open authorisation bugs in Nov 2026" means the developer should expect breakage and cannot pin a version.

### Gaps
- The MusicKit on the Web v3 reference itself (`js-cdn.music.apple.com/musickit/v3/docs/`) could not be opened. Not verified against Apple's own text: the documented wording and range of `playbackRate`, whether `currentPlaybackTime` is fractional or whole seconds, how often `playbackTimeDidChange` fires, the full v3 event list (the researcher recalls `playbackRateDidChange`, `nowPlayingItemDidChange` and `drmUnsupported` but could not confirm them), and whether the v3 docs name supported browsers (Apple DTS says they do not).
- No first-hand or developer report was found for full-track playback specifically in Chrome on Android phones or in Safari on iPhone in 2026; the evidence is indirect (WKWebView and Android WebView reports, Apple's 2022 statement about iPhone background behaviour).
- Whether `createMediaElementSource` works on the MusicKit element in Safari (FairPlay, HLS) is unknown.
- Measured position accuracy and measured quality of browser time-stretching at -30% were not found.

## Key question 2: Apple's rules: monetising access, modifying or synchronising content, downloading, combining with other audio or visuals; user caps; tempo data

### Takeaway
The licence agreement in force (updated 29 Oct 2026) says MusicKit content may not be modified and "cannot be synchronized with any other content, unless otherwise permitted by Apple in the Documentation", and that access to Apple Music may not be paid for or "indirectly" monetised. A beat-locked animation with a metronome and spoken cues is therefore in territory Apple has never ruled on in public, and Apple staff decline to judge individual designs. There is no user cap for independent developers, only unspecified request-rate limiting, and the Apple Music API has no tempo or beat field.

- A developer building "an iOS MusicKit app that overlays a metronome on top of Apple Music playback" asked how to get beat data or waveforms (2025); no Apple reply, and nobody told them the overlay itself was forbidden. — [Apple forum thread 783914](https://developer.apple.com/forums/thread/783914)
- Tempo change, Apple's own position on the native side. In Mar 2022 an Apple frameworks engineer wrote: "The feature to change the playback rate only applies to content owned by the user, such as songs purchased on the iTunes Store. If it was possible to do it in earlier releases, it was a bug, and we've fixed it in iOS 15.4." Regressions followed in iOS 16.1 betas (fixed) and are reported again for iOS 26.0 (Sep-Oct 2025, no Apple reply). — [Apple forum thread 702397](https://developer.apple.com/forums/thread/702397); [Apple forum thread 703048](https://developer.apple.com/forums/thread/703048); [Apple forum thread 801861](https://developer.apple.com/forums/thread/801861)
- User caps and quotas: the MusicKit section has no limit on the number of users. - Previews without sign-in are also unclarified: a Jul 2026 question whether a free web game may play catalogue previews in a plain `<audio>` element has no reply; the iTunes Search API terms are quoted by a developer as allowing previews "only to promote store content and not for entertainment purposes" (Nov 2026, no reply). — [Apple forum thread 836910](https://developer.apple.com/forums/thread/836910); [Apple forum thread 857472](https://developer.apple.com/forums/thread/857472)

### Inferences
- The synchronisation clause is the main legal risk for the use case. Read literally, an animation, metronome and spoken cues that are timed to the beat of the song are "other content" "synchronized" with MusicKit content. Read in the way guideline 4.5.2(ii) frames it (sync rights for playing "a specific song at a particular moment" or creating shareable audio/video files), the clause targets soundtrack-style and export uses, and a live visual aid that the user starts on a song the user's own subscription plays is closer to a visualiser or a lyrics display. No Apple statement settles which reading applies; three recent forum questions of the same kind are unanswered.
- Because the prohibition on modifying and synchronising applies "unless otherwise permitted by Apple in the Documentation", a `playbackRate` property that Apple documents for the web player (to be confirmed, see Gaps of question 1) would make tempo change a permitted use of the API rather than a "modification". Apple's 2022 reversal for native apps points the same way: it decided that rate change for subscription content in third-party apps can be "safely" allowed.
- A free app with a voluntary donation button does not "require payment". Whether donations are "indirect monetisation" of access to Apple Music is untested; the listed examples (in-app purchase, advertising, requesting user info) are all things imposed on or extracted from the user in exchange for access, which an optional donation is not. Placing the donation link away from the player and not tying any feature to it is the cautious design.
- Computing a beat grid in advance (R3) cannot use audio obtained through MusicKit, because downloading is prohibited. The developer would have to analyse their own lawful copies of the same recordings and match them to Apple's catalogue by ISRC and duration; different masters or editions can shift the grid, so each song needs a check against the stream.
- The web app is not subject to App Review, so guideline 4.5.2 is not enforced by a review step; the licence agreement binds the developer anyway because a developer token requires programme membership.

### Gaps
- The Apple Music Identity Guidelines (now hosted on `marketing.services.apple`) were not opened; attribution and badge rules for a web player are therefore not quoted.
- No written Apple position exists (in anything found) on visualisers, lyric displays, metronome overlays or beat-synced animations with MusicKit; the developer would need to ask Apple directly and should expect no binding answer.
- The actual numeric rate limits for developer tokens are not published.

## Key question 4: TIDAL: developer platform and open-source SDK for web: full tracks or previews, access requirements, terms

### Takeaway
TIDAL publishes a well-built, actively maintained web player SDK (Apache-2.0) that exposes the media element and an API that includes BPM and key, but as of November 2026 third-party clients still receive 30-second previews with the reason `FULL_REQUIRES_HIGHER_ACCESS_TIER`, even for paying subscribers; TIDAL has announced no date and has left dozens of access requests unanswered. ## Key question 7: SoundCloud: Widget API, full tracks or previews, API registration, terms, repertoire

### Takeaway
SoundCloud has two routes. The embeddable widget needs no registration and can be driven from the page (play, pause, seek in milliseconds, volume, progress events), plays ordinary uploads in full for everyone and plays subscription-only ("Go+") tracks as 30-second snippets unless the listener signs in inside the widget; it has no speed control and sits in a cross-origin iframe. The public API returns HLS stream URLs that a page could play in its own audio element, but app registration has been paywalled since 2026 (Artist Pro subscription), Go+ tracks are excluded by label contract, and SoundCloud's own advice for those is "our official widget".

### Cited Findings
**Widget**
- (Search summary; official page not opened.) The Widget API is a JavaScript library at `https://w.soundcloud.com/player/api.js` for interacting with an embedded SoundCloud player; it needs no credentials; documentation is at `developers.soundcloud.com/docs/api/html5-widget`. — [SoundCloud Widget API docs](https://developers.soundcloud.com/docs/api/html5-widget)
- How a widely used open-source player drives it: `SC.Widget(iframe)`, `player.bind(event, handler)` with events `PLAY`, `PLAY_PROGRESS`, `PAUSE`, `FINISH`, `ERROR`; `PLAY_PROGRESS` delivers `e.currentPosition` in milliseconds and `e.loadedProgress`; methods `load(url, options)`, `play`, `pause`, `seekTo(milliseconds)`, `setVolume(0-100)`, `getDuration(callback)`. The iframe is `https://w.soundcloud.com/player/?url=...` with `allow='autoplay'`. — [react-player SoundCloud.js](https://github.com/cookpete/react-player/blob/v2.16.0/src/players/SoundCloud.js)

### Inferences
- Against the requirements, the widget gives R1 (yes), R2 (position arrives through cross-frame messages at the widget's own cadence, so the app must interpolate between `PLAY_PROGRESS` events and will see jitter; 30-50 ms is doubtful and must be measured), R3 (the developer can pre-compute grids, and `bpm` exists only for some tracks), R4 (no), R5 (own sounds yes; ducking through `setVolume`, which on iPhone probably has no effect for the same reason as any media-element volume), R6 (no registration or fee; embedding is the intended use), R7 (subscribers must sign in inside the widget, and currently again every hour).
- The API route would give an own `<audio>` element (HLS through native support in Safari or a library such as hls.js elsewhere) and therefore `playbackRate`, exact `currentTime` and Web Audio processing, but only for tracks whose `access` is `playable`, at the cost of an Artist Pro subscription, a 15,000 plays per day quota, and under terms that were not read. Classic swing-era recordings are label repertoire and would most likely be Go+ (snippet-only through the API); tracks uploaded by today's swing bands themselves are the realistic catalogue.

### Gaps
- `developers.soundcloud.com` could not be opened: the Widget API reference (the researcher recalls, unverified, the getters `getPosition`, `getDuration`, `getVolume`, `isPaused`, `getCurrentSound` and a `SEEK` event), and the API Terms of Use (clauses on syncing with visuals, altering audio, caching, attribution and commercial use) are not quoted.
- How much swing or jazz dance music is on SoundCloud, and what share of it is Go+, was not researched (no search available).
- The price of the Artist Pro subscription was not verified.
- Whether widget audio and the page's own Web Audio sounds play together reliably in iOS Safari and Android Chrome was not tested or found.

## Key question 8: Qobuz, Napster, Mixcloud, Bandcamp, Audius, Jamendo, Beatport/Beatsource and other services: can a web page play and control full tracks, and on what terms

### Takeaway
Of this group only Audius is verifiably open: a free API key, an Apache-2.0 SDK and a plain MP3 stream URL that a page can play in its own audio element with full control, plus a `bpm` field; its catalogue is independent uploads, not the swing canon. Mixcloud has a controllable widget but only for long mixes and without volume control; Napster has an old iframe-based web SDK of uncertain status; no usable evidence was obtainable for Qobuz, Bandcamp, Jamendo or Beatport/Beatsource.

### Cited Findings

### Inferences

## Key question 9: For every service: phone-browser support, whether the audio element is reachable (so `playbackRate` or Web Audio are possible) or sealed in DRM or an iframe, and how accurately position can be read

### Takeaway
Three architectures exist. Players that put a DRM-protected media element in the page's own DOM (Apple MusicKit JS, TIDAL's SDK) allow rate changes and precise time reads but depend on the phone browser's protected-media support. Cross-origin iframe widgets (SoundCloud, Mixcloud, Napster) seal the element, so there is no rate control and position arrives by message. Plain stream URLs (Audius, SoundCloud API for playable tracks) give full control. On iPhone no element-based player can have its volume changed from script.

### Cited Findings
- Apple MusicKit JS: element created in the host page (`<audio id="apple-music-player">`, also `music._player._currentPlayer.audio`); `playbackRate` set by a shipping client; Web Audio routing done by a shipping client in Chromium; iPhone playback relies on the media element and stops queue handling when the browser is backgrounded or the phone locked; Apple documents no supported browsers. — [Cider audio.js](https://github.com/ciderapp/Cider/blob/main/src/renderer/audio/audio.js); [Cider audio-playbackrate.ejs](https://github.com/ciderapp/Cider/blob/main/src/renderer/views/components/audio-playbackrate.ejs); [Apple forum thread 699926](https://developer.apple.com/forums/thread/699926); [Apple forum thread 852793](https://developer.apple.com/forums/thread/852793)
- Apple MusicKit JS on phones, developer evidence: the same MusicKit.js code runs in WKWebView (iOS) and in a Chromium-based WebView (Android); seeks and rate changes hitch on WebKit and are smooth on Android (Jun 2026). — [Apple forum thread 829734](https://developer.apple.com/forums/thread/829734)
- TIDAL SDK: `getMediaElement()` returns the element; `<video playsinline crossorigin="anonymous">` in the page; FairPlay and Widevine both configured, which covers Safari and Chromium browsers; position from `currentTime`; third parties limited to previews. — [player index.ts](https://github.com/tidal-music/tidal-sdk-web/blob/main/packages/player/src/index.ts); [shakaPlayer.ts](https://github.com/tidal-music/tidal-sdk-web/blob/main/packages/player/src/player/shakaPlayer.ts); [tidal-music discussion 351](https://github.com/orgs/tidal-music/discussions/351)
- SoundCloud widget: iframe from `w.soundcloud.com`; position through `PLAY_PROGRESS` events in milliseconds; rate change impossible from outside ("CORS prevents"). — [react-player SoundCloud.js](https://github.com/cookpete/react-player/blob/v2.16.0/src/players/SoundCloud.js); [soundcloud/api issue 557](https://github.com/soundcloud/api/issues/557)
- SoundCloud API: HLS URLs (`hls_aac_160_url`) that the app plays itself; some catalogue is "delivered only as encrypted HLS" and Go+ is excluded. — [soundcloud/api openapi/api.yaml](https://github.com/soundcloud/api/blob/master/openapi/api.yaml); [soundcloud/api issue 605](https://github.com/soundcloud/api/issues/605)
- Mixcloud widget: iframe from `www.mixcloud.com/widget/iframe/`; `progress(seconds, duration)` events; no volume. — [react-player Mixcloud.js](https://github.com/cookpete/react-player/blob/v2.16.0/src/players/Mixcloud.js)
- Napster: player iframe; `playtimer` events. — [Napster/napster.js](https://github.com/Napster/napster.js)
- Audius: MP3 URL for the app's own element. — [Audius TracksApi.ts](https://github.com/AudiusProject/apps/blob/main/packages/sdk/src/sdk/api/tracks/TracksApi.ts)
- Browser facts that apply to every element-based option: `playbackRate` is supported in all current browsers including Safari on iOS; "The pitch of the audio is corrected by default"; Gecko "mutes the sound outside the range `0.25` to `4.0`"; iOS Safari ignores writes to `volume`; `timeupdate` fires at 4-66 Hz; `currentTime` update frequency "depends on the browser and media playback pipeline". — [MDN source: playbackRate](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/playbackrate/index.md); [MDN browser-compat-data HTMLMediaElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLMediaElement.json); [MDN source: timeupdate event](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/timeupdate_event/index.md); [MDN source: currentTime](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/currenttime/index.md)
- Web Audio processing of a media element is done with `createMediaElementSource()`, after which the audio "can then be played and manipulated" (for example through a gain node). — [MDN source: createMediaElementSource](https://github.com/mdn/content/blob/main/files/en-us/web/api/audiocontext/createmediaelementsource/index.md)
- Iframe players need the autoplay permission delegated (`allow="autoplay"`) or a user interaction inside the frame's page context before script-initiated playback is allowed. — [MDN source: autoplay guide](https://github.com/mdn/content/blob/main/files/en-us/web/media/guides/autoplay/index.md)

### Inferences
- Position accuracy ranking (expected, not measured): own element with plain or HLS stream (Audius, SoundCloud API) is best; DRM element in the page (Apple, TIDAL) is nearly as good on desktop and unknown on phones; iframe widgets are worst because every reading crosses a message channel and the widget decides how often to report.
- For ducking on iPhone the only script-level volume control is a Web Audio gain node on an element the page owns. That exists for plain streams, is undocumented for Apple's DRM element, and is impossible for iframes. The practical fallback on iPhone is to not duck and instead make the voice cues loud and short.
- An app that must run on iPhone and offer tempo change on mainstream recordings has exactly one candidate in this scope, MusicKit JS, and should expect audible hitches at each tempo change there.

### Gaps
- No measurements were found for any service of real position error on iOS Safari or Android Chrome.
- Whether Chrome on Android plays MusicKit JS full tracks reliably outside a WebView, and whether Bluetooth output latency is reflected in `AudioContext.outputLatency` on phones, were not established.

### Inferences
- Ranked shortlist for this use case:
  1. **Apple Music via MusicKit JS.** The only way to give subscribers the real swing repertoire with start, pause, seek and tempo change in a phone browser. Costs: USD 99/year, a curated list with self-made beat grids matched by ISRC, no ducking on iPhone, hitches on tempo change and seek in Safari, a "Beta" product with open authorisation bugs, and a licence clause on synchronisation that a strict reader could hold against a beat-locked animation and overlay. The developer should write to Apple with the exact design before investing, and keep the donation link separate from playback.
  2. **SoundCloud widget.** Zero cost and zero approval, works as a second source for songs that bands have uploaded themselves. No tempo change, coarser timing, and subscription repertoire needs an in-widget sign-in that currently lapses hourly.
  3. **Audius.** Best technical behaviour and free, useful only if suitable recordings exist there or bands agree to upload; good as a demonstration catalogue so that the app works without any subscription.
  4. **TIDAL (watch list).** Would become the first choice on technical grounds if `THIRD_PARTY_PROD` access opens: element exposed by design, BPM and key in the API, FairPlay and Widevine. TIDAL's last relayed statement hopes for the end of 2026; its record on dates is poor.
  5. **Not usable:** Deezer (SDK dead, no outside sign-in), Amazon Music (closed beta), Qobuz and Beatport/Beatsource (partner-only as far as known), Napster (uncertain), Mixcloud (wrong content unit), Bandcamp (no API as far as known).
- No service outside Spotify and YouTube supplies a beat grid; TIDAL, SoundCloud and Audius supply at most a single BPM number, which gives tempo but not where beat 1 is. R3 therefore always means a developer-made grid per curated song.
- R4 on mainstream repertoire is available only through Apple; everywhere else it requires an own audio element, which only exists for non-label repertoire.

### Gaps
- The table rows for Deezer, Amazon Music, Mixcloud and Napster rest on indirect or search-summary evidence, and the last row has none; a follow-up with working search and access to the blocked documentation hosts should confirm them.
- The decisive open point for the first-ranked option is Apple's reading of "cannot be synchronized with any other content" for a live, user-started visual and audio practice aid. No public source resolves it.
