READMEs it points to. The user is a swing dancer who runs the PC tools and the phone app; for the app they do nothing
technical at all: you edit, commit, push, watch the build, fix it, and tell them a release is ready.

## 2. How the user wants you to work (these are rules, learned the hard way)

1. **Advisory mode.** Build your best guess, flag it, and put the question in a short numbered list at the end of your
   report. The user answers all questions in one batch. Do not block on questions; do not guess silently about dance
   decisions (who turns which way, where an element ends, distances): those are theirs.
2. **Never add correction layers** (nudging, repulsion, clamping) to make a rule pass. A failed rule check means the data
   is wrong: fix the placements or ask.
3. **Only the editor writes the skeletons.** Since 2026-10-25 the user writes every element by hand in the web editor
   (`python RunWeb.py`), and every edit is saved to `dance/skeletons/` (one file per element) at once: there is one version, the one on disk.
   No script and no agent writes that file. (Until then an agent script, `author_skeletons.py`, generated the skeletons
   from the lurklurk notes and a baseline + `diff.py` guarded the user's edits; it once overwrote an hour of them. The
   script, the baseline and `diff.py` are retired in `dance/old_elements/`.) The same for `dance/compositions.json`.
4. **Everything autosaves.** Any tool you build that holds the user's work writes it to disk on every change (and keeps a
   browser copy), and switching items never discards unsaved state. The beat annotator lost an hour of marks before this rule.
5. **Compositions are the user's.** `dance/compositions.json` and the app's own composition file are edited by the user;
   load, modify, save; never regenerate from scratch.
6. **The app release loop.** For every change to the app: edit, commit, push to `main`, watch the GitHub Actions run, fix
   failures, then tell the user the release number. There is no Android SDK on the PC; GitHub is the compiler (about 3 to
   5 minutes a build). Only pushes that touch `app/`, the Gradle files or the workflow build a release; pushes of
   `dance/`, `music/`, `tools/`, `design/` or the docs alone do not (the `paths:` filter in `.github/workflows/build.yml`).
   Asset and icon changes reach `app/` through `tools/make_assets.py` and `design/make_icon.py`, so they do build.
   Pull before you push: two agents have pushed to `main` on the same day. Push with `git push https://x-access-token:<token>@github.com/LiorAvrahami/6SteP.git main`.
7. **The GitHub token.** The user gives you a fine-grained token (Contents, Actions, Workflows read-write on that repo).
   Keep it only in a temporary file outside both projects, never in a commit, a memory note, a README or a message. Ask the
   user for it again at the start of a new session. `tools/watch_build.sh` reads it from `$GH_TOKEN` or `$GH_TOKEN_FILE`.
   The user may revoke the old token and give a fresh one.
8. **Ports.** 8765 belongs to another app of the user's (requests silently go there). The skeleton editor is on 8771, the
   beat annotator on 8772. Run `netstat -ano | grep :<port>` before starting a server; never kill a listener that is not yours.
9. **Report short.** Lead with the outcome, numbers in tables, a numbered list of questions at the end.

## 3. The dance side (`dance/`, reference: `dance/README.md`)

- **Model.** Units cm. A skeleton is written in the frame of its start: leader's left foot at (0, 0), heading 0 = +y = his
  forward, +x = his right, headings clockwise in degrees. **Facing states** fix all four feet relative to the leader's left
  foot: `side` (follower on his right, both facing the same way, his right shoe and her left 4 cm apart = 34 cm between body centres, user 2026-10-19), `facing`
  (open hold, the facing toes 5 cm apart = 31 cm between body centres, user 2026-10-19; it was 70), `reversed_side` (defined, unused). The user dances the basic side by side; animations
  must start there or they look wrong to them.
- **Lookup key** of a skeleton: (element name, start state, which of the leader's feet is free) = the element and its
  *starting condition*. Elements are merged by name (rock step and triple step each have four starting conditions); a
  composition dictates each element's starting condition from the end of the previous one, so the composer picks the
  variant and refuses a sequence that has none.
- **Elements that exist** (14 skeletons): rock step, triple step (side by side it drifts 10 cm towards the free foot's
  side), rock back cutoff (the user placed all 16 steps themselves), follower underarm pass (from side: she turns
  clockwise; from facing: anticlockwise as lurklurk's Changing Places, he follows her round from behind), lead underarm
  pass (facing), recapture underarm pass (facing to side; the user's name), circle (facing, 8 beats).
- **Rules** (checked by `check.py`, no exceptions beyond an explicit close hold): a weighted foot never moves or rotates;
  a dancer's feet never more than 70 cm apart; the two dancers' shoe outlines at least 4 cm apart (until 2026-10-19: 20 cm circles) and 20 cm body circles never overlap; hands
  in reach (65 cm, a guess); the end state reached. `check.py --storyboard` draws every skeleton to `dance/out/` and you
  review them by eye; the user judged every element by eye too.
- **Timing** (`model.py`, `render.py`, `Timeline.kt`): a foot lands exactly on its count; its weight ramps up over 0.3
  beat (or 45 percent of the gap to the dancer's next step); a foot travels only while weightless, with ease-in-out;
  opacity = weight over a grey silhouette at 0.2. The swung "&" lands at the track's measured swing fraction (0.68 to 0.71).
- **Composer** (`model.compose`, `Composer.compose` in the app): chains elements through the end frame of the previous
  one; for play loops it pads with triple-step fillers until the loop is at least 4 beats and the free foot is restored,
  then chains the loop for the whole track so there is no jump.
- **Compositions** (`dance/compositions.json`): named lists of entries: an element, a sub-composition (RTT = rock step,
  triple step, triple step; "follower pass & back" = follower underarm pass, recapture; pass+circle), either "x N",
  "say: text" annotations (app only), and quiet entries in parentheses, "(recapture underarm pass)", which are danced
  but never announced and are not swipe stops (since v10; the edit dialog has a "quiet" box). The daily routine is
  "5 minutes exercise" (582 beats; 4:03 on Hot Swing): 5 RTT quiet, 15 follower passes, 15 lead passes, 10 cutoffs,
  12 "follower pass & back", 15 lead passes, 10 cutoffs, with quiet bridges where the states do not meet (the cutoff
  starts side by side, the lead pass starts face to face). The user wants bridges quiet and RTT never announced.
- **Tools.** `render.py` makes an MP4 on the music (about 40 fps, stops where a short track ends); the editor
  (`dance/editor/server.py`, port 8771) edits skeletons and compositions, plays in the browser with Web Audio and
  autosaves; a Node test with a stubbed DOM covers the page logic: `node dance/editor/test/test_editor.js`.
- **`python dance/check.py` reports 0 errors** since v17 (2026-10-19). Until then it reported 2 known errors in the rock
  back cutoff (her end 15 cm from his right foot, and 10 cm off the old side spot); the new side spacing and the shoe rule
  agree with the user's own placement, so both are gone. Any error now is a real regression.

## 4. The music side (`music/`, reference: `music/README.md`)

- **Tracks** in `music/chosen/`: Hot Swing (Kevin MacLeod, CC BY, looped to 5:15, 144 BPM, sequenced, dead steady),
  Sunday Reflection (127) and Slow Your Roll (123) by Laughing Manny & The Swinging Dicks (CC BY-NC-SA: fine privately,
  a deal with the band is needed before any commercial release; contact form on their Free Music Archive page). The user
  wants saxophone-led real swing; the whole search history and their 1 to 10 scores are in the README.
- **Beat grids** `<track> - beatgrid.json`: `beats[]` is the time of every beat and is used directly (it is NOT uniform
  for the live band), `bars[]` the bar starts, `swing` the "&" fraction, `grid` = `fixed` (comb-search tempo, Hot Swing),
  `tracked` (librosa beats snapped to onsets, Sunday Reflection) or `annotated` (the user's own marks, Slow Your Roll).
- **Annotating by ear**: `python music/tools/beat_annotator/server.py` (port 8772) shows a high-resolution mel
  spectrogram; Space plays, Enter marks a beat, `1` a downbeat, marks autosave to `<track> - taps.json`;
  `python music/tools/beat_annotator/grid_from_taps.py <hot|sunday|slow>` interpolates the grid (constant tempo between
  marks, running period beyond them), writes it and plots the tempo and phase to `analysis_<key>.png`. The previous
  automatic grid is kept as `- beatgrid.analysis.json`.
- **Slow Your Roll is the hard track.** The band bends the tempo on purpose: base 122.8 BPM, two bars at 111 (58.9 to 63.2 s),
  two bars at 136 to 138 (82.7 to 86.2 s), smaller bends at 33 to 37 s (+4 percent) and 43 to 45 s (−6 percent); 8 of 57
  bars are more than 3 percent off, 14 percent of the time; a fixed metronome ends up 0.8 beat off. No net drift over the
  tune and only 1.4 percent spread outside the bends: a steady band playing with the beat. The user's idea for later:
  grade exercises by using the sections of this track where the beat moves (harder) or does not (easier). The app shows
  a per-track `difficulty` text next to the title.
- **Tempo variants** (`music/tools/make_variants.py`, output `music/variants/`): every track time-stretched to −40, −30,
  −20, −10, +10, +20 BPM with the pitch unchanged, Rubber Band R3 "fine" engine offline (the command-line tool is in
  `music/tools/rubberband-4.0.0-gpl-executable-windows/`; the script finds it there, or through `--rubberband`, or falls
  back to ffmpeg's rubberband filter and records the engine in `variants.json`). 96 kbps mono, 48.7 MB. The script's
  `--check` verifies with onset correlation that every beat of the grid lands at `beats[i] / tempo` in the variant file;
  all 18 pass (lag within 16 ms of the original, stretch linear within 3 ms). A reviewer suggested CBR encoding so the
  phone's seeks are frame-accurate; the files are CBR 96k.

- **Build and release.** `.github/workflows/build.yml`: JDK 17, Android SDK 34, Gradle 8.7, `gradle assembleRelease`,
  the APK attached to release `v<run number>` (the user installs from the releases page; the version code is the run
  number). Signed with the committed PKCS12 keystore `app/keystore/sixstep.p12` (alias and password `sixstep`), so
  each APK installs over the last; the repository is public, which the user accepted. AGP 8.5.2, Kotlin, Material3
  DayNight theme without an action bar.
- **The redesign (2026-10-28).** The user drew the app in Lunacy: `design/app_layout.free` (a zip of JSON; each page has a
  hidden text layer "Description of page" saying how it works) and PNGs of its pages in `design/app_layout_design_screenshots/`.
  Pages: Launcher, Launcher tutorial (help mode), Dancefloor, Explore, Heart, Settings (left empty). Icons are Lucide
  (ISC): `design/make_ui_icons.py` turns the SVGs in `design/lucide/` into `res/drawable/ic_*.xml`. The font is Inter
  (SIL OFL) in `res/font/`. Colours are the draft's (`Ui.kt`). Licences in `assets/licenses/`.
- **Files** (`app/src/main/java/org/lior/sixstep/`): `DanceData.kt` (skeletons, states, elements with starting
  conditions, compositions with sub-compositions, "x N" and "say:" entries, `CompositionStore` merging the asset file
  with the user's own file on the phone, `Composer`), `Timeline.kt` (foot tracks, weights, travel, `elementIndexAt`),
  `FloorView.kt` (`FeetPainter`, the one drawing of the dancers: shoe soles, dashed arrows, grid, through any camera;
  `FloorView`, the top view with the camera that keeps the couple's feet about half the screen and stays between the
  dance floor's bars, the title, the count and the annotation banner), `StepStrip.kt` (a sideways strip of step
  pictures with a scroll bar and annotation callouts: the dance floor's bottom bar and the explore rows), `Piece.kt`
  (`Piece`: an element version, a building block or a composition; the stops; `Rarity`, how unusual a pose is),
  `Audio.kt` (`BeatGrid` with `beatAt`/`beatSeconds` interpolating the non-uniform beats and `scaled(tempo)`, `Track`
  and `TrackVariant`, the clocks, `Metronome`, `Speaker`, `MusicPlayer`), `Playback.kt` (the music plan and the playing: made
  from scratch at every play, see Clocks), `Ui.kt` (the draft's colours, outlined boxes), and the activities: `MainActivity`
  (the launcher; keep the class name, home-screen shortcuts point at it), `DanceFloorActivity` (extras `kind`
  element|block|composition, `name`, `variant`, `autoplay`; it always opens on the first step), `ExploreActivity`, `HeartActivity` (the email, the
  website and the beer links: `WEBSITE` and `PAY_URL` are still empty, the user has to give them), `SettingsActivity`.
  `tools/check_app.py` checks resources, ids, string arguments and leftovers before a push.
- **Clocks and the music plan** (`Playback.kt`, rewritten 2026-10-28 after the user found the dance jittering on play
  after a pause and a few steps: "when pausing there should be no memory of the animation left over, playing should
  initialize everything from the step that we are currently in; for every step the app should know via a lookup which
  beat this is in the audio"). The plan lays the songs along the dance once, for the chosen song and tempo: the first
  track's first downbeat (`BeatGrid.startBeatIndex`) on dance beat 0 with four beats of it before (the count-in), each
  next track on the first element start at least 2 beats after the previous file runs out (250 ms before its end), the
  snare and hi-hat in between. A chosen song repeats; shuffle goes through all of them in a random order fixed for the
  session. `segmentAt(b)` is the lookup: every dance beat has one place in one file. `play(b)` stops everything, opens a
  new MediaPlayer, seeks it to b's place, starts it when the seek reports back, runs the dance on a `TempoClock` from
  that instant and hands over to the `MusicClock` (the player's position through the beat grid) after 220 ms with a
  `SlewClock` fading the difference out over 1.2 s; the next track is opened in the gap and started on its planned beat.
  `stop()` releases every player and forgets the clock, the drums, the voice and everything scheduled. A change of song,
  tempo or mute while playing is a stop and a play from the same beat (so unmute picks the music up where the dance is).
  The clock never wraps: the floor maps a looping piece onto its timeline (`playBeat`, `pieceBeat`, `clockBeat` in
  `DanceFloorActivity`) and tells `Playback` where elements start (`boundaryAfter`); a pause keeps only the step and
  which loop it is in. The old engine's in-place seeks, tempo crossfades and track hand-overs are gone.
- **The dance floor** (one for everything since 2026-10-28; the old `PlayerActivity` and `FloorActivity` are gone).
  Swipe left or right: the next or previous stop (the start position one beat before count 1, then every instant a foot
  lands; it wraps round), flow (the feet travel, at twice the beat length, trapezoid easing) or schema (dashed arrows,
  both dancers at once). Swipe down: the bars, a tap closes them; double tap or play: play (the bars close); a tap or a
  double tap while playing pauses; a swipe while playing jumps to the next part or back (the old player's 2 s rule,
  `BACK_REPLAY_SECONDS`): a composition's entries, any other piece's elements. Top bar: play/pause, tempo (the 7 offsets
  of the song's variants, the same offset for every song), song (shuffle, or one song over and over), mute (music,
  drums and voice; a change of any of these while playing is a stop and a play from the same beat), flow/schema (manual stepping only; play always flows), edit (a "not implemented yet" note).
  Bottom bar: every stop, the current one framed and followed while playing, the annotations (a composition's "say:"
  texts and entry names; a building block's element names) as khaki callouts; tap a stop to go there. Compositions play
  once and end on "Done!". Play starts from exactly the picture of the step (the beat where its weight has settled);
  a swipe or a tap on a step while playing starts afresh there too, and shows the part's name without reading it aloud
  (the music does not dip under the voice: user 2026-10-28). Schema arrows are drawn over the shoes, darker, outlined
  in black. Elements and building blocks loop: chained to about 1200 beats when they close on themselves
  (`chainedLoop`), otherwise from the start position again after 2 beats (an even period keeps the music's bars). The
  daily exercise opens playing; everything else opens paused with the bars shown. The system bars are hidden on the floor.
- **Launcher.** The daily exercise's tile shows how long it takes (its beats plus a 4-beat count-in at the chosen song's
  tempo and offset, or the songs' average for shuffle); the little floor dances the "quick recap" at 1.5 times that
  tempo (user 2026-10-28: "all the elements that we learned one after the other without repetitions": made in the app
  from the daily exercise, every entry once, the quiet bridges kept, so it follows the exercise when that changes); help swaps
  the little floor for the draft's two explanations and draws arrows to the tiles (`HelpArrows`).
- **Explore.** Groups Elements (one row per version), every row subtitled with how it starts and ends (user
  2026-10-28; a version that starts and ends like another adds its free foot, a building block its elements),
  Compositions, Building Blocks (folded by default; `explore_open_*` preferences). Each row's three pictures start
  centred on the step that stands out most: `Rarity` describes a pose relative to the couple (the feet around their
  middle, his-to-her direction along x, headings as short vectors) and takes the step with the lowest Gaussian density
  among the poses of every element. Dragging one row puts the others back.
- **Metronome.** Snare on the odd counts, closed hi-hat on the swung "&" and the even counts; scheduled on its own thread
  at exact uptimes from the clock. Both sounds are synthesised by `make_assets.py`.
- **Speech.** Annotations are fetched once from Google Translate's TTS endpoint and cached per phrase (`cacheDir/tts_<md5>.mp3`),
  prefetched at the start of a session; the phone's own voice is the fallback after waiting up to 1.2 s for an in-flight
  download. Speech plays as media with headroom; the music dips to 60 percent under a phrase and is always restored
  (completion, error, stop, a watchdog). The player holds audio focus for the session with `setWillPauseWhenDucked(true)`
  and ignores "may duck" requests, so the system never dims the whole app; a real loss (a call) pauses the workout.
  This was the fix for "the music and the annotations both go dim sometimes" (2026-10-19); the diagnosis also named the
  phone's output limiter reacting to music + voice + metronome at full scale, hence the headroom.
- **Preferences** (`6step`): `metronome_over_music`, `speak_annotations`, `snare_on`, `hihat_on` (the settings page);
  `bpm_offset`, `song` (a track key or `shuffle`), `muted`, `strategic` (schema mode) (the dance floor's top bar);
  `explore_open_elements`, `explore_open_compositions`, `explore_open_blocks`. Gone with the redesign: the exploration
  floor's free `bpm` slider (the tempo is the song's), the main screen's switches and the player's options bar.
- **Shipped compositions and the phone's copy.** `CompositionStore` reads the phone's own file when there is one and only
  adds shipped compositions it does not know. Since v9 a shipped composition carries a `revision`; a higher one replaces the
  phone's copy unless that copy is marked `edited` (set by the phone's edit dialog, which the 2026-10-28 redesign removed). Bump the revision whenever you change a shipped
  composition, or the phone keeps its old copy.

## 8. Pitfalls seen in this environment

- Windows with Git Bash: MSYS rewrites arguments that look like paths (`/CN=...` for openssl: set `MSYS_NO_PATHCONV=1`);
  long heredocs with quotes break: write a script file and run it. `python -I` hides the user-site packages (numpy,
  librosa live there): run your own scripts without `-I`. Git warns about CRLF on every commit; harmless.
- The rendered video is slow if you draw full-frame layers; the renderer blends cropped layers (40 fps).
- MediaPlayer seeks on MP3 are frame-accurate only with `SEEK_CLOSEST` (used); positions reported by the player lag the
  sound by a few ms, which the slewed hand-over absorbs.
- When a Python interpolation gets one bad mark (NaN or negative time) every derived beat vanishes: the annotator
  filters marks and guards the period.
